# Any Music Development Guide

## Start work

- Locate the target module, current implementation and tests, then read its nearest `AGENTS.md`. When working from the repository root, explicitly read the target package's guide.
- Identify the runtime first: `userscript` (Tampermonkey), `tauri` (desktop), or `shared`. Infer it from paths, call chains and the reported environment when unspecified. If ambiguity remains, analyze the shared boundary before asking for missing information. Trace and verify each runtime separately for cross-runtime tasks.
- `apps/userscript` and `apps/tauri` are production runtimes. `packages/music-workbench` owns shared product orchestration; `packages/ui` owns controlled UI. Preserve visible contracts and storage isolation during migration.
- Start with the [documentation index](docs/en/README.md), then [Userscript Development](docs/en/userscript/development.md) or [Desktop Development](docs/en/desktop/development.md). For shared ownership, read [Project Architecture](docs/en/cross-platform/architecture/project-architecture.md) and [Reusable Package Boundaries](docs/en/cross-platform/architecture/reusable-package-boundaries.md). For TypeScript/Vue naming, extraction, builds or dependencies, read [Development Workflow](docs/en/cross-platform/architecture/development-workflow.md); its coding-style rules do not apply to Rust.
- Use `$any-music-userscript-runtime` for GM integration, `$any-music-tauri-runtime` for desktop IPC/native data/accounts, `$any-music-ui-delivery` for product UI implementation/review, and `$music-source-adapter` for source or playback-startup behavior. Capture skills record website contracts; they do not establish GM or Rust transport acceptance.

- The product is unreleased: implement the current architecture directly. Do not add compatibility packages, previous product-schema readers, source JSON importers, archive UI or duplicate IPC aliases. Current plugin upgrade/rollback and crash recovery remain supported.

| `packages/network-routing`                                         | Pure request competition, cancellation/timeouts and proxy health; inject transport, clocks and credentials                      |

| `packages/plugin-center`                                           | Generic identity/lifecycle; music contracts only through `/music-sources`                                                       |

| `packages/plugin-music-creation`                                   | Built-in drafts, materials, editing state and specialist UI; published recipes remain host-owned; lightweight root, lazy `/vue` |

| `crates/am-plugin-runtime`                                         | Install/grant/context/provenance and commit/revoke authority through Store/Clock/Ids/InstallFiles; no concrete IO               |
| `crates/am-plugin-net`                                             | Anonymous HTTP, public-target validation and bounded transport; native Gate supplies authority; no account credentials/proxies  |
| `crates/am-plugin-package`                                         | Bounded ZIP/resources, integrity and signatures; no networking, install/grant authority or execution                            |

- Keep dependencies one-way: `apps -> shared packages`, `ui -> core/audio-composition`, `core -> audio-composition`, `plugin-source-* -> core/plugin-center`, and the `plugin-center` music entry `-> core`. audio-composition has no internal dependencies; shared packages never depend on apps.
- `music-workbench -> core/ui/audio-composition/plugin-center` is for browser renderers only, without GM, Tauri, Electron or Node imports. Userscript retains one host account/proxy; multi-account/proxy composition belongs to `apps/tauri`.
- `music-workbench -> plugin-sdk` is only for trusted core/wire conversion. SDK root and `/music` stay lightweight; `/schema` uses build-generated validators only. core, ui and source implementations never depend back on SDK.
- `music-workbench -> plugin-ui-vue -> ui/plugin-sdk`: theme directory metadata stays free of Vue/styles; trusted themes load only through build-known loaders. ui never depends on the plugin framework; built-in themes in both runtimes are outside external-plugin policy.
- Applications inject built-in tag/creation plugins. Workbench never imports their implementations; plugins consume core, plugin-center types and public ui exports without private repository access. Host library writes never rewrite tag/creation namespaces. Disablement retains data and withdraws projections.
- `account-pool -> network-routing`; network-routing has no internal dependencies. Both exclude Node, DOM, GM, Vue, music models and raw credentials. Current product composition belongs to `apps/tauri`; see [Desktop Runtime](docs/en/desktop/runtime-architecture.md).
- Use `workspace:*` for internal dependencies and consume public exports only. Lightweight entries must not eagerly load Vue, source implementations or codecs. Failed dynamic imports must allow retry. New packages need independent, stable, reused responsibilities.
- Put package tests in root-level `test/`, mirroring `src/`. Move tests with implementation ownership; keep application composition tests in the app and fixtures in their owning package's `test/`.
- Add useful comments for module responsibility, public contracts or non-obvious implementation reasons. Preserve domain vocabulary, filenames, APIs and visible behavior during structural refactoring.

## Preserve product contracts

- Follow [Privacy and Secret Handling](docs/en/cross-platform/architecture/privacy-and-secrets.md) for every runtime and artifact. Never commit real credentials, personal contact data, account/browser state or local home/workspace paths in source files, commit messages, captures, screenshots or deleted intermediate commits. Git author/committer email metadata may contain personal addresses, although GitHub noreply is recommended for privacy. Use synthetic fixtures and portable placeholders. Run the pinned privacy gates; never bypass hooks, suppress findings broadly or weaken scanner/CI policy to pass. Review images and binary artifacts manually.

- Use Composition API and `<script setup lang="ts">`. Root components compose dependencies. Components accept typed props and emit events; composables own cross-view state, racing async workflows and effects requiring cleanup.
- Card movement must preserve rendering, paint coordinates and elevation through FLIP interruption, drag previews and landing. Follow the [motion and drop handoff contract](docs/en/cross-platform/features/cross-platform-ui-and-interaction.md#7-motion-and-gestures). Regress both directions, rapid layout reversals and stale completion cleanup; a final screenshot alone cannot verify flicker.
- Product snapshots persist only stable source identities, recipes and necessary operation metadata, never ephemeral media URLs, Blob URLs, media bytes or final disk paths. Disposable bounded resource bytes belong only in the owning runtime's separate [resource cache](docs/en/cross-platform/features/resource-cache.md), outside product backups and credentials. Use `AppErrorState` across layers and storage; retain upstream detail in adapter causes.
- Built-in HTTP uses the owning GM/Rust runtime with explicit `credentials: 'include'`. External desktop packages use native verification and consent. Generic guest networking stays anonymous; declarative source gateways use native source-owned credentials with explicit source/network consent. Catalogs still provide no media resolution; see [Music Source Authentication](docs/en/desktop/source-authentication.md). Userscript fixes `externalPlugins: none`; Tauri composes from `runtime_capabilities`, and native installation rejects unadmitted targets.
- Userscript data requests use `GM_xmlhttpRequest`; its fetch option is still manager transport. Desktop renderer invokes Rust HTTP through IPC; Rust binds account cookies/proxies. Shared `credentials` semantics never authorize renderer credential storage. Do not substitute host `fetch` or WebView cookies. Page signing/capture does not establish native capability.
- Preserve startup order: lightweight media description → native streaming → bounded Range/MSE → complete-read fallback. Custom tracks prefetch bounded leaf segments; seek, track switch and disposal abort old reads. See [Music Source Architecture](docs/en/cross-platform/architecture/music-source-plugin-architecture.md) for budgets, concurrency and fallbacks.
- Maintain both locales, counterparts and indexes. Preserve platform-contract `documentType`/`platform`; update `captureDate` only after a real live recapture.
- Read only the relevant indexed sections; follow the [documentation lifecycle and agent prompt](docs/en/cross-platform/architecture/documentation-lifecycle.md) when adding, closing or consolidating documents. Keep current contracts, unfinished gates and evidence still needed for admission or unresolved issues; delete redundant completed plans and histories.
- Correct obsolete ownership/status/scope statements directly in maintained guides instead of appending contradictory override paragraphs. [Implementation steps](docs/en/cross-platform/architecture/plugin-system-refactoring-steps.md) own current progress; delivery matrices own actual capabilities. Historical command counts or closed states do not define today's product.
- Documents declare `runtimeScope` (repository/shared/userscript/tauri). Remove superseded proposals after migrating needed contracts and open work; do not archive completed plans by default. `platform` identifies the music source, not the runtime. Distinguish website, GM and Rust evidence. Rust-specific conventions belong in desktop docs and `apps/tauri/src-tauri/AGENTS.md`, not shared/userscript rules.
- Write AGENTS.md, repository skills and their references in English; use English documentation links when available. Keep `README.md`/`docs/zh-cn` in Chinese and `README.en.md`/`docs/en` in English. Public SDK/CLI/testkit READMEs use English. Keep identifiers, paths, commands, protocol fields and literal UI/source text exact. Document language does not determine the user's response language.

## Verify and deliver

- Follow [Git Flow Team Policy](docs/en/cross-platform/architecture/git-flow.md): use `main`/`develop` as long-lived branches and feature/fix/release/hotfix topic branches. Commit on topic branches and integrate through reviewed PRs with merge commits. Never directly push, force-push or delete long-lived branches. Publish only explicitly accepted annotated version tags from `main`; confirm all back-merges before deleting completed topics. The guide records the current GitHub plan's server-enforcement limitation.

- Report command, test and build outcomes directly in the handoff. Do not create local log files or per-commit note files unless explicitly requested. Preserve existing referenced evidence; see [verification results](docs/en/cross-platform/architecture/development-workflow.md#verification-results).
- Work from the repository root with pnpm. Install the verified scanner with `pnpm privacy:setup`. Run target tests during changes; before committing complete `pnpm check:privacy`, `pnpm check:privacy:history`, `pnpm test`, `pnpm typecheck`, `pnpm lint`, `pnpm format:check` and `pnpm build`.
- Rust uses the root Cargo workspace, one `Cargo.lock` and `target/`. Read `crates/AGENTS.md` and `apps/tauri/src-tauri/AGENTS.md`. Native changes also run `pnpm check:native`, `pnpm check:rust:msrv` and `pnpm check:rust:deny`. Do not replace explicit release combinations with all features.
- **Start development servers, product previews, emulators, screenshots, clicks or live regressions only when the user explicitly requests browser/application inspection in the current task.** Logic/component tests, builds and local test backends that do not launch product UI may run directly.
- Source/playback changes test request counts, order, concurrency, cancellation and retry. Report missing live acceptance honestly; public-network elapsed time and source inspection are not runtime evidence.
- Report results, verification and remaining limits. Commit/push only when requested. Split commits by responsibility; English messages use Conventional Commits (`type: subject` or `type(scope): subject`, optional `!` for breaking changes) and follow `commitlint.config.js`. Keep Chinese explanations in the task handoff.

See [Development Workflow](docs/en/cross-platform/architecture/development-workflow.md) for guidance/skill maintenance rationale and official sources.

- Execution: VM depends only on SDK/fixed engine; browser adapter/testkit depend on VM/SDK. `/profile`, `/control` and adapter roots stay engine-free. `pnpm check:plugin:vm` is offline build/same-engine testing only. Review Profile/bridge changes and update hashes. A permissionless VM grants no native business/network/install authority; production target admission remains separate.
- Native authority: am-plugin-runtime uses Store/Clock/Ids/InstallFiles for installation, grants and commit/revoke ordering. Application storage/plugins injects separate plugins.sqlite3 (schema 3). Values/provenance/receipts and revocation commit in serialized transactions. Production accepts native-verified results and explicit consent, without fixture seeds, arbitrary grants/sessions or general data relays.
- External transport: am-plugin-net owns anonymous transport/target checks; the application injects native Gate. Every hop/Range/byte delivery shares identity, epoch, budgets and revocation barriers. Reject proxies lacking equivalent public-target constraints, cookies/keys/links and arbitrary host writes. Controlled text/diagnostic saving uses controlled native dialogs with an epoch recheck.
- Desktop author/delivery contracts, native consent, isolated DEV and exact-target admission follow the [delivery matrix](docs/en/cross-platform/architecture/plugin-system-s15-tools-and-desktop-delivery.md). CLI/testkit never enter production applications; close contexts before acknowledging cancellation and install the native resource filter before guest delivery. Unknown required capabilities/contributions/targets fail. Mobile external installation/execution/DEV stays unavailable; remaining device/channel work follows [mobile delivery](docs/en/cross-platform/architecture/plugin-system-s16-mobile-delivery.md).
