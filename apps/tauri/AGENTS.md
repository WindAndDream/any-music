# Tauri desktop runtime

Applies to `apps/tauri`. Read [Desktop Development](../../docs/en/modules/tauri/development.md) and [Runtime Status](../../docs/en/modules/tauri/runtime.md); use `$any-music-tauri-runtime` for platform integration. Native code, permissions and configuration also follow [src-tauri/AGENTS.md](src-tauri/AGENTS.md). Mobile capabilities require explicit declarations.

The native crate belongs to the root Cargo workspace. Application test/typecheck/check:native cover all members; release outputs live in root `target/release/` and root start:tauri consumes that path. Builds/checks do not authorize product launch.

- music-workbench owns shared music behavior. src/platform adapts IPC, HTTP, login, media and storage. Frontend consumes QR/public state/allowlisted business responses, never cookies, CDP connections or proxy passwords.
- Current product schema-2 mirrors recover committed generations and revisions before mounting. Failed writes stop later saves; unsupported schemas are rejected. Product storage does not convert earlier formats.
- Ordinary built-in requests follow `native-http.ts -> http_request IPC -> Rust HTTP` with included credentials. Generic guest transport remains anonymous and follows the native Gate restrictions below. Declarative source authentication belongs to plugins/source_auth, with separate source-owned vault tokens and no built-in CookieStore/proxy/browser authority; see [Music Source Authentication](../../docs/en/modules/tauri/source-authentication.md). Standalone Douyin identity checks use native HTTP and compare the returned UID with the verified account binding. Douyin login/search, watch history/personal likes/collected videos/mixes, mix works and work detail use `douyin-browser-catalog.ts -> douyin_catalog_request -> Rust douyin_browser` in the account's embedded page; shared code receives portable ports only. Imports match page/endpoint and GET-query/POST-form cursors; stopping closes targets. Discover reuses its search WebView per account. Detail reads open on demand and can reuse the page that delivered a matching detail API response. Search and retained detail pages expire after 90 idle seconds. Media bytes stay in Rust HTTP/loopback grants. Both paths cancel through cancel_request, without renderer fetch/cookies or GM doubles.
- Preserve account identity across APIs, lazy pages and media. Rust registers loopback grants; account environment changes revoke old work. GM Range, page BDMS and protected-page capture are not desktop capability evidence.
- src-tauri owns account catalogs, separate CookieStore/HTTP clients, system vault and embedded account pages. Remote pages reach only `account_page_report` through the separate `account-pages` capability; product commands accept only the `main` WebView.
- Account pages are child WebViews of the main window (`browser/embedded`): per-account persistent data directories (macOS: UUID-derived WebKit data stores), store locks and proxies, never headless or test Chromium. Official Douyin pages generate login/search; a document-start bridge reports allowlisted exchanges and Rust drives pages through a bounded CDP-subset driver, operates uniquely matched SMS controls and reads credentials through the native cookie API. Hidden pages stay outside the visible window. Explicit login/verification uses `AccountPageDialog`. On Windows, Discover can lease an account-owned result WebView to the active list. The build-owned WebView2 isolated-world entry mounts the standard theme list in a closed Shadow root, supplies display-only data and relays bounded actions to the main workbench. The source adapter owns the official result target and pagination. Bilibili/NetEase read credentials/page User-Agent only after the user selects completion.
- Windows-debug-only `login_experiment` uses separate temporary profiles/system Chrome or Edge and official requests. Credentials remain in memory without production accounts/vault access. Only user action opens a visible browser; release IPC rejects experiment operations.
- Bilibili uses native QR; Douyin returns official-page QR/status/SMS results through CDP. Unverified challenges use the same account's in-app official page, without invented SMS/CAPTCHA protocols. Model mobile login/QR capabilities explicitly; mobile never falls back to embedded account pages.
- Tests live in test; native unit tests stay with Rust modules. Run pnpm from root. App/browser launch requires an explicit runtime-inspection request in this task.

Run application test/typecheck (including Rust fmt/all-target Clippy), check:native for native changes, then root checks. TypeScript/Vue naming does not apply to Rust; read [Backend Engineering](../../docs/en/modules/tauri/backend-engineering.md) and the native guide.

- Inject tag metadata and its separate `/vue` loader from features/plugins. The creation workspace is paused. Tag data uses its named generation-storage port.
- built-ins use independent source metadata and lazy /runtime assembly. Keep provider IDs separate from module/contribution IDs. Disablement/invalidation cancels old lists/resolution/media; restore never replays tasks. Zero usable sources must not block core views.
- plugins.sqlite3 (schema 3) is native authority. native-plugin-authority injects snapshot/revoke, previews and named delivery ports; the center never creates grants. Native verification/consent drives install/rollback, without fixture seeds, arbitrary grants/sessions or general data-relay commands.
- Generic omit only reads current loopback media grants. plugins/network injects am-plugin-net Gate for external networking, without account cookies/proxies. Reject unknown required capabilities according to S15.

- The product is unreleased: implement the current architecture directly. Do not add compatibility packages, previous product-schema readers, source JSON importers, archive UI or duplicate IPC aliases. Current plugin upgrade/rollback and crash recovery remain supported.

- features/plugins/built-in-theme-directory owns metadata only; built-in-themes registers the Classic root as the production renderer and fallback. The sole MusicSourceWorkbench owns one controller/audio above the complete ThemeHost. Shared/SFC/theme CSS resources are activated transactionally inside its stable Shadow surface; protected slots receive host-only CSS. Build audits record actual static execution graphs.
