# 桌面抖音目录与视口交接

[English](../../../en/modules/tauri/douyin-catalog.md)

账号专属子 WebView 执行官方网页操作，工作台持有产品结果。这里记录搜索、分页及 Windows 隔离世界适配。

## 搜索列表与安全验证恢复

2026-10-04 经用户授权排查“华语”单项结果：当前正式账号响应为 HTTP 200、业务码 0、`search_nil_info.search_nil_type=verify_check`，应用显示安全验证错误。用户手动完成验证后列表自动恢复，首屏九首，按需加载下一页后累计十八首且仍可继续加载。重建后的桌面产物同样通过首屏与下一页操作。正常原生响应包含一条作品的首帧、ack 和九条卡片的后续帧，过滤相关词卡片后共九首。最初“仅一项且无加载更多”的响应未再次复现，不能将当前验证信号认定为其完整原因；另用合成协议及 IPC 回归夹具确认并修复最后一帧缺字段时丢失前帧分页元数据的缺陷。该记录包含正式 Rust/IPC、桌面列表操作和人工验证恢复，不证明 GM 或媒体播放，网页契约 captureDate 不更新。

账号浏览器启动时先进入精选首页 `/jingxuan`，从官方自身资料响应与登录 Cookie 确认账号。首页五秒内没有资料响应且没有在途资料请求、二维码或登录挑战时，最多创建一次临时辅助页面访问 `/user/self` 做兼容确认；已就绪账号的显式个人资料导入操作读取 `sec_uid`。该操作与验证后的凭证确认可使用独立辅助页面。辅助页面始终隐藏；成功、失败、取消或超时后均关闭临时目标，检查过程继续观察当前列表与验证搜索的响应。上述检查不重载或导航当前可见页面，仍保持官方身份响应、读取预算与取消要求。首页持续产生资料响应及辅助页面的逐步行为尚未独立实测。

搜索控件提交前按 250 ms 检查页面初始化完成与唯一匹配的官方控件，确认点击一次后恢复每秒检查登录与安全挑战。Rust 先通过页面控件聚焦并选中原输入，再用页面自身的编辑命令写入关键词（未获得焦点的页面拒绝时，改用输入框原生 setter 与 `InputEvent`）；等待一次任务切换后重新读取当前输入和按钮，确认关键词未被重置、React 字段值一致、按钮中心未被遮挡后才点击。只有输入框和按钮都已被 React 接管（节点上出现 `__reactProps$`）才算控件就绪：服务端渲染的控件更早出现，但在接管前会静默丢弃输入和点击。官方首页要等全部脚本（约 110 个）加载完成才会接管，慢网络下独立 WKWebView 基线实测 5 到 32 秒。macOS 上点击是投递给账号 WebView 的原生 AppKit 鼠标事件（浏览器可信，`isTrusted=true`），CSS 坐标按页面桥接上报的视图顶部遮挡高度换算；Windows 上则通过 WebView2 DevTools 协议的 `Input.dispatchMouseEvent` 依次发送移动、按下、松开，坐标即 CSS 视口坐标，页面同样收到可信输入。其他平台或原生派发失败时，退回 CDP 子集鼠标序列。页面加载与接管预算为 60 秒，从导航或接管账号首页时开始计时；点击后或需要后续页时，产生对应结果页的预算为 18 秒。发现页每个账号只保留一个关键词搜索 WebView。首次搜索在确认身份后接管隐藏的账号首页。退出列表后释放游标和响应缓存，WebView 最多在视口外空闲保留 90 秒。展示租约解除遮罩后，下次搜索会清空结果页顶部的官方搜索框，再输入并提交关键词。如果控件不可用，或者点击后既未导航也未发出搜索请求，就在同一个 WebView 里回到精选首页提交。每次提交只接收在该次浏览器提交时间之后开始、且关键词匹配的请求。原生端单次搜索操作最多等待 85 秒、单个命令 100 秒，界面端为 105/115 秒。提交后等待匹配的官方搜索请求。2026-11-16 经用户明确授权，在 macOS 内嵌传输上实测：关键词搜索返回结果；同一列表页面滚动后由页面自身发出后续 `search/single` 请求，共加载三页；播放经官方详情 API 成功。本次没有出现风控验证，因此未实测应用内人机验证。随后同日用户在 Windows x64 上使用 WebView2 可信点击确认了同样的登录、搜索、翻页和播放流程，同样未遇到验证。超时文案分别注明控件尚未就绪、搜索尚未成功提交或结果响应尚未完成。各列表保留独立游标，即使复用同一个 WebView。

2026-10-04 经用户授权，在当前正式账号的原生浏览器中复现旧流程：合成事件填词并点击后，受控输入被网页重置，页面停留精选首页，没有发出目标搜索请求，最终超时。仅等待页面完成仍会重置输入；改为浏览器原生输入与鼠标操作后，同账号首屏、第二页和复用账号浏览器的新列表均返回 HTTP 200、业务码 0，并分别通过共享适配器解析为九首曲目。一次冷启动首屏约 8.3 秒，同浏览器新列表约 3.2 秒，属于该环境的单次样本，不是耗时保证。验证包括正式账号浏览器、Rust 响应读取与共享列表映射，不包含桌面 UI 操作、人工验证码恢复、GM 或媒体播放；网页契约 captureDate 不因此更新。临时响应文件与诊断代码已删除，账号凭证未改写。

Any Music 音乐列表通过 `douyin_catalog_request` 原样传入搜索文本，由 Rust 校验后，在结果页或精选首页匹配唯一的官方搜索输入与按钮，填词并点击一次。官方网页生成 `/jingxuan/search/<编码关键词>?aid=<本次生成的 UUID>&type=general` 以及请求、签名和游标。共享列表的来源/验证链接使用精选搜索路径，不保存或硬编码一次搜索的 aid。可见验证从精选首页开始。不直接导航结果地址，因为 2026-10-04 独立测试浏览器观察到直达会 302 回旧 `/search/` 路径并返回 502，首页提交则成功。该网页观察不代表新版正式账号浏览器已验收。搜索不会重放接口 URL，也不会在网页失败后退回 Rust HTTP，原生 HTTP 入口拒绝抖音搜索 API 路径。抖音搜索强制串行尝试（包括旧的并行偏好），Any Music 列表在首次风控错误时停止账号尝试并等待用户验证，避免同一搜索在多个账号中同时发起。

Windows 桌面端「发现」将账号的原生结果 WebView 接到当前歌曲列表视口。来源适配器登记请求账号、关键词、结果 WebView 和允许的页面来源。Rust 在 WebView2 的隔离执行环境中加载构建时编译的 Vue 脚本，使用经典主题的列表组件和样式，在一个封闭 Shadow DOM 内渲染。展示期间通过文档样式遮蔽原背景和顶层内容，抑制官网图片、视频和画布的绘制，并禁用原节点交互。遮罩只处理新增和移出的页面顶层节点，保留官网 DOM、结果区布局和滚动容器。隔离环境只接收显示数据并返回有界列表操作，播放和数据写入仍由工作区执行。其他桌面引擎在接入各自的隔离执行环境前使用项目的标准列表。

桌面主窗口中的抖音歌曲结果和 Windows 子 WebView 都使用实测虚拟列表。两个渲染端都使用经典主题的歌曲卡片网格。工作区持有完整结果与选中状态。各渲染端使用自己的主题滚动容器挂载视口附近的条目及预渲染缓冲区，子 WebView 采用主窗口的布局断点。Windows 先在视口外按实际列表尺寸准备结果页，等虚拟列表按恢复位置和官网遮罩一起绘制后再显示。视口被部分裁切或重新打开只读结果时使用应用内列表。打开歌曲操作或展示方式弹窗时，应用先按最新记录的位置恢复列表，等子 WebView 移出视口再打开。弹窗关闭后，子 WebView 绘制当前列表窗口再接手。末页返回后，应用先恢复虚拟窗口，再释放子 WebView。

宿主歌曲视图补齐首屏后再交给注入列表展示。两端按虚拟列表的完整滚动范围判断分页，恢复滚动位置不会触发翻页。向下输入时，距底部约 1.5 个视口高度便可预取一页，距离限制在 240 至 1600 CSS 像素，筛选后的列表沿用常规滚动阈值。同一列表同一时间只读取一页。抖音适配器按需推进官网结果滚动容器并保留其布局，分页继续匹配官方游标，验证通过账号弹窗处理。Windows 仍待实测布局、滚动交接、分页、验证和内存。

抖音搜索及搜索链接导入继续通过账号内嵌页面读取官方 `search/stream` 和 `search/single` 响应，共享适配器解析流式数据并映射歌曲。每个列表独立页面、关键词与游标；消费者向下滚动才请求下一页。官方页面提前加载的响应有界缓存，读取时不重复请求；关闭列表或取消读取后回收页面。滚动优先沿官方结果列表 `[data-e2e="scroll-list"]` 的内容祖先推进，兼容没有作品链接的精选结果卡片；旧页面保留作品链接及 window 滚动回退，避免误滚侧栏。可见验证码和登录弹层分别报告验证、登录错误。等待当前页超时使用 `AM-4003` 并提示重试，不据此认定需要验证或已经没有更多结果。

内容容器存在时，每步滚动只作用于该容器可命中的区域：页面先收到滚轮事件，未被页面取消时再滚动该点下最近的滚动容器；找不到容器才使用页面滚动区域，此外不直接修改 scrollTop。每步重新检查可见区域与剩余距离，容器被遮挡或命中嵌套滚动区时等待，不转向侧栏或外层页面；到底后停止发送滚轮。滚动与验证码地址检查同时识别 `/search/` 和 `/jingxuan/search/`；验证码地址检查排除搜索路径中的关键词，避免搜索 `captcha` 等文本误报验证。

后续翻页的滚动节奏由 Rust `search/scroll.rs` 持有：先等待 180–420 ms，再把不超过 480 px 的短段拆成 16–22 个滚轮增量，按平滑曲线逐渐加速、减速；增量之间等待 28–46 ms，段间停顿 350–1400 ms，距离与停顿在有界范围内变化。按消费需求推进，已有缓存直接读取；当前游标请求一旦发出就停止滚动，等待响应，不在网络加载期间继续推进。计时器只存在于本次读取 future 中，不追赶延迟的滚动步骤；响应完成、取消、验证或原有 18 秒页面超时会结束该轮滚动并按既有规则清理。该算法改善输入节奏，不保证规避平台风控；自动化测试覆盖节奏与清理预算，原生运行时观察记录见下文，网页契约的 captureDate 不变。

列表的错误弹窗在首次打开已恢复的验证错误时即可提供“验证”按钮。仅在打开错误详情时构造轻量验证闭包，不创建迭代器、租约或请求；运行中的失败仍绑定实际失败账号，恢复的闭包使用当前操作账号策略范围内需要验证的账号。用户点击后打开应用内验证弹窗，使用该账号的独立页面上下文和代理；页面按上文规则在挑战出现前保持隐藏。软件观察该关键词的官方搜索响应；共享适配器确认业务成功、包含结果数组且无 `verify_check` 后，Rust 重新读取凭证并关闭展示页面。列表自动从第一页重新加载，固定使用刚刚验证的账号，后续滚动仍沿同账号翻页。仅隐藏验证码、仅存在登录 Cookie、空响应或验证失败响应均不视为搜索验证通过。

后续搜索页返回空数组时，会在关闭目标前检查该官方页面，响应体缺少验证标记时也适用。原生页面检查区分可见验证、登录弹窗和语义不明的空响应；登录弹窗结合原账号 Cookie 核对，不能仅凭弹窗认定退出登录。检查固定使用原列表、原会话，不发送搜索请求或滚轮输入；正常结束与异常结果的协议判断仍由共享适配器负责。

搜索验证从初始页面开始观察匹配响应，账号确认后复用已经加载的精选首页提交关键词，不再重复导航首页。用户已自行进入同一关键词的结果页时等待该页响应，不重发搜索；登录或验证码仍可见时等待用户操作。只有加载完成且没有挑战的无关页面才返回首页准备搜索。验证成功后的资料确认使用上述临时辅助页面，因此当前搜索结果不会因凭证交接被刷新或跳到个人页。自动化回归覆盖路由保留、响应隔离和辅助页面清理，原生搜索观察见下文。

验证入口只属于当前运行时列表，不进入持久化配方。关闭错误弹窗、取消验证、删除列表或停用来源会取消等待；十分钟超时返回可展示错误；关闭验证弹窗会取消验证。每次验证使用独立 UUID，旧轮询及取消不能读取或关闭替换会话。自动测试覆盖以上状态和页面响应隔离；下文原生观察确认了一次用户完成验证、自动关闭和隐藏会话重载；更广泛的账号验收仍独立记录。

验证启动 IPC 等待页面创建与初始导航完成再返回；页面创建失败不能归因于抖音风控。

用户取消时先按验证 UUID 中止正在启动的会话，再等待交接锁完成清理，避免取消被启动等待阻塞。CDP 响应已经送达后，即使连接紧接着关闭，也先交付该响应；尚未完成的命令仍报告连接结束，业务层的取消检查继续阻止过期结果写入。

## 抖音验证范围

记录的 Windows 正式链路观察覆盖指定 QR／SMS 凭据提交（2026-10-03）、账号绑定的多页搜索及分段原生滚动（2026-10-25），以及用户完成验证后的首屏恢复（2026-11-01）。空页核对、响应隔离、重试、取消及进程清理有确定性回归；这些观察基于此前的系统浏览器传输，不代表内嵌页面传输已经验收（后者目前只有自动化测试）；也不证明 GM 传输、完整结果耗尽、所有账号组合或完整播放验收。

原始缓存空响应及早期七／八页失败未保留，确切原因未知；另有间歇首屏超时尚未解释，超时本身不建立风控挑战。网站契约 `captureDate` 不变。原生命令变化必须重建／重启 Rust，前端热更新不能替换正在运行的原生进程。
