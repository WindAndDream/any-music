### 1.1 扫码登录局部契约（2026-10-02）

本次使用用户指定为 `test` 环境的现有 Chrome DevTools MCP 专用 Chrome，未使用 Codex 内置浏览器的会话。用户完成两轮扫码：第一轮直接登录，没有二次验证；第二轮出现身份验证，用户选择接收短信、输入验证码后成功登录。第一轮的确认响应在跳转后不可读；第二轮以临时只读响应投影及时记录字段类型和状态码，未记录原始响应、凭证或个人资料。以下确认状态来自第二轮，不能据此补写第一轮未观察到的响应。

| 阶段         | 方法与地址                                                    | 业务参数与已观察字段                                                                                                                                                                                                        |
| ------------ | ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 生成二维码   | `GET https://login.douyin.com/passport/web/get_qrcode/`       | 查询包含 `next`、`need_short_url`、`need_logo`、`is_new_login`；成功响应为 `message` 与 `data`，`data.error_code=0`，包含 `qrcode`、`qrcode_index_url`、`token`、`expire_time`、`is_frontier`、`frontier_params`、`captcha` |
| 检查扫码状态 | `POST https://login.douyin.com/passport/web/check_qrconnect/` | 表单包含 `need_logo`、`is_frontier`、`token`、`is_new_login`、`next`、`need_short_url`；等待响应为 `data.error_code=0`、`data.status="new"`，另有 `captcha`、`desc_url`、`description`、`extra`、`scan_app_id`              |

此次网页使用 `aid=6383`、`passport_jssdk_version=3.4.9`、`passport_jssdk_type=normal`、`is_from_ttaccountsdk=1`。这是已观察的网页 SDK 参数，不是原生 HTTP 已验证的最小请求集合。

`data.qrcode` 是 PNG 的 Base64 图片，页面用 `data:image/png;base64,...` 展示；`qrcode_index_url` 是 HTTPS 地址，`token` 是非空的扫码会话标识。图片与二维码内容是两种表示，不能把 PNG Base64 当作二维码内容再次编码。该样本的 `expire_time` 为 Unix 秒时间戳，与响应服务器时间相差 60 秒；不能当作剩余时长或固定有效期。`is_frontier=true`，`frontier_params` 包含 `access_key`、`frontier_device`、`method`、`product_id`、`service_id`，推送分支与轮询的关系尚未验证。二维码图片、地址和会话标识只属于临时登录会话，不进入资料库、夹具或文档。

两类请求均观察到查询键 `fp`、`verifyFp`、`sign`、`qs`、`msToken`、`a_bogus`，以及 `account_sdk_source`、`account_sdk_source_info`、`request_host`、`device_platform`、`biz_trace_id` 和 Passport SDK 的 `p_*` 元数据。请求头包含 `web-sdk-version`、`x-tt-passport-csrf-token`、`x-tt-passport-aid-sign`、`x-tt-passport-verify-portrait`、`x-tt-session-dtrait`、`x-tt-passport-trace-id`；响应包含 Ticket Guard 结果头和 `Set-Cookie`。仅记录这些字段的存在，不保存原文，也不据此认定所有字段均必需。共享音乐请求的本地 `a_bogus` 实现尚不能证明足以实现 Passport 登录。

已观察的扫码状态如下。HTTP 200 不等同于业务成功；`captcha` 在这些样本中为空，不能仅凭该字段判断是否需要二次验证。

| 状态检查响应                              | 已观察行为                                                                                                                                       |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `data.error_code=0`、`status="new"`       | 等待扫码                                                                                                                                         |
| `data.error_code=0`、`status="expired"`   | 响应另含二维码图片、地址、会话标识、有效时间等生成字段，网页随后继续等待扫码；不假定所有过期响应均带这些字段                                     |
| `data.error_code=2046`                    | 打开身份验证选项；这不是二维码失效或登录成功                                                                                                     |
| `data.error_code=0`、`status="confirmed"` | 短信验证后检查成功，响应包含 `redirect_url` 与 `user_data`，随后网页进入已登录个人页；`user_data` 包含凭证字段，不能整体交给渲染端或存入公开状态 |

二次验证响应包含 `encrypt_uid`、`account_flow`、`passport_scene`、`verify_scene_desc`、`verify_ways[]`、`common_params`、`biz_params`、`event_params`、`extra_params`、`user_info`、`schema`、`url`。`common_params`/`biz_params` 提供 `std_verify_flow_id`、`std_verify_scene`、`std_verify_template`、`std_verify_token`、`std_verify_type`、`std_verify_way` 等挑战上下文。`url` 在该样本中指向官方二次验证 JavaScript SDK 资源，并不是可直接嵌入的认证网页。临时票据、上下文及 SDK 调用状态由运行端私有登录会话持有，不向 UI 暴露原始对象。

| -------------------------- | ----------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `face_verify`              | 手机刷脸验证；含 `auth_ticket`、`flow`、`cert_app_id`、`scene`、`is_auth_verify` 等 | 只观察选项；没有打开刷脸流程，也没有获取或记录生物识别资料 |

接收短信分支的已观察顺序：

1. 用户选择“接收短信验证码”后，网页调用 `POST https://login.douyin.com/passport/web/challenge/`，响应包含 `passportiv`、`template`、`ts`；这些安全上下文不进入公开状态。
2. 网页自动调用 `POST https://www.douyin.com/passport/web/send_code/`。表单含 `mix_mode`、`type`、`encrypt_uid`、`verify_ticket`、`copywriting_key`、`ies_safety_diversion_tag`、`new_verify_flow`、`std_verify_*`、`is6Digits`、`aid`、`new_authn_sdk_version`。成功响应为 `message="success"` 与 `data`，含脱敏 `mobile`、`mobile_ticket`、`retry_time`；本次 `mobile_ticket` 与请求中的 `verify_ticket` 均为空，不能据字段存在认定票据必需。`retry_time=60` 与页面重发倒计时一致，运行端应使用响应值。
3. 页面显示脱敏手机号、验证码输入框、重发倒计时、“验证”“无法验证通过？”和“选择其他验证方式”。用户自行输入验证码并提交 `POST https://www.douyin.com/passport/web/validate_code/`。表单沿用挑战字段，增加 `code`，不含发送请求的 `is6Digits`；响应投影包含 `data.ticket`。响应头包含 `x-tt-passport-mfa-token`，`Set-Cookie` 含 `passport_mfa_token`，由同一私有 CookieStore 接收。
4. 后续 `check_qrconnect` 表单在普通检查字段外增加 `passport_mfa_retry_tag` 与 `std_verify_*`，并携带更新的 Cookie，返回 `confirmed`。不能仅在软件中收集验证码，或看到验证请求成功就直接提交账号凭证。

本次短信请求线上参数为 `mix_mode=1`、`type=3737`、`std_verify_scene=account_login`、`std_verify_template=ato_web`、`std_verify_type=MFA`、`std_verify_way=mobile_sms_verify`。提交的 `code` 为 12 个十六进制字符，记录的是编码形态，没有保存用户输入或编码值；在同一测试浏览器读取官方二次验证 SDK 后，确认 `type` 与数字验证码按 ASCII 字节 XOR 5，再输出十六进制；合成向量 `22 → 3737`、`123456 → 343736313033` 用于自动化测试。SDK 安全上下文生成仍未实现，不能把该编码确认当作原生短信流程已通过验收。发送与提交查询含 `new_authn_sdk_version`、`device_platform`、`biz_trace_id`、`msToken`、`a_bogus`，请求头另含 `x-secsdk-csrf-token` 及 Passport 验证相关头。

原生 HTTP 可行性也做了有界试验：使用现有 Tauri Rust 依赖创建干净 `CookieStore` 与 `reqwest` 客户端，不导入浏览器 Cookie、设备令牌或签名；生成请求仅带上述公共 SDK 参数、语言、`next` 和二维码选项，以及抖音 Origin/Referer。生成返回 HTTP 200、`error_code=0`，二维码图片、地址、会话标识均非空。随后用同一 CookieStore、返回的会话标识和六个已观察的检查表单字段请求 `check_qrconnect`，返回 HTTP 200、`error_code=4031`，没有进入等待状态。因此“原生可生成二维码”已验证，“原生完成扫码与二次验证”尚未成立；不能把被拒绝的检查当作未扫码继续无限轮询。该试验没有保存二维码、会话标识或凭证，临时试验程序已移除。

Tauri“账号与代理”新增试验性抖音 PNG 二维码、状态检查、二次验证选项、接收短信、验证码提交及重发倒计时。原生待登录会话私有保存 QR/MFA 参数；UI 只接收公开选项、脱敏手机号、倒计时和状态。二次验证未完成时暂停检查，短信验证后使用原挑战 token、实际完成的 `std_verify_way` 与更新的 Cookie 再查最终状态，确认登录 Cookie 后才提交保险库。取消使用公开 UUID 隔离旧响应，过期要求显式重新生成；`4031`/CAPTCHA 停止请求并提示系统 Chrome/Edge，刷脸与发送短信选项也由该入口完成。没有嵌入官方认证页面。

同日刷新该测试 Chrome 后，再次观察到生成成功及检查返回 `status=new`，生成响应的会话标识原样用于检查表单。读取该页面加载的公开 Passport SDK 确认：当前 UI 的检查调用固定发送 `is_frontier=true`，响应中的同名字段表示推送可用性，不能直接用来决定轮询参数。

公开 SDK 的请求认证已在 Rust 中实现：查询键按字典序取前十项，以未 URL 编码的值及全部表单项计算 SHA-256 `sign`，`qs` 是所选查询键名的 XOR 5 十六进制表示；`x-tt-passport-aid-sign` 使用公开客户端配置、当日 UTC 中午的 `ts`、HKDF-SHA-256 与 HMAC-SHA-256，绑定 `aid` 和请求路径。请求在签名后统一序列化，使用自己的 CookieStore 中的 CSRF 值或默认 CSRF 值。网页请求头与独立计算结果仅比较一致性，没有保留实际签名；离线合成向量及表单绑定有自动化覆盖。这不生成设备指纹、BDMS 或 Web SecSDK 安全上下文。

当前原生状态检查仍被安全校验拒绝；补齐上述认证、公共 SDK 参数、CSRF 与检查分支后，干净 Rust 会话仍收到 `4031`，服务端说明因账号安全风险阻止访问，`captcha` 为空。旧版 SDK 的 GET 检查也未进入等待状态。软件内完整扫码、原生短信发送/提交、安全上下文和凭证提交仍需实站验收；已通过的自动化覆盖不能证明这些链路已可用。手机刷脸与发送短信分支尚未单独复测。

随后使用正式 Rust 生成/检查实现单独获取二维码，以临时 PNG 展示给用户。用户明确确认扫描的是该 Rust 二维码，并在手机确认登录；只在用户操作后检查一次原会话，结果仍进入安全拒绝分支，没有返回 `confirmed`，没有提交凭证。该结果证明二维码可扫描，不证明原生完成登录；原生会话也未观察到可供软件消费的 `2046` 挑战。扫码图片及临时试验程序已移除，测试 Chrome 的已有验证页面保留。

### 1.2 扫码与原生请求复测（2026-10-03）

通过同一 Chrome DevTools MCP 专用测试 Profile 打开官方登录页，用户自行扫码、接收短信并提交验证码。临时只读响应投影观察到 `new → error_code=2046 → send_code → validate_code → confirmed`，最终检查仍是 `POST https://login.douyin.com/passport/web/check_qrconnect/`。只保留方法、路径、参数键、公共 SDK 常量及响应字段类型；未将浏览器 Cookie、设备状态或实际签名复制给 Rust。此次没有复测刷脸、发送短信、搜索或媒体接口，也没有观察到可据以更新契约的 `challenge` 请求。

本次校对确认以下原生请求契约及修正：

1. 普通二维码请求仍使用 `passport_jssdk_version=3.4.9`、`passport_jssdk_type=normal`。`is_new_login` 查询只出现在生成请求，状态检查只在表单中发送该字段；Rust 已移除检查 URL 的多余查询项。对实际生成及普通检查请求，解码 `qs` 得到参与签名的查询键，独立计算 SHA-256 和 HKDF/HMAC，仅比较一致性，均与网页请求匹配。`msToken`、`a_bogus` 在 Passport 签名后加入，不应把最终 URL 的全部查询键重新排序后当作最初的签名输入。
2. 短信发送/提交实际使用 `passport_jssdk_version=5.1.2`、`passport_jssdk_type=lite`，查询包含 `aid`、`is_from_ttaccountsdk`、`language`、`account_app_language`、`device_platform` 和 `new_authn_sdk_version=1.0.0.428-web`，表单也包含该验证 SDK 版本。两条请求没有二维码分支的 `ts`、`sign`、`qs`、`web-sdk-version` 或 `x-tt-passport-aid-sign`；仍观察到 `msToken`、`a_bogus`、CSRF 与验证相关头。

最终 `confirmed` 请求的签名只绑定普通六项二维码表单；`passport_mfa_retry_tag` 与 `std_verify_*` 由后续重试阶段追加到线上表单。独立计算对比确认：仅使用普通表单可匹配该请求的签名，把追加字段也纳入则不匹配。Rust 现按调用阶段拆分签名表单和追加表单，保留原二维码 token、实际完成的验证方式及同会话 CookieStore；短信请求改用已观察的 lite SDK 参数。离线测试覆盖追加挑战不改变普通签名、挑战实际进入请求体、短信 SDK 与二维码认证隔离，以及既有暂停/取消与公开投影契约。

## 2. URL 识别

导入器支持以下稳定网页形态：

- `www.douyin.com/search/<keyword>` 与 `www.douyin.com/jingxuan/search/<keyword>`；
- 搜索 URL 中的 `modal_id=<awemeId>`，优先按当前打开的单个作品处理；
- `www.douyin.com/video/<awemeId>`；
- `www.douyin.com/note/<awemeId>`；
- `www.douyin.com/collection/<mixId>/<index>`；
- `www.douyin.com/user/<secUid>`；
- 用户页的 `showTab=like`、`tab=favorite` 等喜欢视图；
- 当前账号用户页的 `showTab=recommend` 推荐视图；
- 用户页的 `showSubTab=compilation` 作者合集视图；
- 当前账号 `showTab=favorite_collection` 下的视频、音乐、合集和收藏夹子页；
- `www.douyin.com/user/self`，首次迭代时通过当前用户接口解析 `sec_uid`。

只接受精确的抖音主机名；相似域名、非数字作品/合集 ID 和未知路径会返回 `unsupported-url`。

拼接多个 URL 或重复页面参数的链接在本地返回 `invalid-input`，不请求账号或平台。喜欢的完整链接是 `https://www.douyin.com/user/self?showSubTab=video&showTab=like`；`showTab=favorite_collection` 默认表示收藏视频，`showSubTab=compilation` 才表示收藏合集。`showTab=record` 表示当前账号观看历史，不复用个人作品接口；其他用户的历史页在本地拒绝。视频或图文导入惰性读取一次详情；存在有效 `mix_info.mix_id`（或 camelCase 字段）时按需展开所属合集，没有合集则保留单作品。播放仍解析所选作品，不展开合集；合集失败保留其错误，不退化成单作品成功。

桌面运行端通过所属账号的官方页面捕获观看历史、个人喜欢、收藏视频、收藏合集目录和合集作品；每个迭代器有独立页面及固定类型/合集身份，收藏视频游标来自 POST 表单，历史与喜欢的时间戳游标可以递减。共用原生有界响应缓存，消费者停止、失败或取消时关闭页面。CDP 只把业务流程消费的事件入队，无关资源、字节进度及页面生命周期事件不参与响应等待。网页拒绝保持原有登录、验证或权限错误，不重放本地签名请求。该实现经 IPC 替身与本地 WebSocket 测试验证。

2026-10-12，经用户明确授权，Chrome DevTools 以 `--user-data-dir` 加载应用中指定抖音账号的已有 Profile，观察两条链接的官方网页请求，不复制凭证。历史首屏为 `www.douyin.com/aweme/v1/web/history/read/`、`max_cursor=0`；后续请求来自 `www-hj.douyin.com` 的同一路径，使用前页时间戳游标。响应均为 HTTP 200、`status_code=0`，消费字段为 `aweme_list`、`max_cursor`、`has_more`，另有不消费的 `aweme_date`；首屏 18 个作品，两次后续页分别 20、19 个作品。视频 `7667482938171202417` 的详情返回 `mix_info.mix_id=7687608991332960299`，页面随即发起 `/mix/aweme/`，`cursor=0`、`count=6`；响应有 6 个作品、`cursor=6`、`has_more=0`。随后使用同一 Profile 按正式 Windows 配置启动原生账号浏览器，通过实际 Rust `AccountProcess`、CDP、详情读取与导入模块复测：历史首屏 18 个作品、下一页 20 个作品且时间戳递减，目标视频详情关联同一合集并读取到全部 6 个作品。首次诊断探针误用了隐藏标签页，后续页超时；按正式运行端的非活动桌面和页面目标配置修正后通过，没有据此改变产品滚动策略。临时探针已移除，未复制凭证。这分别提供网页观察和原生捕获证据；渲染端 IPC 来自自动化替身覆盖，未执行完整桌面产品导入、GM 实站请求或媒体播放验收。

## 3. 作品字段映射

Web API 使用 snake_case，视频和图文详情页的 React Flight 数据使用 camelCase。平台类型与映射器同时接受两套名字，统一输出：

- 稳定曲目 ID：`douyin:video:<awemeId>`；大整数 ID 始终保存为字符串。
- 标题：依次使用 `item_title`、`itemTitle`、`desc`、音乐标题。
- 作者：`author.sec_uid/secUid + nickname`；缺失时回退音乐作者。
- 封面：图文首图优先，其次视频封面、音乐封面。
- 时长：视频 `duration` 已为毫秒；音乐 `duration` 为秒，映射时乘 `1000`。
- 发布时间：`create_time/createTime` 为秒，映射为 Unix 毫秒。
- 标签：`text_extra[].hashtag_name/hashtagName`；图文额外加入“图文”。
- 统计：播放、点赞、评论和收藏映射到 core 的可选统计字段。

持久化作品 Track 只包含 `awemeId`、`video/note` 解析配方和稳定页面 URL，不包含 `play_addr`、`play_url` 或图片下载地址。收藏音乐使用 `douyin:music:<musicId>` 和 `audio/music` 配方；播放时重新读取 `music/detail`，收藏列表中的短时 `play_url` 同样不会进入 Track。

## 4. 视频与图文播放

普通视频的 `music.play_url` 往往只是背景配乐，不能代表作品中的完整人声。因此按以下顺序选择媒体：

1. `video.bit_rate_audio_list` 中最高码率的独立音频；
2. `video.play_addr` 或 H.264 播放地址；
3. `video.bit_rate[].play_addr`；
4. 最后才回退 `music.play_url`。

HTML `<audio>` 可以读取 MP4 中的音轨，所以没有独立音频时直接使用完整视频 URL，仍不下载或渲染画面。图文作品（`aweme_type=68` 或存在 `images[]`）没有视频轨，使用 `music.play_url`。短内容使用 `eager`，长内容使用 `range`；每次播放重新调用详情接口，解析结果只在当前播放会话缓存。

2026-09-04 复测确认：`video.bit_rate_audio_list` 可能为空；有值时每项使用 `bit_rate/bitRate`、`quality_type/qualityType`、`gear_name/gearName` 与自己的 `play_addr/playAddr` 建立独立音频档位。缺少独立音频时优先使用 `video.play_addr/playAddr` 这类完整作品地址，不能让高码率 `video.bit_rate/bitRate` representation 抢在完整地址前面，否则 DASH 视频轨可能被 `<audio>` 接受却静音。只有完整地址缺失时才尽力使用 bit-rate 候选，并排除 URL 路径明确包含 `media-video-avc1` 或 `media-video-hvc1` 的纯视频轨。`play_addr.url_list` 中的多个 URL 是同一档位的 CDN 备用节点，不是多个音质；因此接口只返回完整地址而没有 `bit_rate_audio_list` 时，播放器只能展示一个可播放档位。`br` 查询参数、MIME 和文件扩展名只在结构化字段缺失时用于兜底。首次播放选择最高有效 rank，切换时必须在新详情响应中重新匹配完整音质 ID，不能按数组位置或旧短时 URL 猜测。

详情接口空结果或非鉴权错误时，适配器先解析 `www.douyin.com/video|note/<id>` 的 React Flight 详情；普通视频还可回退 `www.iesdouyin.com/share/video/<id>` 的 `_ROUTER_DATA`。React Flight 中先出现的同 ID 卡片可能只有标题和封面；只有对象包含当前可解析媒体时才结束回退，否则必须继续尝试另一页面和分享页。`aweme/detail` 无可识别业务码的 HTTP 403 也允许尝试公开页：公开页返回同一作品即说明这是接口层拒绝而非内容私密；页面同样失败时仍保留原始 `access-denied`。登录失效、`2483` 和明确的权限业务码不会被页面回退吞掉。

抖音 VOD 地址在 B 站宿主页的表现并不统一：部分地址在 `no-referrer` 的原生媒体元素中可直接流式播放，另一些会在元数据阶段被拒绝。因此只有 Referer 的来源先尝试原生 URL 和备用节点；失败后才通过 GM HTTP 携带抖音 Referer，使用 Range 抽取已编码音轨并重封装为碎片媒体。入口若忽略 Range、重定向并声明过大的完整正文，GM 适配器会在响应头阶段中止，Range reader 只在当前会话内使用 `finalUrl` 重试真正的 CDN 地址。短时地址不进入错误状态、日志或资料库。

Userscript 元数据用 `@connect douyinvod.com` 显式授权 VOD 根域，Tampermonkey 同时允许其子域。官方作品描述还可能先使用 `aweme.snssdk.com/aweme/v1/playwm/`，因此该精确媒体入口也需要 `@connect`。[GM-R3](../../../../baselines/theme-ui-migration/T13-gm-r3.json)记录缺失权限的失败及修复后真实 GM 的 302→CDN 206→Range／MSE 播放。`*.douyinvod.com` 不是有效域名写法；生产脚本固定 `externalPlugins: none`，只授权精确内置域名，不以 `@connect *` 回退。该运行端证据不改变网站契约捕获日期。

备用 CDN 节点以 250 ms 间隔错峰竞争到首个编码音频包，胜出后取消其余请求；Range 首探测和整个 MSE 首碎片预算均为五秒。实测 MP4 的 AAC 首包可带约 `-0.16s` 预卷时间戳，Mediabunny muxer 要求非负时间线，因此播放器以首包为零点整体平移时间戳而不重编码。MSE 通过背压只保留播放点前约 30 秒、后约 15 秒，避免长音频在后台快速灌满 SourceBuffer。用户拖到窗口外时会中止旧读取，并通过按时间定位的音频包从目标处重建 MSE；因此先向后跳、再回到已清理的前段不会永久等待，暂停态 seek 保持暂停，播放态 seek 在新首片段可用后续播。连续拖动只保留最后一次重建。浏览器明确拒绝对应编码时继续生成音频专用 Object URL；Range 输入不可用或首碎片超时时则跳过重复抽取并进入完整媒体兜底。切歌会中止在途读取并释放缓冲与 Object URL。

## 5. 分页与终止条件

搜索适配器必须收到明确的 `data` 数组；HTTP 200、业务码 0 或只有元数据/ack 的流式帧不能证明结果为空。缺失或非数组的列表报 `invalid-response`；明确返回空数组、`has_more=0/false`，且 `result_status` 缺失或为 0 时正常结束分页，之前已加载过内容也适用。空数组仍声明还有内容、缺少终止标记或带异常结果状态时，第一页报告 `invalid-response`，后续页报告 `pagination-unavailable`。`verify_check` 仍优先报告人工验证。桌面端还会在关闭目标前检查每个空响应所属的官方页面，包括第一页，核对可见验证或登录弹窗，不重放搜索请求。异常空响应也不能作为安全验证已经完成的依据。规则经合成响应与桌面 IPC 测试验证，`captureDate` 不变。

搜索用 `offset/count`，合集、用户作品、喜欢和个人收藏用游标。作者合集与收藏合集先惰性读取各自的合集目录，再逐个按页展开 `mix/aweme`；收藏夹也先读 `collects/list`，再逐个展开 `collects/video/list`。不会同时拉完全部目录。异步迭代器不并行预取。满足任一条件立即终止：

搜索的当前网页契约固定使用 `count=10`，因此搜索分页与账号列表的默认页大小分开维护。

- `has_more/hasMore` 为假；
- 原始作品数组为空；
- 非搜索列表映射后没有有效曲目；搜索页若只有被过滤的直播等卡片且仍有下一页，则保留按需加载入口；
- 平台声称还有下一页但游标没有变化。

最后一项是防止异常响应造成无限循环的保护。游标来源按接口读取 `cursor` 或 `max_cursor/maxCursor`。

第一页已经返回内容且声明 `has_more=true` 后，第二页及以后若返回语义不明确的空 `data` 或发生无法识别的来源错误，适配器映射为 `pagination-unavailable`（`AM-3006`）并保留已加载内容；明确的正常结束按上文处理。该错误本身不能证明需要人机验证。已识别的断网、超时、限流、鉴权、权限和风控码 2483 保留各自语义；`search_nil_info.search_nil_type=verify_check` 或桌面官方页面检查确认可见验证时，报告 `verification-required`（`AM-3005`）。分页提示和错误详情引导用户查看或收藏已加载歌曲，并稍后重试，不暗示未经确认的验证。重试会从第一页重新加载，后续页能否恢复取决于来源。

## 6. `a_bogus` 与风控

`a_bogus` 必须针对最终未含 `a_bogus` 的精确查询串和真实 HTTP 方法生成。主路径不再假定本地算法可以长期等价于网页：抖音宿主页在 document-start 发现当前页面的 BDMS，把它装进隐藏同源 iframe，并把 iframe 的底层 `fetch` 固定为拒绝；BDMS 只能返回签名 URL，不能产生第二条 API 请求。喜欢与收藏视频再调用页面现有 Web SecSDK 的 `webSignUrl`，补齐 `timestamp`、查询签名和两个请求头。实际数据传输仍只有注入的 GM HTTP 请求。

非抖音宿主页不能安全复用页面主世界。适配器改用不含 `allow-same-origin` 的 `data:` 沙箱 iframe，加载锁定版本 BDMS，并用 CSP 禁止 `connect/img/frame/object/form` 等外联能力；SDK 无法读取宿主 DOM、Cookie 或 storage，只能通过带随机通道号的 `postMessage` 返回签名 URL。Tampermonkey 的 `GM_cookie` 仅为当前请求读取目标域 `UIFID`/`UIFID_TEMP` 与 `s_v_web_id`，值不写入 GM value、日志或 DOM。纯 TypeScript SM3、RC4 与自定义 Base64 实现保留为 SDK 超时/不可用时的尽力降级，不作为已验证的动态签名主路径。

锁定版本 BDMS 是平台运行时而非 Userscript `@require`，不会进入脚本包；2026-09-02 生产构建的测试产物为 2,087.08 kB（gzip 519.27 kB）。离线或 CDN 缓存未命中时，签名提供器最多等待五秒后退回本地尽力签名；受保护列表若仍不可用，再按统一规则打开后台页，不会因外部脚本加载失败阻塞应用。

参数有两套已验证版本轮廓：搜索流使用 `19.6.0 / 190600 / update_version_code=0`，其业务和设备字段在签名前按键名字典序重建；个人资料、喜欢、收藏、推荐和作品详情使用 `17.4.0 / 170400`，并保留各端点的网页顺序。2026-09-04 的详情请求还包含 `webcast_sdk_version=170400`、`webcast_version_code=170400`，并像受保护列表一样附加 `timestamp`、查询签名和可用的 Web SecSDK 签名头。UA、窗口、屏幕、CPU、内存、网络和媒体能力都从当前浏览器动态读取，不使用固定设备常量。

搜索的安全字段顺序是 `...webid, msToken, a_bogus, verifyFp, fp`；其余 17.4 请求先把 `verifyFp/fp` 放进 BDMS 覆盖范围，再追加 `msToken/a_bogus`。设备状态提供器在一个 `DouyinApi` 实例内保持回退 `verifyFp` 和 19 位 `webid` 稳定，每次请求重新读取可变化的网络、在线与窗口状态；能读取页面/目标域真实值时优先使用真实值。

业务码 `2483` 仍映射为专用 `DouyinRiskControlError`，其通用语义码为 `verification-required`（`AM-3005`）；401/鉴权业务码映射为 `not-authenticated`，403/隐私限制映射为 `access-denied`，429 映射为 `rate-limited`。搜索列表收到验证错误时显示明确提示，并只在用户主动点击后打开对应搜索页，不自动跳转。喜欢、收藏视频和推荐的固定顺序仍是“完整 GM 请求 → 校验 HTTP、JSON、业务码与列表结构 → 任一不可用时打开后台页”；因此普通 403、HTML 拒绝页和接口结构漂移也不会静默返回空列表。

所有主动 API 请求通过应用 `platform/http` 注入的 GM HTTP 客户端并显式设置 `credentials: 'include'`。即使 Any Music 挂载在非抖音网页，也不能主动退回宿主页面原生 `fetch`。抖音宿主页在 `document-start` 保存原始 `fetch`，让页面自己的 BDMS 包装它；签名探针命中后只读取最终安全字段并立即以 `AbortError` 终止，真正的数据请求仍由 GM HTTP 发出，其他页面请求原样委托给原始 `fetch`。跨站搜索使用无同源权限且禁止联网的沙箱 BDMS + 目标域 Cookie 状态；喜欢和收藏需要同源 Web SecSDK 时会在直接 GM 请求失败后进入后台页。

## 7. 跨站封面

抖音封面与 B 站封面都可能显示在任意宿主页。UI 不直接使用裸 `<img>`，统一通过 `RemoteImage` 设置 `referrerpolicy="no-referrer"`，避免把当前页面 Referer 带给第三方 CDN。该策略属于跨音乐源展示边界，不写入抖音 mapper 或 `Track`；图片失败时显示占位，不持久化图片字节。
