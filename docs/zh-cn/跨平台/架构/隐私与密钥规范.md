# 隐私与密钥规范

英文对应页：[Privacy and Secret Handling](../../../en/cross-platform/architecture/privacy-and-secrets.md)。适用于两种生产运行端的贡献者、代理、来源抓包、测试、文档、CI 与发布产物。

## 仓库允许保存的数据

禁止提交真实账号 Cookie、授权头、访问／刷新令牌、API 密钥、代理凭据、签名私钥、个人联系方式（除 Git 作者／提交者邮箱元数据外）、账号数据库、浏览器配置目录、已认证 HAR、登录二维码令牌或恢复材料。范围包含一组提交中后来删除的文件、提交说明、截图、日志、备份和编译产物。编码或加密真实凭据不能使其成为合格测试数据。

运行端秘密只放在所属 GM 存储、原生凭据库或私有 CI 密钥存储中。`VITE_*` 会进入客户端构建，不能保存秘密。公开配置只允许 `.env.dev`、`.env.prod`、`.env.staging` 中已审核的 `VITE_APP_ENV`、`VITE_APP_DEBUG`。本地 `.env*` 保持忽略；`.env.example`／`.env.template` 只放空值或明确占位符。测试公私钥应由测试生成，不能复制开发者或发布身份的密钥。

Android 正式 JKS 及 Base64 导出保存在检出目录外；编码密钥文件名同时受 Git 忽略和隐私路径门禁保护，强制添加仍会被拒绝。CI 签名值只放在受保护的 `release-signing` 环境，配置见[构建与发布](GitHubActions构建与发布.md#接受贡献前配置-github)。私钥内容和密码不能进入测试夹具、日志、产物或文档。

使用保留示例域名、明确的合成标记和测试自有 ID。抓包脱敏保留字段名、类型、顺序和行为，不能仅因脱敏修改 `captureDate`。证据中的实际个人目录和项目目录改成 `<user-home>`、`<project-root>`。原有哈希和日期仍表示脱敏前的历史测量，脱敏不等于重跑或新运行端验收。提交截图前，以可读分辨率检查账号身份、二维码、密码与通知；自动文本扫描不覆盖每个像素或安装器内部。

Git 作者／提交者邮箱允许使用个人邮箱或 GitHub 提供的 noreply 邮箱；由于提交元数据会公开，建议注重隐私的开发者在每个克隆执行 `git config --local user.email YOUR_GITHUB_NOREPLY_ADDRESS`（替换为实际地址）。此例外仅限 Git 作者／提交者元数据；协作者署名、提交说明和源文件中仍不得填写私人邮箱。既有提交仅因作者／提交者邮箱为个人地址，无须重写历史。

## 安装与执行门禁

```sh
pnpm install --frozen-lockfile
pnpm privacy:setup
pnpm check:privacy
pnpm check:privacy:history
```

`privacy:setup` 从 Gitleaks 官方发布下载固定版本 8.30.1。直链返回服务端错误时，改用 GitHub 发布资产 API 下载同一个归档。两条路径都核对仓库内固定的 SHA-256，再将程序缓存在被忽略的 `.local/privacy-tools/`。支持 Windows、macOS、Linux 的 x64／arm64，解压需要 `tar`。离线检查复用已验证的本地安装；缺少程序、内容损坏或版本错误时拒绝继续。安装不会修改全局 Git 配置。

`check:privacy` 检查已跟踪文件和未被忽略的新工作区文件，拒绝敏感文件名（含 DER 导出）、个人目录／实际项目路径、邮箱、手机号，并运行 Gitleaks 默认规则及来源会话凭据规则。二进制 PKCS#8、PKCS#1、SEC1 私钥即使改名隐藏格式也会被拒绝；测试在内存中生成临时密钥，不提交密钥夹具。强制加入忽略文件也会被拦截。暂存检查将完整索引复制到一次性忽略目录，工作区修改不能掩盖索引中的原始字节。检查成功或拒绝后均删除快照，诊断仅显示规则和位置，不显示匹配值。

- `pre-commit` 执行 Git Flow／空白检查并扫描完整暂存快照；不限制 Git 作者与提交者邮箱类型。
- `commit-msg` 校验仓库规定的英文标题 Conventional Commits 格式，同时扫描提交说明中的隐私与秘密。
- `pre-push` 保留 Git Flow 检查，扫描新增提交的说明、变更快照和秘密差异，包括后来被删除的值；允许提交元数据中的个人邮箱。两项检查读取同一份 Git 推送更新流。
- CI 的 **Privacy and secrets** 检查当前文件、含秘密的历史和新提交隐私。Windows 质量检查在完整回归前安装同一个扫描器。文档 PR 也不能通过路径过滤跳过门禁。

历史秘密扫描覆盖所有已获取引用。新增隐私检查覆盖推送／PR 引入的提交；原私有仓库仍保留规范实施前的个人元数据和证据。新的公开快照必须具有一个独立根提交，不能携带原仓库引用或对象。不能把原私有历史推入该公开仓库。

## 例外与评审

不能通过跳过钩子、添加告警基线、使用 `gitleaks:allow`、忽略整个测试／文档目录或关闭秘密规则消除失败。封装检查会忽略行内抑制与 `.gitleaksignore`。`.gitleaks.toml` 扩展默认规则，仅保留经过审核且限定规则的例外：验收文件哈希映射、精确合成测试值、有公开来源记录的 SDK 常量及精确文档文字。新增例外须说明来源与范围，并增加回归，证明同一区域的真实凭据形态仍会被拒绝。敏感文件名及补充隐私规则不受 Gitleaks 例外影响。

扫描器、钩子、校验和、允许列表与 CI 的修改按安全相关变更评审。在实际公开仓库中，为 `main`／`develop` 配置必须经过 PR 审核、**Privacy and secrets**、**Git Flow policy**、**Repository checks (Windows x64)**，撤销过期批准、解决所有对话、禁止强推／删除和管理员绕过。仓库创建、套餐或可见性变更后核验实际强制效果；仓库里有工作流文件并不代表服务器保护已启用。

本地钩子可以被绕过，扫描器存在误报和盲区。审核者仍须检查抓包、图像和二进制产物，拒绝削弱门禁的修改。自动检查降低误提交概率，不能证明不存在任何隐私或恶意编码。

## 发现敏感数据时

停止相关发布或推送。在所属服务撤销或轮换真实凭据，清理工作区及受影响产物，并排查提交历史、PR 讨论、Actions 日志、Release 和外部副本。不能把原值复制到公开 Issue、审核、测试断言或诊断。删除提交、`.gitignore`、`.mailmap` 都不会清除原始历史数据。

需要防止旧个人元数据公开时，保留原仓库私有，另行准备脱敏导出。审查实际导出文件树，扫描新仓库完整历史，在接收贡献前配置保护。改写历史、强推已有长期分支不属于常规修复流程；遵守 [Git Flow](GitFlow团队规范.md)，涉及独立迁移时与相关维护者协调。
