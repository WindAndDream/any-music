# 开发工作流与代理指南

适用范围：共享 TypeScript/Vue 与仓库工作流。文件命名、SFC 和 composable 规则不套用于 Rust；端级数据获取分别遵守[篡改猴规范](../../用户脚本/开发规范.md)与[桌面规范](../../桌面端/开发规范.md)。

英文对应页：[Development Workflow](../../../en/cross-platform/architecture/development-workflow.md)。本页按任务保存命名、Vue 协作、构建与指南维护细节；始终生效的边界和验收入口在根 `AGENTS.md`。

## 命名与文件归属

- `src` 目录、普通 TypeScript 和样式文件使用 `kebab-case`；Vue SFC 使用有业务含义的多单词 `PascalCase.vue`，`App.vue` 是根组件例外。保留 `index.ts`、`main.ts`、`vite-env.d.ts`、配置文件与 Sass `_partial.scss` 的工具约定。
- 组件导入名、模板标签和文件名保持相同 PascalCase；import 大小写与磁盘一致。Windows 仅改大小写使用两次 `git mv` 经临时名。
- 变量、参数、字段、普通函数用 camelCase；类型、接口、类用 PascalCase；只有模块级不可变共享常量用 UPPER_SNAKE_CASE。缩写按普通单词写作 Api、Http、Url、Id、Html、Css、Ms；外部协议名和环境变量保留原样。
- 布尔值优先 is/has/can/should；loading、disabled 等已有控件语义的 props 可直接用。集合用复数，计数/索引/单位用 Count、Index、Ms、Bytes。
- 函数以动词表达结果或副作用；原生回调用 handleXxx，事件转发用 forwardXxx。沿用 Track、source/plugin、catalog 等既有模型词汇，公共重命名同步类型、导出、测试与文档。
- composable 文件 `use-xxx.ts` 与主导出 `useXxx` 对应；纯计算、解析和格式化保持普通函数。类型与所属模块共置，公共 API 经包入口或明确子路径导出。
- 测试位于所属包根 `test/`，镜像 `src/`，文件与被测模块同名并加 `.test.ts`；共享组件测试归 UI，运行端组合测试归应用。测试替身放本包测试目录，不为了共用夹具建立生产依赖。
- 来源 snake_case DTO 仅在 `plugin-source-*` 和端级桥接出现；进入 core、feature 和 UI 前映射为本项目 camelCase。SDK 线协议字段在可信适配边界保留其版本化 Schema 名称。

## Vue 协作与迁移

- SFC 顺序固定为 `<script setup lang="ts">`、`<template>`、可选 `<style scoped>`。共享 reset/tokens/Shadow 样式单独导出，局部样式 scoped；类使用 kebab-case 或一致 BEM，变量 `--am-*`。
- 显式类型化 props、emits、slots、defineModel。TypeScript 名称 camelCase；模板 props、事件和带参数 v-model 使用 kebab-case。props 只读，事件/model 请求修改，computed 只派生值。
- 根组件和功能容器只组合依赖。请求、持久化、定时器、订阅、媒体会话、有竞态/取消/重试的异步流程、跨视图状态，或需要脱离渲染测试的逻辑，迁入 feature/UI composable。编排三个以上独立功能状态源也应拆分；不以行数单独判定。
- 焦点、悬停、动画和实际尺寸等仅服务当前结构的展示状态可留 SFC；影响业务结果或跨视图延续时提取。运行端优先共享 headless 契约，不复制组件内部实现。
- 多依赖用 options；响应式输入接受 Ref/getter/MaybeRefOrGetter，在响应式上下文通过 toValue 读取。返回普通对象中的 refs/computed 和命名动作，内部受控状态默认 readonly，草稿或双向输入才可写。
- 在 setup 或活动作用域同步创建 composable；在 onScopeDispose 清理监听器、计时器、请求、Object URL、媒体和编码任务。取消或 generation/token 忽略旧结果，失败 Promise 立即清除。
- 重构先锁定 props、emits、文案、DOM 语义与操作结果，再补 composable 单元测试和组件黑盒回归。Node 渲染宿主仅验证可执行交互契约；真实焦点、布局与设备行为需要明确获准的运行态复测。

## 构建与依赖变更

- pnpm workspace、catalog 和递归脚本是当前构建基线，内部依赖 `workspace:*`。新增库前检查原生/CSS 替代、浏览器 ESM、维护、许可证、测试、tree-shaking 与实际产物增量。
- 新可部署应用命名 `@any-music/<app>`，提供 `build:dev`、`build:staging`、`build:prod`，应用 `build` 默认 prod。
- 单应用使用 `build:<app>` 构建生产版本，其他模式使用 `build:<app>:dev` 或 `build:<app>:staging`。根 `build`、`build:dev` 和 `build:staging` 分别递归构建拥有对应脚本的包。
- 不建立空的未来端目录或转发包。新包须有独立、稳定、被复用的职责；编排工具仅在实测 CI 瓶颈、affected graph/远程缓存或多团队任务边界需要时评估。
- Userscript 依赖默认打包。外置 `@require` 须锁版本，先测量体积并记录离线/缓存语义；不能用浮动 CDN。移动减包需要真实入口与产物检查。

## 公开前的隐私检查

遵守[隐私与密钥规范](隐私与密钥规范.md)和[贡献指南](../../../../CONTRIBUTING.md)。通过 `pnpm privacy:setup` 安装固定扫描器，提交身份使用 GitHub noreply 邮箱，完整检查前先执行 `pnpm check:privacy`、`pnpm check:privacy:history`。测试、证据、截图、日志和产物不能携带真实账号数据；持久证据使用 `<user-home>`／`<project-root>`。已有证据脱敏后保留原始测量日期和哈希，不构成新一轮验收。

## 验证结果

开发命令直接在终端输出，检查结果和退出码后，在任务交接中说明结论与剩余限制。除非用户明确要求，不创建本地命令／测试／构建日志、任务日志目录或逐次提交说明文件。此约定适用于共享代码、Userscript 和 Tauri 开发；已安装应用的诊断仍由各运行端负责。

需要在仓库长期保留的验证结论，按[文档生命周期](文档生命周期与代理约束.md)保存简短记录，注明命令、结果、运行端／构建范围及必要哈希或引用。已有且被引用的证据保留记录中的路径；移动或清理旧文件前检查引用并保留独有证据。已有本地日志和个人说明继续由 Git 忽略。

## 文档与语言约定

按需读取、事实归属、任务关闭后的保留／删除和可复用代理提示词见[文档生命周期与代理约束](文档生命周期与代理约束.md)。

按读者和用途选择语言，同一文件保持一致的主体语言。这是本仓库的维护约定，不表示英语天然更适合模型。

| 内容                                         | 主体语言           | 保留原文的内容                                                      |
| -------------------------------------------- | ------------------ | ------------------------------------------------------------------- |
| README.md、docs/zh-cn                        | 中文               | 包名、API、字段、路径、命令、标准与产品名称                         |
| README.en.md、docs/en                        | 英文               | 中文对应页标题、真实界面文案、搜索词和来源原文                      |
| 各级 AGENTS.md、仓库 SKILL.md 及技能参考材料 | 英文               | 代码标识符与需要准确匹配的界面/来源原文；项目文档优先链接英文对应页 |
| 对外 SDK、CLI、testkit 的 README 与协议说明  | 英文               | 公共出口、协议字段、命令和原始测试向量                              |
| 面向用户的说明与交付                         | 跟随用户使用的语言 | 用户指定的语言及产品原文                                            |

中文叙述优先使用“渲染端、命名空间、加载器、事务日志、数据来源标记”等中文术语；引用具体标识符时保留 `namespaces`、`permissionEpoch`、`InstallFiles`、`AppErrorState` 等准确拼写，并用行内代码区分。Profile、QuickJS、Tauri、GM、IPC、DTO 等专名和通用缩写可保留英文，首次出现且可能歧义时补充中文解释。

英文文档中的中文对应页名称、真实按钮文案和搜索词属于必要引用，保留原文，需要时附英文释义。翻译不重命名文件、导出、存储键或协议枚举，不改历史事实、授权条件或 `captureDate`。中英文版本同步维护事实和范围，不在一个正文中重复整段翻译。语言约定不改变与用户沟通时的语言。

## AGENTS.md 与 skills 维护

官方文档核对日期：**2026-10-01**。以下是基于官方指导选择的本仓库组织方式，不是 OpenAI 强制的模板、语言或行数限制。

- 根 `AGENTS.md` 写持久工作目标、目录定位、关键禁区和完成标准；包级文件写当地职责与差异。跨领域细节放维护中的文档，按任务链接阅读，不复制整份手册。
- Codex 在启动时按全局、仓库根到当前目录构建指南链；每层优先 override，再 AGENTS，再配置的回退，默认合计上限 32 KiB。从根工作不会自动加载所有后代指南，因此编辑目标包时主动读取其文件。不要用增加上限代替去重。
- 仓库 skills 留在 `.agents/skills/<name>/SKILL.md`；frontmatter 必含 name/description，描述应准确说明能力与触发时机。一个 skill 对应一个可识别工作流，条件细节进 references，脚本只用于必要的可靠计算或重复执行。
- SKILL.md 只加载当前任务需要的参考材料；尊重用户明确指令、已有授权和根验证规则。capture skill 不给普通代码修改自动添加实站查看权限；没有实测就不刷新 captureDate。
- `agents/openai.yaml` 是可选 UI/依赖元数据，不为满足形式创建空文件。共享技能、两端运行端技能及网页 capture 技能保持默认自动选择；触发描述必须区分 GM 与 IPC/Rust，运行端差异只加载对应技能。本次维护只调整仓库技能，不修改个人或已安装的通用 skills。
- 修改后检查 frontmatter、路径、当前模块归属和代表性触发/不触发请求；静态检查不能证明模型实际选择效果。明确区分静态验证和已执行的 agent eval。
- 重构批次完成后直接修改现行指南中的旧职责、依赖、存储与开放状态，同步中英文对应页和索引；不要用文末“取代上文”保留矛盾。实施步骤维护当前进度，专项交付矩阵维护实际能力，阶段记录保留当时证据与限制。

官方依据：[AGENTS.md 发现与分层](https://learn.chatgpt.com/docs/agent-configuration/agents-md)、[Codex 最佳实践](https://learn.chatgpt.com/guides/best-practices#make-guidance-reusable-with-agentsmd)、[Build skills](https://learn.chatgpt.com/docs/build-skills)。

## 验证与 Git 批次

任务分支、PR 流向、独立审核、merge commit 与发布 Tag 职责遵循 [Git Flow 团队规范](GitFlow团队规范.md)。提交前完成根检查，本地钩子不能替代它们。

按根指南完成五项检查，先检查 diff 再按职责提交；格式规则交给 formatter/lint，不把格式清单重复成 review 规则。需要跨包依赖的迁移保持在同一可构建批次，独立交互和指南分开。

`commitlint.config.js` 校验英文标题的 Conventional Commits 格式，例如 `docs: refresh agent guidance` 或 `fix(tauri): cancel stale media requests`；类型与示例见[提交与验证](GitFlow团队规范.md#提交与验证)。中文说明直接写在任务交接中；提交不再要求本地说明文件或 post-commit 日志钩子。

未明确请求运行态查看时，不启动产品、开发服务器、浏览器、模拟器或界面自动化。只有真实抓包完成才更新平台契约复测日期；未做实站或设备检查应在交付中列出。
