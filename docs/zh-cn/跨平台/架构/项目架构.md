# Any Music 项目架构

英文对应页：[Any Music Project Architecture](../../../en/cross-platform/architecture/project-architecture.md)。

适用范围：共享模块归属与两端对照。GM 细节只适用于 Userscript；IPC/Rust 细节只适用于 Tauri。端级开发先看[篡改猴规范](../../用户脚本/开发规范.md)或[桌面规范](../../桌面端/开发规范.md)。

当前正式运行端为 `apps/userscript` 与 `apps/tauri`。共享工作台、features、播放器、下载、资料库、stores 与仓库校验在 `packages/music-workbench`；端级 GM 与页面桥仍在 Userscript。Tauri 的当前实现与移动范围见 [Tauri 运行端](../../桌面端/运行端架构.md)。

## 数据归属

宿主与插件命名空间分别拥有数据，通过代次提交及当前版本可移植数据 API 保存。标签与创作会话由各自插件持有，工作台只装配具名端口和投影。两端在挂载前配置 `/storage` 适配，详见[数据归属](插件数据归属.md)。

## 呈现装配

当前依赖新增 `music-workbench -> plugin-ui-vue -> ui/plugin-sdk`；ui 保持不依赖插件框架。应用主题包根提供轻量主题元数据，`/trusted` 是可信 Vue 装配与主题事务，根入口是受限 DTO 的宿主渲染。播放器、下载器、资料库与旧导航偏好归属保持原位，详见[呈现边界](可复用包边界.md)。

正式应用向唯一共享工作台注入构建已知元数据、完整根组件、加载器及明确预加载的经典回退。经典与工作室各自拥有完整页面树；工作台将单一稳定控制器投影为 ui/theme 公共契约，不导入具体主题。音频、下载、来源会话、编辑及受保护原生／账号曲面独立于主题展示生命周期；ui/catalog、ui/library 保留中性交互，标签／创作插件保留会话和命名空间。

共享／SFC／所选主题样式作为惰性字符串资源，在稳定内部 Shadow 曲面中事务式激活；受保护插槽使用独立宿主 CSS。油猴保留外层 Shadow 挂载与轻量 document-start 启动器，Tauri 保留嵌入式／能力驱动组合。真实构建审计约束元数据隔离与可选工作室延迟执行。已移除局部加载器／分派和提取期映射，只分配一个 theme.root；页面／歌曲行样式归独立主题包。浏览器／设备验收仍属 T13。见 [主题开发](独立主题开发指南.md)。

## 1. 架构目标

Any Music 采用 pnpm monorepo，同时承载 Tampermonkey Userscript 与 Tauri 桌面端；移动原生适配在同一 Tauri 应用内继续演进。

架构主要解决以下问题：

- 共享 Vue 组件，但不让组件依赖 Tampermonkey 或 Tauri。
- 共享音乐领域模型和业务逻辑，但不让业务逻辑依赖 Vue、DOM 或平台 API。
- 小工具就近归属，仅在出现稳定、真实的复用需求时提取独立包。
- 将网络、存储、文件系统和 Shadow DOM 等平台能力隔离在各自应用中。
- 保持依赖单向，避免循环依赖和跨平台迁移。

## 2. 顶层结构

```text
any-music/
├─ apps/
│  ├─ userscript/          # 正式 Tampermonkey 应用
│  ├─ tauri/               # Tauri 桌面及后续移动原生适配
├─ packages/
│  ├─ account-pool/        # 独立多账号身份、策略与租约
│  ├─ network-routing/     # 纯请求竞争与代理健康调度
│  ├─ audio-composition/   # 独立时间线与可选浏览器编解码
│  ├─ plugin-center/       # 无框架插件身份与生命周期
│  ├─ plugin-sdk/          # DTO、线协议与生成 Schema 校验
│  ├─ plugin-ui-vue/       # 受限 DTO 渲染与可信主题装配
│  ├─ plugin-tag-management/ # 标签规则、状态与惰性专属视图
│  ├─ plugin-music-creation/ # 草稿、素材与惰性创作编辑器
│  ├─ plugin-vm/           # 固定无权限 QuickJS 内核
│  ├─ plugin-sandbox-browser/ # 可信 Worker 与有界执行会话
│  ├─ plugin-testkit/      # 仅 Node 的同 VM 作者测试工具
│  ├─ plugin-cli/          # 仅 Node 的作者 CLI 与封包工具
│  ├─ plugin-source-bilibili/ # B 站协议、元数据与贡献
│  ├─ plugin-source-douyin/   # 抖音协议、元数据与贡献
│  ├─ music-workbench/     # 共用产品组合、播放器与稳定存储校验
│  ├─ core/                # 音乐领域与平台能力接口
│  └─ ui/                  # 可跨端复用的 Vue 组件与样式
├─ crates/                 # protocol/policy/runtime/net/package 原生插件库
├─ .agents/skills/         # 仓库专属、高风险或易漂移工作流
├─ scripts/                # 包边界检查；test/ 保存隔离夹具回归
├─ docs/                   # 项目设计与架构文档
├─ AGENTS.md               # 面向 AI 的精简开发约束
├─ package.json            # 根命令和仓库级工具
├─ pnpm-workspace.yaml     # workspace 范围与依赖版本目录
└─ tsconfig.base.json      # 共享 TypeScript 规则
```

桌面与移动共享 `apps/tauri`。只在页面结构、导航或原生能力出现明显分叉后，再考虑拆成 `apps/desktop` 与 `apps/mobile`。

每个 workspace 包只设置一个包级 `test/`，内部镜像 `src/` 的职责层级。这样 `src/` 只承载生产代码，测试也不会被扁平堆放；测试夹具留在所属包的 `test/`。

## 3. 依赖方向

```text
apps/userscript ──┐
apps/tauri ───────┴───> packages/music-workbench ───> ui / core / plugin-center
       │               packages/core ─────> packages/audio-composition
       └──────────────> 各端平台适配器与账号调度


```

允许的内部依赖关系：

- `network-routing` 无内部依赖；`account-pool` 仅依赖 `network-routing`，运行端组合它们。接入状态见[桌面账号与代理](../../桌面端/运行端架构.md#账号与验证)。
- `core` 可以依赖 `audio-composition` 的纯算法入口。
- `audio-composition` 无内部依赖；来源包依赖 core/plugin-center，plugin-center 的音乐入口依赖 core。
- `ui` 可以依赖 `core` 和 `audio-composition` 纯契约入口，但不得依赖任何 `apps/*`。
- `music-workbench` 组合 ui/core/audio-composition/plugin-center，可信转换另消费 plugin-sdk；通过端口接收运行端能力，不依赖 GM、Tauri、Node 或应用。
- `apps/*` 可以组合所有共享包，并实现 `core` 定义的平台接口。
- 共享包之间禁止循环依赖。

包的入口、兼容适配和后续拆分标准见 [可复用包边界](可复用包边界.md)。

### 3.1 插件目标架构与迁移边界

插件框架负责生命周期、静态贡献、依赖／分配和可信主题。当前数据、功能、VM 及原生契约见[实施状态](插件系统重构实施步骤.md)，实际准入的目标和能力见[桌面交付](插件系统重构S15工具与桌面交付.md)。

下列边界描述当前分层与仍需独立验收的目标。完整设计包含尚未开放的扩展点、分发服务及手机能力，不能仅凭设计文档视为可用，见[插件扩展与安全契约](插件扩展与安全契约.md)。

- 宿主固定拥有发现、待听、喜欢、歌单、下载中/历史、播放历史、插件中心，以及播放器、权限、调度和持久化。标签管理和音乐创作迁为独立内置插件；来源各自作为内置来源插件，不能把所有业务继续堆进 MusicSourcePlugin。
- 插件由 Manifest、多类声明式贡献与按授权提供的服务组成。通用线协议、执行器端口、能力代理分层；应用注入实现，工作台不获取具体插件的内部状态，ui 不反向依赖插件。
- 桌面与手机共用包格式和安装事务；文件导入、文件关联、分享接收、链接与深链仅是不同获取入口，统一经过预览、兼容性校验和授权。平台适配器将文件/URI 转为私有暂存快照，声明式/代码类型与有效策略独立判断；后续市场复用安装器。
- Tauri 的安装实例、授权与预算以 Rust 为权威；前端只缓存展示，原生危险操作再次校验。共享 SDK 不暴露 GM、IPC、账号、CDP 或完整工作台对象。可信内置代码与恶意外置代码的信任模型明确分开。
- 核心规范数据和已发布配方由宿主拥有，插件持有自己的草稿、标签等命名空间。禁用创作不影响标准作品执行，但停用叶子来源仍中止相关媒体；缺失插件数据保留而不执行。
- 后续本地用户由宿主管理；独立账号提供方、云同步、分享与报告归可选插件／服务，一个本地用户可绑定多个提供方实例中的多个账号。Web 需求推动宿主业务／API 拆分，不把账号提供方业务移入核心。上述契约尚未实施，见[本地用户与服务规划](多用户与本地云端部署规划.md)。
- 先建立内置贡献和可恢复数据迁移，再实现无权限沙盒、联网授权与手机适配。新增包、SDK 发布和 Rust crate 抽取按实际可测试职责落地，不一次建立空包。现行包检查器和局部指南随实施阶段更新。

## 4. `apps/userscript`：Tampermonkey 应用

`apps/userscript` 是当前可运行、可构建的产品入口。它负责所有只在浏览器脚本环境中成立的代码。

```text
apps/userscript/
├─ public/
├─ src/
│  ├─ features/            # 内置来源的运行端组合
│  ├─ platform/            # DOM、GM HTTP/存储与页面桥接
│  ├─ styles/              # 注入 Shadow Root 的应用样式
│  ├─ App.vue
│  ├─ bootstrap-userscript-app.ts
│  ├─ main.ts
│  └─ vite-env.d.ts
├─ test/                   # 镜像 src 职责的正式应用测试
├─ index.html
├─ package.json
├─ tsconfig.app.json
├─ tsconfig.node.json
└─ vite.config.ts
```

### 4.1 `src/main.ts`

`document-start` 轻量入口，负责：

- 在宿主页脚本注册前安装必要的快捷键边界与抖音页面桥。
- 区分只执行回退捕获任务的标签页与正常可见入口。
- 在 HTTP(S) 顶层页面挂载不依赖 Vue 的原生启动器。

入口不得导入 Vue、Pinia、资料库、播放器或媒体编码模块。用户第一次展开时才动态加载 `bootstrap-userscript-app.ts`，由后者创建 Pinia、收集内联样式并把 `App.vue` 挂入 Shadow Root；加载失败保留可重试入口。

### 4.2 `src/App.vue`

Userscript 的根组合组件目前只组合 `MusicSourceWorkbench`。正式工作台已经连接音乐源、待听、播放、资料库、片段、下载、历史、插件与全局设置；功能状态仍由对应 feature composable 持有。

根组件应保持轻量。一个功能出现独立状态、明显 UI 区域或可复用逻辑时，应拆到功能组件或 composable，而不是持续堆入 `App.vue`。

### 4.3 `src/platform/dom`

承载只适用于 Userscript 页面注入场景的 DOM 能力。当前挂载模块负责：

- 创建唯一的 `<any-music-root>` 宿主元素。
- 将宿主挂载在 `document.documentElement` 下。
- 创建 Shadow Root、样式节点和 Vue 挂载点。
- 监听宿主是否被目标网站移除，并在需要时重新挂载。
- 提供完整卸载函数，清理 Vue 实例和 `MutationObserver`。

这些能力不能移动到 `ui`，因为 Tauri 页面不需要 Userscript 注入过程。

### 4.4 `src/platform/http`

承载 Tampermonkey 网络适配器。`gm-http-client.ts` 使用 `GM_xmlhttpRequest` 实现 `core` 中的 `HttpClient` 接口。

共享代码依赖 `HttpClient`，不直接调用 `GM_xmlhttpRequest`。Tauri 端通过 Rust command 实现独立账号 CookieStore 和代理；渲染层不持有完整凭证。

同样的原则也适用于存储、剪贴板、文件系统和系统通知：接口归 `core`，具体实现归相应 `apps/*/platform`。

### 4.5 `src/styles/host.scss`

只负责 Shadow Host 与宿主页面之间的样式隔离，例如：

- 重置宿主继承属性。
- 固定 `color-scheme` 和根字号。
- 为 Shadow Root 内元素设置统一盒模型。

共享组件样式不放在这里，而由 `packages/ui` 提供。

### 4.6 `vite.config.ts`

Userscript 独占的 Vite 配置，包含 `vite-plugin-monkey`、脚本匹配地址和 `GM_*` 权限。Vue 与运行时第三方依赖默认直接打入脚本，由 Tampermonkey 随脚本版本持久保存；进入新页面时不再请求 unpkg 等 CDN。其他应用不能复用或导入该配置。

本地 Vite 页面由 `index.html` 在正式入口之前加载 `src/platform/dev/install-dev-userscript-runtime.ts`，只提供布局、主题、焦点和无障碍回归所需的最小 `GM_*` 兼容能力。生产构建不会从正式入口导入该模块；跨域请求、Cookie、登录态、下载和宿主页兼容性仍须使用真实 Tampermonkey 产物验证。

目录是否抽离不由文件数量决定。一个平台即使只有一个构造文件，也不应单独建立 `features/<platform>`；反过来，签名、API、类型和 mapper 即使文件较多，只要读取平台私有契约，就必须留在 `packages/plugin-source-*/src`；应用平台目录只保留端级能力适配。内置源把 `MusicSourceDescriptor` 与实现分开：注册表可以立即展示名称、能力和 URL 范围，第一次检查会话、消费列表或解析媒体时才动态加载平台代码；加载失败后清除 Promise 缓存，允许用户重试。

Userscript 的元数据使用 `*://*/*` 与 `@noframes`，保证跨站请求和抖音页面回退任务具备授权。在所有正常 HTTP(S) 顶层页面提供原生启动器；`document-start` 桥与首次展开后的 Vue 功能树分开，展开前不读取资料库或触发远端会话。

正式音乐源工作区使用 Pinia 保存全局启用源、搜索/URL 草稿、代理/下载设置和抽屉请求配方。每个配方只包含插件 ID、请求类型、原始输入、自定义标题与展开状态；`Track`、已加载页数、分页迭代器与短时媒体不进入 Store。刷新后抽屉保持收起，用户展开时才恢复第一页，后续页仍由一次“下一页”动作消费一次迭代。

每个正式运行端只创建一个下载管理器。`core/download` 提供并发、重试与取消调度，`music-workbench/src/features/downloads` 负责媒体生成和 MP3/ZIP，`music-workbench/src/storage` 保存元数据历史并通过运行端存储端口写入。Userscript 只在 platform/http 转换 GM proxy，秘密留在脚本专属配置；桌面的账号与代理由 Rust 绑定，保存文件通过原生命令。

B 站与抖音纵切片的公共插件契约、惰性分页与短时媒体约束见 [音乐源插件架构](音乐源插件架构.md)；功能阶段和完成标准见 [功能需求与路线图](../产品规划/功能需求与路线图.md)；实际抓包字段见 [哔哩哔哩 Web 接口契约](../平台接口/哔哩哔哩/网页接口契约.md) 和 [抖音 Web 接口契约](../平台接口/抖音/网页接口契约.md)。

## 5. `packages/core`：领域与平台接口

`core` 表达“Any Music 是什么以及它能做什么”，但不负责“当前平台怎样完成它”。该包只使用 TypeScript，不依赖 Vue、DOM、Tampermonkey 或 Tauri。

```text
packages/core/src/
├─ errors/                 # 统一语义错误、稳定 AM 状态码与可序列化快照
├─ download/               # 平台无关的并发、重试与取消调度
├─ library/                # 本地资料库模型、标签与片段配方
├─ models/
│  └─ track.ts
├─ music-source/           # 插件契约、清单校验、分页与媒体策略
├─ player/
│  ├─ normalize-progress.ts
│  └─ playback-mode.ts
├─ ports/
│  └─ http-client.ts
└─ index.ts
```

### 5.1 `models`

存放音乐领域模型，例如歌曲、歌手、专辑、歌词、播放队列和来源平台。类型应和所属领域放在一起，不要建立一个无归属的全局 `types` 目录。

### 5.2 领域模块

按业务能力组织纯逻辑。`music-source/policies.ts` 统一页大小归一化与媒体加载策略，使平台只声明默认值、上限和阈值；`library` 管理可持久化资料与虚拟片段；`player` 管理播放领域规则；`download` 在不依赖 `AbortSignal`、计时器或 Blob 的前提下调度固定 worker；`errors` 是所有可预期操作型错误及 `AM-*` 状态码的唯一目录。

如果函数理解歌曲、歌词、歌手、播放队列等音乐概念，即使它是纯函数，也应放在 `core`。

### 5.3 `ports`

定义业务需要的平台能力接口，例如：

- `HttpClient`
- `KeyValueStorage`
- `AudioOutput`
- `FileSystem`
- `NotificationService`

接口由 `core` 定义，由 `apps/userscript` 与 `apps/tauri` 实现。这可以避免业务代码直接绑定 `GM_*` 或 Tauri API。

### 5.4 `index.ts`

共享包的公共出口。其他包优先从 `@any-music/core` 导入，不应随意引用 `core/src` 内部路径。只有准备长期维护的 API 才从这里导出。

## 6. `packages/ui`：共享 Vue 组件

`ui` 提供可用于 Userscript、Tauri 桌面端和后续移动端的 Vue 组件、UI composables 与设计样式。跨端视觉和交互契约见 [跨端界面与交互规范](../功能设计/跨端界面与交互规范.md)。

```text
packages/ui/src/
├─ components/
│  ├─ AppIcon.vue
│  ├─ NavigationRail.vue
│  ├─ MobileBottomNavigation.vue
│  ├─ MusicAppShell.vue
│  ├─ BottomSheet.vue
│  └─ PanelShell.vue
├─ styles/
│  └─ index.scss
└─ index.ts
```

### 6.1 `components`

组件使用 Vue 3 Composition API、`<script setup lang="ts">` 和显式的 props/emits/slots 契约。组件通过 props 接收数据、通过事件表达交互，不直接读取 `GM_*` 或 Tauri 状态。

共享基础件与受控产品面板由 `packages/ui` 维护，包括导航、壳层、资料库、列表、筛选、设置与插件表单；`PanelShell` 保留最小兼容契约。`music-workbench` 维护产品组合、播放器和仓库校验；应用保留运行端薄适配、账号组合及 Shadow DOM/原生挂载。测试随职责放在对应包的 `test/`。

新增多个同类组件时，优先按功能建立目录，例如 `components/player`、`components/lyrics`，避免所有文件长期堆在同一级。

### 6.2 `styles`

共享样式通过 `@any-music/ui/styles` 单独导出：

- Userscript 使用 Vite 的 `?inline` 将其作为字符串注入 Shadow Root。
- Tauri 应用可以直接作为普通样式导入。
- 自定义属性统一使用 `--am-*` 前缀，并在 `.am-root` 上提供默认值。
- 共享尺寸优先使用 `px` 或受控的局部 `em`，避免依赖第三方页面的根 `rem`。

组件样式通常可以和 SFC 放在一起；但需要注入同一 Shadow Root 的公共样式必须进入统一样式出口，否则 Vite 默认注入到页面头部的样式无法穿透 Shadow DOM。

### 6.3 Vue 依赖

`ui` 将 Vue 声明为 peer dependency，由每个应用提供运行时版本，避免组件包捆绑第二份 Vue。Userscript 应用提供这一版本并在最终构建中打包一次；“peer dependency”只解决 workspace 依赖归属，不代表必须通过远程 `@require` 加载。

## 7. 局部工具与包提取

小工具应留在所属模块。播放进度归一化及其数值边界计算归 `core/src/player/normalize-progress.ts`，无需单独的通用工具包。

音乐语义归 `core`，Vue/DOM 行为归 `ui`，GM/Tauri 逻辑归对应应用的 `platform`。只有多个独立消费者证明了稳定职责和清晰依赖边界，才提取新的共享包；不为未来可能出现的工具预留空包。

每个 workspace 包根目录都包含局部 `AGENTS.md`。AI 或开发者进入具体包时，应同时遵循根约束和距离当前文件最近的包级约束；局部文件用于补充该包职责，不重复完整架构文档。

## 8. 代码放置判断

新增代码时按以下顺序判断：

1. 是否调用 `GM_*`、Tauri 或特定运行端 API？放入对应的 `apps/*/platform`。
2. 是否依赖 Vue、DOM 或视觉交互？放入 `ui`；只服务一个运行端时留在对应 `apps/*`。
3. 是否理解歌曲、歌词、播放或搜索等音乐概念？放入 `core`。
4. 是否只有一个调用者且很短？留在调用者附近。
5. 是否有独立消费者共享稳定职责？优先复用已有职责包，或在需求得到验证后评估提取。

## 9. 包导出与构建策略

现有业务共享包均为私有的 source-first workspace package；plugin-sdk 另提供可本地打包、离仓消费的 ESM/声明产物，尚未发布 npm（见[契约记录](插件扩展与安全契约.md)）：

- `package.json` 的 `exports` 直接指向 `src`。
- Vite 在构建应用时处理共享 TypeScript、Vue SFC 和 Sass。
- 各包通过独立 `typecheck` 脚本校验自己的完整源码。
- 内部依赖必须使用 `workspace:*`。

当未来需要发布 npm 包、被非 Vite 工程消费或构建速度明显受影响时，再为共享包增加独立产物和声明文件构建。除已具备外部协议消费职责的 plugin-sdk 外，当前业务包不引入额外打包层。

### 9.1 Userscript 依赖缓存

Userscript 的“强缓存”以脚本管理器持久化安装产物为边界：

- Vue、`js-md5` 等运行时依赖随 `.user.js` 打包，页面刷新、跨站跳转和 SPA 路由不会再次下载依赖；
- 依赖版本由 `pnpm-lock.yaml` 与 catalog 固定，升级随脚本版本一起验证和发布；
- 禁止 `vue@3` 这类浮动 CDN `@require`，因为其内容可在项目未发布时变化，离线时也不可用；
- 只有测量证明某个依赖显著拖慢安装/更新，并明确接受 CDN 可用性与供应链风险后，才允许用精确版本 URL 外置。

正式脚本和测试脚本都把各自使用的 Vue、Pinia、Mediabunny、MP3 编码器、ZIP 与平台适配器打入可安装产物；动态模块延迟执行，但当前不能仅凭动态 import 假设移动端已经减包。未来移动应用需要独立入口、可 tree-shake 出口和产物分析，确保桌面专属导航、操作器与重型编辑器不进入移动依赖图。每次新增明显依赖后以实际构建产物重新记录体积，不能把未锁定编码器改为远程 `@require`。

### 9.2 第三方库准入

引入库前依次检查：是否能由清晰的浏览器/CSS API完成；是否支持浏览器 ESM 和 tree-shaking；维护、许可证与测试是否可信；是否引入 Node polyfill；gzip 增量是否与收益匹配。当前工作台仅用 GSAP 做一次水平位移，已改为 CSS `transform`/`transition` 并移除 GSAP；WBI 的 MD5 继续使用小型 `js-md5`，抖音 SM3/RC4 因与 `a_bogus` 契约强耦合且已有固定向量测试，暂不为了“统一依赖”替换。

## 10. 常用命令

在仓库根目录运行：

```bash
pnpm install           # 安装所有 workspace 依赖
pnpm dev               # 启动正式 Userscript 的 dev 环境
pnpm dev:staging       # 启动正式 Userscript 的 staging 环境
pnpm dev:prod          # 启动正式 Userscript 的 prod 环境
pnpm dev:userscript    # 同上，显式启动正式 Userscript 的 dev 环境
pnpm dev:userscript:staging # 启动正式 Userscript 的 staging 环境
pnpm dev:userscript:prod  # 启动正式 Userscript 的 prod 环境
pnpm typecheck         # 检查所有应用和共享包
pnpm test              # 运行领域算法与清单校验测试
pnpm lint              # 运行 oxlint
pnpm format            # 使用 oxfmt 格式化
pnpm format:check      # 只检查格式
pnpm build             # 类型检查后构建所有可构建应用
```

针对单个包可以使用 pnpm filter：

```bash
pnpm --filter @any-music/userscript build
pnpm --filter @any-music/ui typecheck
pnpm --filter @any-music/core typecheck
```

## 11. 运行端扩展

Tauri 已存在于 apps/tauri；修改现有桌面能力先读[桌面开发规范](../../桌面端/开发规范.md)与原生局部指南。平台端口在应用实现，共享工作台/UI 不直接导入 GM 或 Tauri。新增其他运行端时复用公共契约，在该应用实现传输、存储、媒体与原生权限；只有出现稳定复用职责才增加 package。

当前 3 个应用、9 个共享包由 pnpm workspace、catalog、`workspace:*` 和递归脚本完整覆盖，并通过 `disallowWorkspaceCycles: true` 在安装阶段拒绝循环依赖；目前不引入 Nx/Turborepo。满足以下任一可测条件后再做 PoC：

- CI 的全量测试/构建稳定超过约 5 分钟，且多数提交只影响少量包；
- 需要可靠的 affected graph、跨机器远程缓存或分布式任务；
- 应用/包增长到十余个并由多个团队独立维护，任务依赖关系难以靠现有脚本表达。

PoC 必须比较冷/热构建时间、缓存命中率、CI 配置复杂度和供应商耦合；没有数据收益时继续使用 pnpm，不把任务编排器误称为“多仓库管理”。若未来真正拆成多个 Git 仓库，再单独评估版本发布、契约兼容和跨仓依赖，不由当前 monorepo 工具替代。

## 12. 项目技能

仓库技能只记录需要反复执行且容易出错的工作流，不重复普通 TypeScript/Vue 常识：

- `$any-music-userscript-runtime`：篡改猴 GM 请求、Cookie/页面桥、存储和权限；
- `$any-music-tauri-runtime`：桌面 IPC、Rust 请求、账号/媒体与原生能力；
- `$music-source-adapter`：所有平台共用的适配器边界、惰性分页、状态机与按需媒体解析；
- `$bilibili-contract-capture`：在专用测试浏览器中脱敏复抓 B 站契约；
- `$douyin-contract-capture`：在专用测试浏览器中脱敏复抓抖音契约；遇到 2483、验证页或 CAPTCHA 时暂停自动捕获，等待用户手动处理；
- `$any-music-ui-delivery`：实现或评审正式产品 UI 时校准跨端语义、Shadow DOM 样式、响应式、动效、可访问性和真实打包边界；
- 不为每个只有普通 REST 映射的平台创建技能；只有签名、风控、浏览器状态或脱敏流程形成稳定且非显然的独立边界时才新增。

Skills 提供任务工作流，`AGENTS.md` 保留持久约束；详细命名、Vue 拆分、构建模式和官方指南维护方式见[开发工作流](开发工作流.md)。平台接口变化时同步文档、raw type、parser 和 mapper；只有明确要求实站复测且实际执行时才刷新 captureDate。
