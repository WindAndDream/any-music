# Resource Cache

Chinese counterpart: [资源缓存](../../../zh-cn/跨平台/功能/资源缓存.md).

Settings → Resource Cache manages disposable artwork, covers and media bytes independently of the library, product generations, credentials and downloaded files. The default limit is **1 GiB**, the minimum **128 MiB**, and the maximum **100 GiB**. Limits are ceilings, not reservations; entry-count limits and script-manager quotas can reduce actual occupancy. Both the form and owning runtime validate integer limits. Shrinking below current occupancy requires confirmation and immediately evicts old entries. Usage is refreshed on entry and by an explicit refresh action.

User-uploaded playlist artwork uses a separate bounded local store: asynchronous GM values at `any-music:userscript:playlist-covers:v1` or a separate WebView IndexedDB database named `any-music:tauri:playlist-covers:v1`. The shared workbench receives only an injected cover port. Each upload becomes a JPEG with its original aspect ratio and a longest edge up to 1024px, without enlarging smaller originals. Encoding tries at most three quality levels (0.9, 0.8, 0.7) within 512 KiB of ASCII data per cover, with an 8 MiB aggregate encoded-data budget. Full storage rejects another upload without evicting existing covers. Replacement/deletion releases unreferenced artwork; startup reclaims abandoned drafts. Only a stable `coverId` enters product generations and portable backups. Image bytes remain local and are independent of the network resource cache and its Clear action; a missing asset uses the default playlist icon.

| Runtime    | Storage and directory                                                                                                                                                              | Cache coverage                                                                                                     |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Desktop    | Separate native `resources-v1.sqlite3` in the OS application-cache directory; a native folder picker can select a dedicated `AnyMusicCache` child directory or restore the default | Account-authorized native streaming, Range/MSE, export reads, and supported built-in public CDN artwork            |
| Android    | The same native store in the application's private OS cache directory; the OS may reclaim it                                                                                       | Existing native Bilibili media and built-in CDN artwork; no new account/source/plugin authority                    |
| Userscript | Asynchronous GM storage under `any-music:userscript:resource-cache:v1:*`, shared across host pages and separate from product generations                                           | Lazy GM artwork and eligible GM binary responses up to 4 MiB each; browser-direct playback remains browser-managed |
| iOS        | Local cache preferences/clearing only                                                                                                                                              | Existing native media unavailability remains; no new media transport                                               |

Mobile cannot use an arbitrary SAF document folder as a random-access SQLite directory. Userscript has no arbitrary filesystem-directory authority. Their settings display the runtime-managed location. Desktop directory changes first validate/open the destination under a process lock, confirm clearing the old cache, and persist the new native preference. Cancellation preserves the old location. Clearing/resetting only touches the dedicated owned database, never a user-selected parent folder or downloaded songs.

## Native data and algorithms

- The native store uses indexed `(key, offset)` lookup and an indexed approximate LRU, with access timestamps coalesced per minute. Keys hash account/track/actual-quality identity for media and complete public URLs for images. URLs, headers containing credentials, cookies, grants and renderer Blob URLs are never persisted. Cached bytes are not an offline entitlement: fresh source resolution and current account/grant checks still precede playback.
- Audio is teed from the existing consumer-driven stream into at most **1 MiB** chunks. Up to four best-effort background writes avoid blocking playback on disk; when that budget is exhausted the cache may skip a chunk. There is no extra full-song request, decoding, network prefetch or complete-file accumulation. Dropping playback stops the network stream and schedules a best-effort write of the already received partial chunk. Only valid successful unencoded media responses with bounded MIME metadata are admitted; `no-store` responses are excluded.
- Cached fragments are read on demand, including when they cover only a prefix of the requested range. The first gap resumes one continuous native account-client Range stream, which is also eligible for caching; a short probe does not create one network request per missing chunk. Account cancellation stops delivery. If the continuation changes its representation or ignores Range, the stream fails through the existing playback recovery path.
- One native blocking job owns the SQLite connection. Hot-path requests bypass a busy/unavailable cache, with a 100 ms wait ceiling for disk work; settings operations serialize. The blocking task retains its semaphore permit if its caller is dropped or its wait expires. No standard mutex crosses `await` and no network operation runs under a database lock.
- Entries expire for reuse after seven days. Capacity/32,768-entry ceilings bound storage and index growth. Usage includes a per-entry metadata allowance; actual SQLite/OS overhead and bounded rollback scratch space are additional. FULL auto-vacuum releases evicted pages. Bulk eviction uses at most 32 chunks per transaction. Clearing closes and removes the one owned database under its retained process lock and recreates an empty one, avoiding a second copy of the old cache. Foreign databases are rejected by application ID.
- Artwork uses session-signed loopback URLs restricted to build-known HTTPS CDN domains. Native requests contain no cookies/account credentials and follow no redirects. Four active reads, 32 admitted requests, an 8 MiB body ceiling and one deadline bound memory/network work. Up to two best-effort background writes avoid delaying the image response for disk work. Concurrent identical artwork shares a native flight lock. Unsupported artwork falls back to the existing no-referrer image path. The image remains hidden until load succeeds, and source URL changes/unmount release image work and Blob leases in the shared boundary.

## Memory cache and settings

Settings separates disk capacity, memory capacity and cache location into independent cards. Cache Introduction sits at the right of the page title, vertically centered; it opens detailed behavior and runtime limits. Disk usage refresh is an icon button at the top right of the disk card, with an accessible name and tooltip. Clear and Save Limit share the disk card's footer; both capacity cards use the concise visible label `保存上限` (Save Limit) with distinct accessible names. Themes arrange the header and content through the cache slot's `placement`, while the host owns the help dialog and cache actions. The memory limit defaults to **64 MiB**, accepts **0–1024 MiB**, and is saved independently of the disk draft; zero disables it. Limits are ceilings rather than reservations. Shrinking immediately evicts least-recently-used entries; Clear removes both tiers. Only the capacity preference persists, never memory bytes or session addresses.

Native caching retains the existing hashed resource/account/quality identity, range checks and expiry. Separate bounded tree indexes locate resource offsets and promote/evict LRU entries in O(log n), with at most 4,096 pieces. Memory hits avoid the disk worker; overlapping fragments can miss to the existing indexed disk query. GM caching uses an insertion-ordered Map for expected O(1) lookup/promotion, at most 1,024 responses and the existing 4 MiB per-response limit. Memory fills only from successful eligible disk writes/reads; failed disk writes remain retryable. Both tiers count body bytes and a per-entry metadata allowance, return consumer-owned buffers and reject stale writes after clearing or changing memory limits. No extra network prefetch or full-song accumulation is introduced.

These limits cover the owned reusable byte cache, not total process memory. Browser/system playback buffers, decoded artwork, active consumers and bounded IO buffers remain independently managed. Userscript direct-browser playback retains its existing browser-managed cache.

## Userscript limits and cleanup

Userscript additionally enforces a **32 MiB** occupancy ceiling, including Base64 and per-entry metadata allowances, even when the configured preference is larger. Tampermonkey includes GM values in its startup message; the cache must leave headroom below Chrome's 64 MiB message ceiling for the script, product generations and manager metadata. LRU eviction runs before each cache write and when opening a stored cache. The settings describe this runtime limit. This is separate from the configurable product preference and does not change native cache limits.

GM-R2 reproduced a 69,030,799-byte manager record that prevented injection before application cleanup could run. Recovery in the dedicated test profile removed only `any-music:userscript:resource-cache:v1:*` values, verified the product-generation fingerprint unchanged, and reloaded the manager. Already oversized test storage needs manager-side cache cleanup; a failed injection cannot repair itself. Do not reset the library or credentials to clear disposable cache bytes.

The GM adapter hashes complete binary request identity, retains only safe response headers, bounds each response and at most four pending writes, and maintains an insertion-ordered Map for constant-time LRU promotion. At most 1,024 records are retained; metadata checkpoints are coalesced. Startup reclaims orphaned/expired cache values once. Base64 and metadata overhead count toward usage; actual manager quota can be lower. API text, failed/incomplete Range responses and `no-store` data are excluded. Cache write failure does not fail a successful network response. Failed/corrupt cache reads fall back to GM transport. No host `fetch`, page IndexedDB or WebView credential storage is introduced.

Artwork retains lazy intersection admission, four active GM reads, a bounded cancellable waiting queue, and disposable Blob URLs. Native browser playback cannot be intercepted by a userscript cache without changing its transport/startup contract, so it continues to use browser caching; the settings explain this boundary. Product storage runs cache shutdown/draining before releasing its manager-owned writer registration, including page exit.

All destructive cache actions use the existing confirmation controller. The shared controller rejects duplicate operations and confirmations from closed/disposed settings sessions. Native and GM epochs reject writes from requests started before clearing/configuration changes. New user activity can populate fresh cache afterward. Library data, favorites, histories, plugin namespaces, credentials and exported downloads remain independent.

## Verification scope

Native content/persistence and cached-stream fixtures inject a test-only 30-second disk wait budget, so their hit/byte assertions do not depend on host filesystem speed. Production retains the 100 ms ceiling. A separate test uses that default budget and an explicitly blocked worker to verify read/coverage misses, bounded write waiting, permit retention after timeout, skipped busy requests and eventual completion of only the admitted write.

Deterministic tests cover minimum validation, persistence/restart, indexed eviction, short-probe replacement, expiry, busy/error retry, late writes after clearing, path isolation, cached Range coverage and continuous resumption after clearing. Shared tests cover confirmation cancellation, duplicate actions, settings/session invalidation, draft preservation and error recovery. GM tests cover manager namespace/privacy, restart hits, cancellation, invalid responses and storage failures. These tests and Android cross-compilation do not establish installed-script behavior, real WebView layout, native folder-picker interaction or physical-device playback acceptance. No live capture date changes with cache work.
