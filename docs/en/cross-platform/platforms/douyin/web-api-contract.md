#### Risk-gate isolation recapture (same day, still 2026-10-03)

Paired requests from the same page, same cookies and same second separated the rejection cause. Only methods, ratios and conclusions are recorded; no cookie, token or signature value is kept.

| Pair                                                                             | Result    |
| -------------------------------------------------------------------------------- | --------- |
| The page's own `fetch` (already wrapped by Web SecSDK)                           | code 0    |
| A pristine same-origin realm's native `fetch` (not wrapped, otherwise identical) | code 4031 |

Both used the identical TLS session, HTTP/2 connection, user agent and cookies, so **the rejection is decided in JavaScript, not by a transport fingerprint**. Peeling fields one at a time showed that `msToken`, `x-tt-session-dtrait` and the `p_ui/p_ca/p_js_*/p_ts/p_no` metadata are each individually unnecessary: **`a_bogus` is the deciding factor**. A native Node client that sends the `a_bogus` Web SecSDK itself produced — without `x-tt-session-dtrait` and without any special `msToken` handling — is accepted; dropping that one parameter returns 4031.

About `a_bogus` itself, this run established only these reproducible facts, judged solely by whether the server accepts:

1. A complete parameter surface is a separate precondition. A sparse query carrying a genuinely signed `a_bogus` is still rejected with 4031, so "valid signature" and "normal SDK parameter surface" are two independent conditions.
2. The server does not verify the whole payload. Rewriting decoded byte 30, 70 or the final byte is still accepted; the checked surface sits within the first four decoded bytes, that is roughly the first six characters of the string, and even there some positions are tolerated (index 4 may change, index 5 is fatal), so it is not a plain prefix comparison.
3. That checked region does not depend on the query string or the clock; it varies only with the client's random material, which makes it look like a client-attestation field rather than a request digest.
4. Stubbing `Math.random`, resetting the seed before every signature and pinning `Date.now` makes one input yield a byte-identical payload (Web SecSDK draws about 59 random values per signature). That rig is the prerequisite for the byte-level and character-level results above and the bench for locating the bit field.

Points 2 and 3 state which region the server reads; they do **not** give the bit rule that region must satisfy, and the repository's local `a_bogus` implementation was rejected under all nine input conventions and three fingerprints tried. Native QR checking therefore remains unverified against the live site. No product code was changed on the strength of this run; blocked sessions still stop polling and keep the system Chrome/Edge verification entry point.

The parser first attempts standard chunked reassembly; otherwise it parses frames independently, ignores acknowledgments, combines all `data[]`, and preserves any business-error frame for the state machine. Metadata is merged in frame order: omitted `has_more` or `cursor` fields retain earlier values, while an explicit `has_more=0` still overrides them. Keeping only the last frame's metadata misreads omission as normal completion and silently removes the next-page action. Protocol and Tauri IPC composition tests verify this fix using synthetic missing-metadata regression fixtures.

## 2. Request State and Protected-Page Fallback

Request fields are rebuilt from the current browser, window, screen, Network Information API, media capabilities, and available same-site cookies. A `DouyinApi` instance keeps generated fallback `verifyFp` and 19-digit `webid` stable only for its lifetime while rereading changing environment values for each request.

On non-Douyin hosts, `GM_cookie` projects only the target-domain `UIFID`/`UIFID_TEMP` and `s_v_web_id` fields required by the current request. Those values never enter GM value storage, logs, DOM, or documentation.

Self likes, favorite videos, and current recommendations always try a complete GM request first. Any unusable HTTP response, non-JSON rejection, non-zero business code, missing list, or malformed payload opens the matching self page in a background tab. The task uses a random ID and a URL fragment; same-tab login/verification redirects may preserve it in that tab's `sessionStorage` for at most five minutes.

The page bridge captures only the requested cursor and projects stable track-mapping fields before publishing a one-shot GM value. It strips media URLs, download addresses, bitrate data, request security fields, and response extras. A successful capture closes the background tab. Manual login or verification pauses capture; timeout, user close, or unresolved verification leaves the page available and never automates evasion. Every later cursor retries GM before opening another fallback.

## 4. Media Resolution

Ordinary videos prefer the highest-bitrate independent audio, then full video playback addresses, then bitrate variants, and only finally background music. Full playback addresses must take precedence over ambiguous high-bitrate video representations so a DASH video-only stream is not accepted by `<audio>` as silent playback. Photo posts use their music. Favorite music is re-read through `music/detail` before playback. Each attempt resolves fresh URLs and keeps them only in the active session.

The 2026-09-03 capture confirmed that `video.bit_rate_audio_list` may be empty. When present, `bit_rate/bitRate`, `quality_type/qualityType`, `gear_name/gearName`, and each entry's own `play_addr/playAddr` define independent audio tiers. Otherwise `video.bit_rate/bitRate` supplies full-work candidates ordered by explicit bitrate, with resolution/profile text derived from `gear_name`. URLs whose paths explicitly identify `media-video-avc1` or `media-video-hvc1` DASH video-only tracks are not exposed as audio choices. Multiple URLs in one `play_addr.url_list` are CDN mirrors for the same tier, not separate qualities; a response with only a complete playback address and no `bit_rate_audio_list` therefore exposes one playable quality. URL `br`, MIME, and extension hints are used only when structured quality fields are absent. Initial playback chooses the highest validated rank, while a switch must match the complete quality ID in the newly fetched detail response rather than relying on array position or an old ephemeral URL.

If work detail is absent for a non-authentication reason, the adapter can parse React Flight data from the Douyin video/note page and `_ROUTER_DATA` from the IES share page. A matching React Flight card is accepted only when it contains resolvable media; metadata-only matches do not stop the share-page fallback. Authentication and access errors are not swallowed by these fallbacks.

The 2026-09-04 capture also confirmed that work detail uses the quick-player business fields (`request_source=600`, `origin_type=quick_player`), the 17.4 webcast SDK version fields, and the Web SecSDK timestamp/query-signature envelope. Cross-site Douyin VOD behavior is not uniform: some URLs stream natively with `no-referrer`, while others are rejected during metadata loading. Referer-only sources therefore try native URLs first, then use GM HTTP with the Douyin Referer after an error. If a Range request is redirected into an oversized complete body, the GM adapter aborts at the headers and the reader retries the request against the ephemeral `finalUrl`; that URL stays inside the current session.

Userscript metadata explicitly grants the VOD root domain as `@connect douyinvod.com`; Tampermonkey includes its subdomains. Official work descriptors may first use `aweme.snssdk.com/aweme/v1/playwm/`, so that exact media-entry host also needs `@connect`. [GM-R3](../../../../baselines/theme-ui-migration/T13-gm-r3.json) records the missing-permission failure and repaired real-GM 302→CDN 206→Range/MSE playback. `*.douyinvod.com` is not the accepted domain form. Production fixes `externalPlugins: none` and grants exact built-in domains, without an `@connect *` fallback. This runtime evidence does not change the website contract capture date.

Backup CDN attempts are hedged at 250 ms intervals through the first encoded audio packet, and both initial Range probing and total MSE first-fragment startup have a five-second budget. Captured MP4 audio used negative AAC preroll timestamps down to about `-0.16s`; packets are shifted onto a zero-based muxing timeline without re-encoding. MSE backpressure retains roughly 30 seconds ahead of the playhead and 15 seconds behind it, pausing background reads and evicting consumed ranges instead of exhausting SourceBuffer on long media. Seeking outside that window aborts the old read and rebuilds MSE from the packet at the requested timestamp, so a backward jump into an evicted interval cannot wait forever; a paused seek stays paused, a playing seek resumes after the first new fragment, and repeated dragging retains only the latest rebuild. An explicitly rejected MSE codec may use a session-scoped audio-only Object URL; an unavailable Range input or startup timeout skips duplicate extraction and proceeds to complete-media fallback. Switching tracks aborts in-flight reads and releases buffers and Object URLs; bytes and ephemeral URLs are never persisted.

## 5. Pagination and Errors

Search requires an explicit `data` array. HTTP 200, business code zero, or metadata/ack-only stream frames do not establish empty results. Missing or non-array lists report `invalid-response`; an explicit empty array with `has_more=0/false` and an absent or zero `result_status` ends pagination, including after useful earlier pages. An empty array promising more, missing a termination flag or carrying an abnormal result status reports `invalid-response` on the first page and `pagination-unavailable` on later pages. `verify_check` retains priority as a verification requirement. Desktop additionally inspects the still-owned official page on every empty response, including the first page: a visible challenge or login panel is reconciled before closing the target, without replaying the search. An abnormal empty response also cannot confirm completion of security verification. Synthetic-response and desktop IPC tests verify these rules; `captureDate` is unchanged.

Search uses offset/count; works, likes, recommendations, and favorites use cursors. Mix and folder directories expand one entry at a time. Iterators stop on `has_more=false`, an empty raw list, or an unchanged cursor. Non-search listings also stop when no items map to tracks; search keeps its next-page action when a page contains only filtered non-work cards.

After a useful first page advertised more results, an ambiguous empty follow-up or unclassified source failure becomes `pagination-unavailable` (`AM-3006`) and preserves loaded items. An explicit successful end is handled as described above. This error alone does not prove that a human verification challenge appeared. Recognized network failures, timeouts, rate limits, authentication failures, access denial, and risk code 2483 retain their own codes. A response whose `search_nil_info.search_nil_type` is `verify_check`, or a desktop page inspection confirming a visible challenge, is classified as `verification-required` (`AM-3005`). Pagination notices and error details ask users to view or favorite loaded songs and retry later, without suggesting unconfirmed verification. Retry reloads from the first page; later-page recovery depends on the source.

The 2026-09-26 test-profile capture confirmed an HTTP 200 search-stream response with `status_code=0`, empty `data`, `has_more=0`, `result_status=5`, and `search_nil_info.search_nil_type=verify_check` while the search page showed a slide challenge (`verify_data.type=verify`, `subtype=slide`, `code=10000`). This is a verification response even without business code 2483. `result_status=5` or an empty page alone does not establish verification; other unclassified later-page failures remain `AM-3006`. After the user manually completed the challenge, only sanitized search classification fields were read. No request signature, cookie, fingerprint, media URL, or full response was saved.

## 6. Signing and Transport

`a_bogus` covers the exact unsigned query and real HTTP method. On a Douyin host, the document-start bridge reuses the page BDMS while aborting its underlying fetch so signing cannot create a second API request. Protected likes/favorites also use the page Web SecSDK to add current query and header signatures.

On other hosts, a sandboxed `data:` iframe loads the pinned BDMS runtime without same-origin access. CSP blocks network, image, frame, object, and form capabilities; only a random-channel `postMessage` returns the signed URL. Local TypeScript SM3/RC4/Base64 logic is a best-effort timeout fallback, not the primary parity guarantee.

All data transport still uses the injected GM HTTP client with `credentials: 'include'`. Host-page native fetch is never used for cross-origin API delivery. Search uses the captured 19.6 parameter profile and account endpoints use the 17.4 profile, including endpoint-specific key order.
