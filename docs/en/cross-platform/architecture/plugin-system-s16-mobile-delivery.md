Chinese counterpart: [S16 手机工程与交付门禁](../../../zh-cn/跨平台/架构/插件系统重构S16手机交付.md). The [implementation steps](plugin-system-refactoring-steps.md) own current progress. Updated **2026-10-20** after authorized Android emulator and physical-device inspection. The user has no macOS/Xcode environment and requested completion of currently verifiable work.

S16 remains **In progress**. Android now also has signed arm64/x86_64 release APK/AAB artifacts, repeatable native tests, a product WebView bootstrap guard and 11 passing native cases plus release lifecycle smoke on a physical arm64 phone. iOS engineering, physical minimum-device measurements, optimized-release Android media/proxy acceptance and iOS account/media adapters, separate declarative/code admission and production channel acceptance remain incomplete. ## Engineering delivered

- The real application has a maintained Android project under `apps/tauri/src-tauri/gen/android`, generated with locked Tauri CLI 2.12.1. The current minimum is **API 26**, with compile/target SDK 37. An authorized API 24 launch of the earlier APK crashed in Tauri's Jackson dependency on missing `java.lang.BootstrapMethodError`; that configuration was corrected rather than reported as working support. Tauri config, Gradle and NDK helpers use API 26. Physical minimum-device acceptance is still pending. Android/iOS configurations use `com.anymusic.app`; desktop identity/storage remain unchanged. iOS has configuration only.
- `pnpm build:mobile:android aarch64` or `x86_64` builds frontend and locked Cargo library and assembles a debug APK. Add `--release` for optimized native/R8 APK and AAB, and `--signed` for explicit signing. Debug/release JNI directories are separate; old main/JNI staging is ignored. Machine-local Gradle paths come from the locked Cargo graph, preserving maintained Kotlin/XML. This requires `JAVA_HOME`, `ANDROID_HOME`, `NDK_HOME`, Rust targets and SDK components; it neither launches the product nor publishes artifacts. `pnpm check:mobile:android` runs offline arm64 zero-warning Clippy; `pnpm check:mobile:boundaries` checks ACLs and the minimum SDK.
- Product startup requires Chromium WebView **111 or newer**. An exported native bootstrap checks before constructing Tauri/WebView; an older/missing provider shows a localized update message. The main Activity is private. Valid OS intents and their grants forward inside the same app UID. This bootstrap floor is independent of external-plugin admission and does not accept all newer engines. API 34/WebView 113 has debug workbench/IPC checks; the reference phone has API 35/WebView 153 release launch evidence. API 26's old provider exercises only the native update message. See [Jackson's Android floor](https://github.com/FasterXML/jackson-databind/issues/4653).
- Desktop `main`, Android `main-android` and iOS `main-mobile` capabilities match only the main WebView. iOS retains local-data/capability/cancellation commands. Android grants bounded package previews, snapshot/revocation, document saving and redacted diagnostics, plus Bilibili-only native account HTTP, QR app handoff, account proxies and account-bound media grants. No system-browser/CDP, DEV, install/rollback, guest commands or executor relays are granted. Kotlin `mobile-platform` is Rust-only, without a JS handler; earlier device tests denied direct renderer credential access.
- Native capabilities select mobile form before mounting. Android advertises document/Keystore/account HTTP/proxy/foreground media adapters and receives a preview-only plugin port without DEV/install/execute controls. Missing capabilities explicitly remain unavailable and mobile external policy remains `none`. The mobile source/module/account directory contains only Bilibili; iOS retains its unavailable metadata without account factories. Earlier real registry tests and mounting fixed the empty-registry startup failure. The 2026-10-20 reference arm64 debug follow-up completed user-confirmed Bilibili app handoff/return, credential reuse and an automatic signed-in check after restart, plus five native search pages (150 results) and three isolated Android handoff tests. Rust and Kotlin now agree on both official QR scan routes; invalid addresses no longer report a missing app. Reactive list-runtime membership fixes new searches falsely displaying an uninstalled source; the initial session probe waits for source activation. App-clone and optimized-release authentication acceptance remain separate; Android foreground media has reference debug-device evidence; optimized-release and broader acceptance remain separate. See [current login and source distribution](../../desktop/runtime-architecture.md#mobile-architecture).
- Android uses `ACTION_OPEN_DOCUMENT` and single granted `content://` VIEW/SEND streams. It copies at most 16 MiB within five seconds into a private fsynced immutable snapshot. Names/size claims do not authorize content. Read polling supports cancellation; two opener slots contain providers ignoring cancellation and close late descriptors. Rust accepts only a generated staging ID, removes staging and runs the existing verifier/preview. Session hashes deduplicate OS input; manual selection can retry. Restart reclaims owned staging only. No URI/path reaches JS or grants installation.
- Android registers package association/sharing and `anymusic://plugins/install`. A fixed notification carries no URI/bytes/authority; the host drains native input. Deep links reuse public-HTTPS anonymous acquisition, rejecting credentials/private targets/malformed links. Suspension clears queued OS input, cancels package acquisition and invalidates previews; late downloads cannot produce usable previews. No new interpreter, renderer fetch or credential fallback is added.
- AndroidKeyStore holds an AES-256-GCM wrapping key; only an authenticated versioned envelope is stored in `noBackupFilesDir`. The data key reaches Rust through the private bridge. Corrupt/missing material fails closed without replacing existing credentials; automatic Android backup is disabled. Emulator testing does not establish hardware backing or physical lock/invalidation behavior. iOS Keychain is unavailable.
- Android `ACTION_CREATE_DOCUMENT` saving uses a single-use native token (30-second expiry), private outbox, 32 MiB pre-read/commit limit and five-second open/write budget. Background/cancel invalidates destinations/writes, including jobs queued before suspension; restart reclaims owned outbox files. Diagnostics use the same adapter. Plugin result saving retains the post-dialog epoch check but is not exposed here. Final URIs/paths never persist in product data. A failed provider may retain an empty/partial destination; the host does not delete arbitrary provider-owned documents.
- Native suspension cancels registered requests/account sessions, ordinary QR sessions, transient media grants/renderer leases, acquisition/previews and the memory key, without replay on resume. Only an explicitly opened Bilibili QR handoff survives within its original 180-second validity; replacement/cancellation/expiry prevents revival. Mobile excludes desktop executor/DEV resources and desktop acceptance features. Android foreground Bilibili media uses the native account-bound loopback listener, initialized before capability discovery; Range requests retain account cookies/Referer/proxy and cancellation. WebView cleartext exceptions cover only loopback. Playback and downloads use existing shared streaming/fallback and native document saving. Background execution and iOS media remain unavailable; the reference debug device has foreground playback/seek/MP3-save and native proxy evidence; optimized-release and audio-interruption acceptance remain separate.
- Restart inspection exposed order-dependent generation checksums: Rust map serialization could invalidate a newer native mirror. Generation manifests now use version 2 and `c1:` checksums that recursively sort object keys. Version-1 insertion-order checksums remain readable; old readers reject new manifests read-only instead of choosing a stale mirror. Native-only restore tests cover key reordering and lost WebView storage. Existing portable-data rules preserve unknown namespaces and exclude install/grant/session authority; this is recovery, not synchronization.

## Repeatable Android release and emulator checks

Use these commands from the root; build commands do not authorize live inspection:

```sh
pnpm build:mobile:android aarch64 --release
pnpm build:mobile:android aarch64 --release --signed
pnpm check:mobile:release aarch64
pnpm build:mobile:android x86_64
pnpm accept:mobile:android --serial emulator-5580
pnpm accept:mobile:android:device --serial DEVICE_SERIAL
```

Signing requires all four environment variables: `AM_ANDROID_KEYSTORE` (absolute path), `AM_ANDROID_STORE_PASSWORD`, `AM_ANDROID_KEY_ALIAS`, and `AM_ANDROID_KEY_PASSWORD`. Passwords are never CLI arguments or generated tracked Gradle files. Incomplete inputs fail before building. There is no debug-signing fallback. Unsigned mode remains explicit even if signing credentials are present. Preserve the chosen private key for updates; local validation keys do not establish a production publisher or Play identity.

Signed builds automatically run the release verifier. It checks APK signature and a single non-debug signer, matching cryptographically verified signatures for every AAB payload, actual manifest package/minimum/target SDK, non-debuggable/non-test/no-backup/no-cleartext settings, absence of the test provider, APK ZIP 16 KiB alignment and every bundled ELF's ABI/LOAD alignment. It reads archives without extraction and writes public hashes/certificate metadata to `release-verification.json` beside the APK. Build alignment does not prove execution on a 16 KiB device.

The live harness requires an explicitly selected, already running x86_64 emulator and an existing debug build. It refuses physical/default devices and an already installed test package, rebuilds the matched app/instrumentation APKs, installs without removing the product, requires successful JUnit completion, reports skipped cases, records device/WebView/page-size/artifact evidence and removes only its test APK/forwarding. It never wipes an AVD or seeds grants. Native-only tests cover adapters and the engine floor. External debug-WebView inspection covers real mount/capabilities, denied desktop/private-bridge IPC, private-target rejection, background/resume and force-stop/process-restart retention of all active core/host/namespaces/archives. It compares canonical business data, excluding mirror revisions and obsolete generations. Unsupported engines instead exercise the native update message and explicitly report `bootstrapOnly`, without claiming workbench checks. Reports remain under ignored `.codex-tmp/s16-accept/`.

The separate physical harness requires an explicit arm64 device, an already installed verified local release with exactly matching APK bytes. It uses the same native adapter sources in temporary `com.anymusic.adaptertest`/`.test` packages with an independent UID, no launcher/network/native JNI library, verifies their compiled identities before installing, initializes only its test-owned fixture provider, then removes only those packages. It does not replace or instrument the user's release, expose release debugging or weaken its R8 rules. Keystore metadata from this host measures device protection of the tested adapter, not the product's existing key. Its adapter-only manifest queries only the fixture provider, following [Android package visibility](https://developer.android.com/training/package-visibility/declaring). USB installation must be permitted by the device. After a prompt timeout, --prepared reuses the already built APKs while repeating identity/release checks; it does not skip instrumentation. Direct optimized-release instrumentation failed before tests on missing runner-only `androidx.tracing.Trace`; it is not recorded as passing release instrumentation.

Forcing repeated Activity destruction/recreation inside one instrumented process exposed a native `pthread_mutex_lock` on a destroyed mutex. That path remains unaccepted, independently of the passing normal background/process-restart checks. The harness drives the product from outside its process so instrumentation cleanup does not repeatedly tear down the Tauri event loop; this does not fix or claim acceptance of forced Activity recreation.

The API 35 software-rendered release emulator also exposed Wry 0.57.0 `main_pipe.rs:421` panicking on `GetUrl`'s canceled reply during its slow first cold startup. A subsequent process startup displayed the workbench; the physical phone's first Activity launch reported 503 ms and a subsequent screenshot confirmed the workbench. The failing cold-start environment remains unaccepted. Origin checks and release security settings are preserved; a successful warm launch does not close this failure.

## Channel requirements and remaining exits

Official channel pages were retrieved on **2026-10-19**: [Apple App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/) distinguish bundled-code restrictions and conditions under 4.7; [Google Play Device and Network Abuse](https://support.google.com/googleplay/android-developer/answer/16559646?hl=en) constrains downloaded executables/interpreted code. Neither approves this application. Android adapters follow [Storage Access Framework](https://developer.android.com/training/data-storage/shared/documents-files) and [Android Keystore](https://developer.android.com/privacy-and-security/keystore); documentation is not device acceptance.

1. Generate/build/sign the real iOS project on macOS/Xcode and implement file/share/save/Keychain/lifecycle adapters.
2. Accept the Android Bilibili account/proxy/foreground-media paths on real devices, including Range/seek/downloads and audio interruptions; implement remaining source and iOS adapters with explicit capabilities.
3. Accept declarative/code install/update/rollback/revoke/restore separately on exact systems/engines/devices. Android code still has no accepted isolated executor.
4. Measure minimum physical devices under memory/storage/network pressure and system termination; validate cross-runtime portable data without authority.
5. Finish publisher-owned Android signing/local-distribution/store acceptance and signed iOS releases; retain separate engineering, emulator, physical-device and channel records.

Only after these exits may S16 be **Implemented**. The current Android batch is implemented and locally verified; the overall stage is incomplete.
