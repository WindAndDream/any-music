# Privacy and Secret Handling

Chinese counterpart: [隐私与密钥规范](../../../zh-cn/跨平台/架构/隐私与密钥规范.md). Applies to contributors, agents, source captures, tests, documentation, CI and release artifacts in both production runtimes.

## Data admitted to the repository

Never commit real account cookies, authorization headers, access/refresh tokens, API keys, proxy credentials, signing private keys, personal contact details (except Git author/committer email metadata), account databases, browser profiles, authenticated HAR files, QR login tokens or recovery material. This includes deleted files in a commit series, commit messages, screenshots, logs, backups and compiled artifacts. Encoding or encrypting a real credential does not make it an acceptable fixture.

Keep runtime secrets in the owning GM storage, native vault or private CI secret store. Do not place secrets in `VITE_*`, which are client-visible build values. Only `.env.dev`, `.env.prod` and `.env.staging` with the reviewed `VITE_APP_ENV` and `VITE_APP_DEBUG` keys are public configuration. Local `.env*` files remain ignored; `.env.example`/`.env.template` may contain empty values or explicit placeholders only. Public/private key pairs for tests must be generated by the test, never copied from a developer or release identity.

Android release JKS files and their Base64 exports stay outside the checkout. Encoded keystore filenames are both ignored and rejected by the privacy path gate if forcibly added. Store CI signing values only in the protected `release-signing` environment; see [Builds and Releases](github-actions-release.md#configure-github-before-accepting-contributions). Never include private key bytes or passwords in test fixtures, logs, artifacts or documentation.

Use reserved example domains, explicit synthetic markers and test-owned IDs. Preserve field names, types, ordering and behavior when sanitizing source captures. Never change `captureDate` merely because data was sanitized. Use `<user-home>` and `<project-root>` in evidence instead of actual home/workspace paths. Previously measured hashes and dates remain historical evidence from before sanitization; redaction is not a rerun or new runtime acceptance. Review screenshots at readable resolution for account identity, QR codes, passwords and notifications before adding them; automated text scans do not inspect every pixel or installer payload.

Git authors and committers may use personal email addresses or GitHub-provided noreply addresses. Since commit metadata is publicly visible, privacy-conscious contributors should use `git config --local user.email YOUR_GITHUB_NOREPLY_ADDRESS` with their actual noreply address. This exception applies only to Git author/committer metadata, not to co-author trailers, commit messages or source files. Existing Git history need not be rewritten solely to change author/committer emails.

## Install and run the gates

```sh
pnpm install --frozen-lockfile
pnpm privacy:setup
pnpm check:privacy
pnpm check:privacy:history
```

`privacy:setup` downloads Gitleaks 8.30.1 from its official release and uses GitHub's release asset API if the direct URL returns a server error. Both routes verify the same checked-in SHA-256 before caching the executable in ignored `.local/privacy-tools/`. It supports Windows, macOS and Linux on x64/arm64 and requires `tar` for extraction. Offline checks reuse that verified local installation. Missing, corrupted or wrong-version scanners fail closed; setup does not alter global Git configuration.

`check:privacy` inspects tracked and nonignored new working-tree files. It rejects sensitive filenames (including DER exports), personal home/workspace paths, mailboxes and phone numbers, and scans text for Gitleaks default rules plus source-session credentials. Binary PKCS#8, PKCS#1 and SEC1 private keys are also rejected when renamed to hide their format. Tests generate temporary keys in memory instead of committing key fixtures. It also checks forced additions that bypass `.gitignore`. The complete index is copied into a disposable ignored directory for staged checks; working-tree changes cannot hide staged bytes. Snapshots are removed after either success or rejection, and diagnostics show rule/location without matched values.

- `pre-commit` runs Git Flow/whitespace checks and scans the complete staged snapshot; personal Git author/committer emails are allowed.
- `commit-msg` enforces the repository's Conventional Commits format with English headers and scans the message for privacy and secrets.
- `pre-push` preserves Git Flow checks and scans incoming commit messages, changed snapshots and secret-containing diffs, including values removed by later commits. Personal Git metadata emails are allowed. Both guards receive the same Git update stream.
- CI's **Privacy and secrets** job checks current files, secret-bearing history and incoming commit privacy. The Windows quality job installs the same scanner before the root regression suite. No path filters skip documentation-only PRs.

History secret scanning covers all fetched refs. Incoming privacy scanning checks commits introduced by a push/PR; the original private repository still retains its pre-policy personal metadata and evidence. A new public snapshot must have a single independent root commit and no original refs or objects. Never push the original private history into that public repository.

## Exceptions and review

Do not skip hooks, add a finding baseline, use `gitleaks:allow`, ignore whole test/documentation directories or disable a secret rule to make a failure disappear. The wrapper ignores inline suppression and `.gitleaksignore` files. `.gitleaks.toml` extends defaults and contains only reviewed rule-specific exceptions: acceptance file-digest maps, exact synthetic test values, SDK constants with documented public origin and exact prose. A new exception must explain provenance and scope and include a regression proving that a genuine-looking credential in the same area is still rejected. Sensitive filenames and additional privacy rules are independent of Gitleaks exceptions.

Review changes to scanners, hooks, checksums, allowlists and CI as security-sensitive changes. Configure the actual public repository to require PR review, **Privacy and secrets**, **Git Flow policy** and **Repository checks (Windows x64)** for `main`/`develop`, with stale approval dismissal, resolved conversations, no force-push/deletion and no administrator bypass. Verify enforcement after repository creation or plan/visibility changes; checked-in workflows alone do not activate server protection.

Local hooks can be bypassed and scanners have false positives and blind spots. Reviewers must examine captures, images and binary artifacts and prevent changes that weaken the gate. Automated checks reduce accidental disclosure; they do not prove the absence of all private information or malicious encodings.

## If sensitive data is found

Stop the affected publication/push. Revoke or rotate real credentials through their owning service, sanitize the working tree and affected artifacts, then assess commit history, PR discussions, Actions logs, releases and external copies. Do not paste the value into a public issue, review, test assertion or diagnostic. A deletion commit, `.gitignore` or `.mailmap` does not remove raw historical data.

Keep the original repository private while preparing a separate sanitized export when old personal metadata must not be published. Review the exact exported tree, scan its complete new history and configure protection before accepting contributions. History rewriting and force pushes on existing long-lived branches are not part of the ordinary repair workflow; follow [Git Flow](git-flow.md) and coordinate any separate migration with affected owners.
