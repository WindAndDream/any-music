# Tauri Desktop Runtime Architecture

Scope: current desktop native composition and status; start with [desktop rules](development.md). Mobile sections state capability limits, not device acceptance. GM rules belong to [Userscript](../userscript/development.md).

Chinese counterpart: [Tauri 桌面与移动运行端](../../zh-cn/桌面端/运行端架构.md).

The production runtimes are `apps/userscript` and `apps/tauri`. Tauri 2, Vue 3, Vite and Rust implement the native app; Electron is not used. Desktop and mobile compose the same application through explicit capabilities. Android native adapters, signed artifacts and selected reference-device evidence exist; iOS and the remaining minimum-device/execution/channel exits are incomplete. The [S16 matrix](../cross-platform/architecture/plugin-system-s16-mobile-delivery.md) defines those separate limits.

## Commands and prerequisites

Run from the repository root:

```bash
pnpm install
pnpm dev:tauri
pnpm build:tauri
pnpm start:tauri
pnpm build:tauri:dev
pnpm build:tauri:staging
pnpm bundle:tauri
```

Windows output: `target/release/any-music-tauri.exe`. Rust (the lockfile was checked with 1.91.1), MSVC C++ tools and WebView2 are required. The product UI uses Tauri's WebView; login/risk verification uses installed Chrome/Edge. macOS and Linux require their Tauri system dependencies and system browsers. [GitHub Actions](../cross-platform/architecture/github-actions-release.md) declares installer builds for Windows x64, macOS arm64/x64 and Linux x64, with unsigned Windows/Linux artifacts and ad-hoc macOS signing. Hosted-runner builds, installer associations and runtime acceptance remain separate; the workflow does not renew external-plugin admission. Certificate signing/notarization, application updates and store publication remain outside this delivery.

Root builds cover Tauri in all three modes. Root tests include Rust tests; typecheck includes Rust formatting checks. Builds and unit tests do not open product windows.

The development frontend uses the fixed address `http://127.0.0.1:21420`. Vite's `server.port`, Tauri's `build.devUrl` and Rust's development origin check must match. Keep `strictPort: true` as described in [Tauri's Vite configuration](https://v2.tauri.app/start/frontend/vite/); Tauri's `beforeDevCommand` starts the frontend through `pnpm dev:frontend`. On the current host, the original `1420` falls within Windows' excluded `1365–1464` TCP range, so it was replaced with `21420`, which passed a socket binding check. Inspect OS exclusions with `netsh interface ipv4 show excludedportrange protocol=tcp`.

## Shared behavior and storage

`music-workbench` owns shared workbench, library, favorites, playlists, player, queue, downloads, history, host-owned published recipes and snapshot orchestration, with tests following their owners. Applications inject HTTP, stable storage, sources, login, media and file-saving capabilities. `plugin-tag-management` owns tag rules/associations and specialist UI; `plugin-music-creation` owns drafts/materials/editing state and specialist UI. Workbench consumes their named ports and projections. `ui` remains controlled presentation; `plugin-source-bilibili` and `plugin-source-douyin` own source protocols; `core` owns domain models and ports. See [package boundaries](../cross-platform/architecture/reusable-package-boundaries.md).

The userscript retains its `any-music:userscript:*` keys, Shadow DOM, lightweight launcher, GM transport and single host account/proxy settings. Desktop uses embedded presentation and native file saving without touching those keys. Its renderer snapshot and native `product.json` mirror contain the current generation map and commit pointer. Startup selects the highest complete generation, then revision, and aligns both mirrors before exposing repositories or the workbench. Unsupported mirror versions and unrecoverable snapshot damage stop initialization while retaining recovery data; a readable peer can restore a damaged mirror. Writes update the local mirror synchronously and queue native persistence; a native mirror failure is visible and blocks subsequent writes until restart. Snapshots exclude credentials, temporary media URLs/bytes, Blob URLs and disk paths. Account policies contain public IDs/operation metadata. Userscript data is not imported automatically. See [data ownership](../cross-platform/architecture/plugin-data-ownership.md).

Desktop and Android download admission uses the injected native `DownloadScheduler`. Rust owns a bounded FIFO semaphore (1–5 whole-song tasks), including waiting-task cancellation; renderer work cannot start before a native permit. The permit covers resolution, reading, encoding and retries, and is released after task cleanup. Shared orchestration retains retry policy and browser encoding. Closing/reloading the main WebView, application exit and mobile suspension clear transient admission. Userscript retains frontend scheduling; iOS media/saving remain unavailable. Automated tests do not establish device acceptance.

Download directory selection lives under Settings → Network and Downloads → Song Downloads. Desktop uses the native folder picker and persists only the selected directory in native `download-directory.json`, outside product snapshots and download history. Native save receipts expose only filename, length and full SHA-256, never a final disk path. Re-download verification opens only that exact name in the current directory and hashes the complete file with a 64 KiB buffer; name-only, size-only and content-only matches never suffice. Saving equal bytes under the exact requested name skips a duplicate write; other collisions exclusively create numbered files and preserve existing content. Android uses `ACTION_OPEN_DOCUMENT_TREE` and persisted read/write grants held in native preferences; only the folder's display name reaches the renderer. Downloads create documents in that tree through the existing bounded save-token adapter (32 MiB, foreground/lifecycle/deadline checks). Reset restores per-file system dialogs, and picker cancellation preserves the previous selection. Missing directories, revoked grants and write failures remain visible errors requiring retry or reselection. Android 11+ restricts storage roots and the Download directory itself; choose a permitted subfolder. See [Android SAF](https://developer.android.com/training/data-storage/shared/documents-files). iOS retains unavailable native-save capabilities. Automated Rust, renderer and Android compilation checks do not establish live picker/device acceptance.

## Accounts and verification

NetEase Cloud Music is built in on desktop with account-bound HTTP/media and native QR polling. Its login UI offers QR only; native login verifies the official account/profile identity before committing credentials. See the [NetEase integration record](../cross-platform/platforms/netease/api-integration.md) for protocol observations and outstanding live GM/desktop acceptance. Mobile does not register this source.

Visible Douyin verification reuses the blank tab opened by the account browser. Rust attaches and enables response observation before navigating to the official page, without creating a second visible window. A bounded wait covers the debugging port becoming ready before the startup tab; background paths without a startup window still create a hidden target. CDP fixture tests verify reuse and command order; this change has not received a live system-browser check.

First installation starts with an empty account list and never creates default accounts. Users prepare login drafts and complete native verification before built-in accounts enter the list. External declarative gateways offer no-login access only when explicitly declared; see [Music Source Authentication](source-authentication.md). Existing saved accounts are preserved; restarting after deleting all accounts does not recreate any. Accounts support add/delete/rename/enable and direct access or one primary unauthenticated HTTP(S)/SOCKS5 proxy with up to eight ordered backups. The account connection settings and native routing own this bounded failover chain, as described below. Proxy authentication and proxy-group UI remain unavailable; independent account-pool/network-routing algorithms do not establish native connectivity or live acceptance.

The permanent entry is Settings: “Music sources → Account management” owns accounts, login/verification, connection assignment and automatic request policies; “Network and downloads → Proxy management” saves multiple independent proxies, shows assigned accounts and allows deletion after assignments are removed. Forms reuse shared settings cards, switches, control radii and single-column container adaptation. The temporary window toolbar is removed.

Proxy settings have separate Add proxy and Proxy management regions. Field errors appear beside inputs; failed saves retain drafts, and successful native saves clear them after snapshot confirmation. Compact rows show name, protocol, endpoint, assignment count and account names, adapting to narrow containers. Both renderer and Rust validate unauthenticated HTTP, HTTPS and SOCKS5/SOCKS5h endpoints with valid IPv4, bracketed IPv6 or domain hosts and explicit ports from 1 to 65535. Paths, queries, fragments, credentials and abbreviated IPv4 forms are rejected. Trimmed names must be unique. Endpoint deduplication normalizes scheme/host case, the terminal domain dot, IPv6, port digits and the trailing slash while preserving explicit default ports. Rust validates and deduplicates within the same configuration transaction to prevent concurrent duplicate saves. Syntax validation does not establish proxy connectivity.

The Discover page opens the platform account switcher; automatic mode displays Random and retains each operation's request policy. A platform with no accounts displays “无账号” and offers “添加” to open a standalone account creation dialog with that platform preselected, including for sources that allow anonymous access. This entry never opens global settings; the protected dialog retains standard enter/leave motion and closes back to Discover. Manual selection persists only a public account ID and applies to new searches, imports, session checks and playback/download resolutions. Existing lists and media retain their actual identity when search preferences change. Inside a track list, the platform and request account are read-only; retry prefers its original account. Removing or disabling an account clears invalid preferences. An idle list chooses an available account on its next load and rebuilds from page one without mixing old cursors. An active load stops and opens an error dialog; retry chooses an available account. If none remain, the error directs users to add or enable an account in Settings. Switcher and settings share the theme and modal host. Validation covers components, state composition and Rust tests, excluding application visuals and live account checks.

Generated account UUIDs bind an isolated CookieStore/client, encrypted credentials and `profiles/<uuid>`. Frontends cannot provide filesystem paths. The OS vault holds a 32-byte key; credential files use ChaCha20-Poly1305, without plaintext fallback. Chrome manages its own profile storage; the app does not read cookie databases or put credentials in URLs/logs.

Bilibili retains native QR generation, polling, confirmation and cancellation. Production Douyin login uses Rust `douyin_browser` to drive official pages in installed Chrome/Edge. The app shows official PNG QR images and observes scanning, MFA, SMS send/submission and account confirmation through CDP. User-selected SMS and six-digit input operate uniquely matched official controls; face, send-SMS and unknown challenges use explicit visible handoff. Login UUIDs scope replacement, cancellation and SMS. Private challenges remain in the page/native memory; stale results cannot update a new session.

Bilibili's native generation endpoint was checked on 2026-10-20 and returned `https://account.bilibili.com/h5/account-h5/auth/scan-web` with the same 32-character challenge key. Both Rust challenge construction and Android intent validation accept that exact host/path and the previously observed Passport scan route, with HTTPS and a single 32-character challenge key; ordinary account pages remain rejected. Android reports invalid handoffs separately from application launch failures instead of treating every rejection as a missing installation. Douyin's QR/check response allowlist covers the exact Passport paths on `www.douyin.com` and `login.douyin.com`. Auxiliary profile checks preserve up to 32 in-flight login requests and 96 ordered events for the main account actor, without retaining response headers or signed queries. They cannot silently consume the QR or confirmation transitions.

Windows creates an inactive desktop and starts a normal headed browser through `STARTUPINFO.lpDesktop`, without switching the user's desktop. Background sessions use ordinary headed pages on that desktop, retaining page visibility/focus behavior; their windows do not appear on the active desktop, taskbar or Alt+Tab. Auxiliary search pages in an explicit visible session use CDP hidden targets. No headless flag or fingerprint spoofing is used. Platform risk decisions are not guaranteed to match visible browsing. Explicit visible handoff ends the same account's background tree before reopening the persistent profile; previous QR/challenge continuity is not promised. Hidden behavior outside Windows remains unverified.

Each account owns a UUID, user-data-dir, exclusive file lock, random loopback CDP port and assigned proxy. Windows launches suspended, assigns a kill-on-close Job, then resumes. Exit/cancel removes the owned tree and retains the profile. Bounded network buffers preserve responses across process navigation. Missing login bodies wait for fresh official account confirmation rather than implying success. An authenticated user object plus a valid login cookie are required before Storage.getCookies reads platform cookies, including HttpOnly values, into the encrypted native vault with the actual browser User-Agent. Credentials never cross renderer IPC. Explicit subsequent session checks fetch fresh state through temporary auxiliary pages; there is no periodic probing. Completing visible verification rereads current cookies and closes Chrome gracefully to flush the profile before hidden handoff. Expired short-lived cookies do not abort valid credential import.

Older Rust Passport login generated QR images from a clean CookieStore but checking entered 4031/CAPTCHA. Its modules/tests remain, outside the production Douyin path. Bilibili's manual system verification still reads browser version/cookies once after the user clicks Complete and then closes that dedicated browser. Test-browser contract observations do not establish production account or Rust HTTP acceptance.

Browser verification pauses that account and cancels its old session without blocking other accounts. Explicit login rejection and known challenge signals produce signed-out and verification states respectively. HTTP 403/429 alone do not establish expiry, and challenge evidence takes priority over HTTP 401. Anonymous session checks do not expire anonymous accounts. Each account has one API request slot, jitter and bounded exponential backoff; three consecutive network/timeouts pause it for user inspection. Unknown errors are not classified as proven proxy failures. There is no automatic direct fallback or periodic background login probing.

Douyin identity checks and search use the following state boundaries. This update has automated tests only; no application, account browser or new live-site verification was started.

Native accounts expose independent `state.login`, `state.verification` and `state.connection` facts. `status` is the account pool routing projection; `authentication` describes stored credential mode. Signed-in and verification-required can coexist. New accounts declare login, verification and connection facts explicitly; persisted accounts must contain those facts. Pausing content for a login action does not record a fabricated CAPTCHA requirement. Cancellation and restart release that operation pause while preserving actual content challenges. An explicit Douyin identity check also validates the account browser when native metadata is still anonymous, adopting credentials only after confirming its profile and cookies.

Routing preflight failures carry the concrete account ID. First-page and pagination challenges bind it to the listing; the verification action exists only while that identity remains present and enabled. Launch failure, browser closure, cancellation, timeout or confirmation failure retain the original request reason and show the action's cause and retry in the same details view. Completion confirms official search results, identity and credentials before refreshing the snapshot and reloading page one. Snapshot failure or cancelled loading exposes the Retry action without another browser verification. Only the listing's own successful credential update can cross this recovery phase; deletion, disabling and proxy changes still cancel old work. Regression tests cover the production source adapter, account selection, listing states and mocked native IPC, without live account-browser acceptance in this update.

| Observation or operation                                                                                 | Account state and recovery                                                                                                                       |
| -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Official user profile and login cookies confirmed                                                        | Valid login; retain any separate content verification requirement                                                                                |
| Official login rejection or visible login panel, with no login cookies in the same account browser       | Signed out (login expired); login is available                                                                                                   |
| Login rejection or panel while browser login cookies remain                                              | Verification required; retained cookies do not prove platform acceptance and establish neither expiry nor success                                |
| `2483`, a verification link or search `verify_check`                                                     | Verification required, taking priority over HTTP/business authentication rejection; retain credentials                                           |
| Missing profile fields, changed format, connection failure or timeout                                    | Check incomplete; preserve account state and read a fresh profile on explicit retry                                                              |
| QR expiry, closed verification window or cancellation                                                    | QR expiry belongs to that scan; cancellation proves neither logout nor completed verification, and saved accounts retain their pending challenge |
| Official search response confirms completed verification, followed by fresh identity/cookie confirmation | Save current credentials and restore availability; restart the same listing at page one                                                          |

The portable adapter parses search state and optionally reports it through `reportFailure` for the current account/listing. Rust checks target ownership, same-account cookies and the current session epoch before persisting public state. Request IDs support cancellation; old listings, replaced account environments and late results cannot overwrite newer state. Unavailable account candidates retain the actual verification or connection reason. Account checks count logout, verification and incomplete checks separately; SMS requests, submission, official confirmation and retry each display their operation progress.

## Account settings and request connections

Native account identity is `(platformId, platformUserId)`, separate from the browser/Profile UUID and editable local name. Login commits and official identity checks reject another configured account with the same platform identity, including disabled accounts. Unauthenticated entries cannot be identified before login. Bilibili uses the native official login's `DedeUserID` and nav `mid`; Douyin uses the validated self-profile `uid`. An existing profile cannot be rebound to a different user. Deleting and re-adding the same platform user creates a fresh runtime UUID and credentials, while public name projections link its previous incarnations.

`accounts.json` atomically retains public account history with ordered name periods (`fromMs`/`untilMs`) and removal timestamps; deletion still removes credentials, connections and browser data. No historical name list crosses IPC: `accountLabels` projects only the latest label for each incarnation. Rename/status updates do not duplicate unchanged name periods. Tracks may retain bounded, display-only `acquisition` metadata (account UUID, name at acquisition and time). Track details resolve the latest name through this projection; persisted provenance never chooses a request account or revives removed operations. The library and download history retain the acquisition snapshot. Previously saved tracks without provenance remain valid and do not invent an account association.

Deletion confirmation separates its short question from three labeled consequences: data to clear, operations to stop and saved data to retain. It explicitly retains songs, music lists and account name history.

Account management immediately shows platforms with total, signed-in, login/verification and disabled counts, with Add account and Check all actions aligned at the bottom right. All layouts omit the redundant introductory text and retain the account-isolation hint. Creation opens within the management dialog, preserves the name draft and supports platform selection; adding from a platform list preselects that platform. Compact continuous account rows place the name, status, connection and check action together, with spacing between the details entry's hover background and its check button. Results appear within the status line: a valid-login result replaces the duplicate signed-in label without adding a result row. Failed checks retain known account facts, disabled accounts show their disabled state, and longer errors can wrap. Details separately edit the name, connection and login state, with Delete account beside Back in the footer and a separate deletion confirmation. Dialog paths start at the current platform or creation popup and exclude the outer account settings. A clickable path returns to any ancestor within the popup; closing its root returns to the platform overview. Long paths scroll horizontally with a hidden scrollbar. Narrow screens retain bottom sheets. Action buttons use content widths and wrap when needed, retaining at least 44px click heights. Trimmed names must be unique within a platform, with native validation immediately before persistence.

Management offers Check all, while account lists and details offer individual checks. Checks run serially with fixed identities and skip disabled accounts. Bilibili reports anonymous accounts as signed out without a request; Douyin also checks for an existing login in that account's browser. Each checked account performs one platform session check without identity competition, automatic login or replay. Closing settings or cancelling aborts native reads and ignores late results. Only Bilibili's official GET nav identity probe and Douyin's self-profile operation may pass a paused state; content requests stay paused. Native authentication evidence updates the status; network errors, timeouts and invalid responses never establish expiry or clear stored credentials. A valid identity never clears a separate content security challenge; the check continues to show required verification. Signed-in accounts disable repeated QR/browser login until expiry or required verification is confirmed.

Login presents QR and System browser. The native layer selects an installed compatible browser and retains an isolated profile. QR generation, encoding or display failure disables that account's QR entry and directs users to the browser; expired QR codes may be regenerated. Secondary verification presents the platform's actual methods, with external methods opening the system browser. Closing, switching methods and late results are isolated by login UUIDs so an older operation cannot end a replacement session.

Connections select one saved primary proxy and up to eight ordered backups, or direct access. Replay-safe Rust HTTP reads fail over only on proxy connection errors, connection timeouts or proxy authentication failures, retaining the account and CookieStore. A successful proxy is reused within the current account environment. Connection attempts share a total budget, while successful media streams do not inherit the short connection timeout. Writes are not replayed; source authentication/security challenges are not proxy failures, and direct access is never an implicit fallback. Douyin CDP restarts the same account browser only for explicit proxy/tunnel failures. Existing later-page requests prompt a listing refresh rather than reuse a cursor from the previous browser.

Deletion confirmation explains that requests, playback, downloads and login verification will stop; accounts in use can be deleted. Native operation startup and deletion share an atomic gate. Deletion blocks new work, cancels old sessions and queued requests, revokes media grants, ends browser verification and releases renderer usage before deleting credentials and detaching the validated Profile through a same-volume rename. A single background collector reclaims cache files and retries tombstones after restart. Failed detachment retains a disabled account and an actionable error for retry. Runtime invalidation synchronizes lists, cached sessions, the player and downloads. Affected playback returns to idle without advancing; other accounts and saved tracks, lists and queues remain intact. Invalidated lists rebuild page one before paging again.

## Operations, pagination and media

Settings no longer expose automatic account request policies. Automatic selection keeps existing defaults and remains compatible with stored account scopes, random/shuffle selection, serial attempts or at most two concurrent accounts. Read competition requires replay safety; login confirmations never compete. Attempt/total budgets are 25/60 seconds; the first valid result cancels losers.

Douyin search follows the stability rules above: serial attempts and user verification after a risk challenge. Other operations retain their configured competition policy.

First-page competition selects one account; later lazy pages retain its identity/cursor. Consumer stop, disabling, deletion or environment changes release requests. Media descriptors become random loopback grants held by Rust. Native audio, Range and complete-read paths retain the grant's account cookies/proxy. Only a random grant ID enters the local URL. The listener binds 127.0.0.1 and streams Range without full-file caching; grants remain in memory with count/expiry budgets and are revoked on environment changes. Descriptor, native streaming, bounded Range/MSE and complete-read fallback order is preserved.

Douyin search uses official search pages to generate requests. Rust captures allowlisted general/search/stream and general/search/single bodies, preserving bytes for shared DTO parsing/mapping. Each listing owns a target, keyword and cursor. First consumption creates its page; later pages scroll on demand; stopping closes it. The official page may preload its next cursor, so matching responses are retained while consumers are idle or checking account state. Each listing keeps at most three pending responses, with a 24 MiB per-account cache budget, eight-listing cap and bounded response sizes/duration. Session checks also use official pages.

Work detail for playback, downloads and single-work imports uses the owning account browser too. Native validation accepts a numeric work ID and video/note kind, then creates a fresh target and captures only its exact aweme/detail response or main-frame work document, bounded to 12 MiB and 18 seconds. The page load event can precede the client detail request, so the matching API takes priority; documents are a fallback only when the read budget expires without an API response. Network, verification and authentication failures retain their original error. Portable API/React Flight parsing checks work identity and playable media; listing URLs are neither reused nor persisted. The target intercepts Media/Image reads and closes after success, failure or cancellation. Actual media still streams through the same account's Rust HTTP and loopback grants. Official detail failures no longer fall back to local requests missing webpage security signatures. Watch history, personal likes, collected videos/mixes and mix works use the owning account’s CDP import port. Other lists and collected-music detail retain Rust HTTP/shared signing; contract records identify actual live coverage.

Native account checks resolved API detail for two real works through the portable parser. One also returned HTTP 206 and 1024 bytes of video/mp4 through its owning account's Rust HTTP; response bodies and media URLs stayed in memory. Automated regression covers document/load before the detail API, bounded no-API fallback, preservation of network failures, timeout, cancellation, response limits and target cleanup. This evidence excludes the product audio playing event and complete loopback-grant playback acceptance, and does not update the website contract captureDate.

## Mobile architecture

`core/ports/account-login` separates QR content from presentation: display for a second device, handoff for same-device platform/native authentication, or unavailable. Mobile must parse and hand off QR content rather than pretend it scanned its own screen.

Verification declares system-browser/platform-auth-session/unavailable and never falls back to a Tauri WebView. Android provides Bilibili-only native account HTTP, isolated CookieStores and Keystore-backed credentials. Its QR presentation is `handoff`: generation automatically opens the Android app chooser with the official Bilibili scan page in `bilibili://browser/`; no package is pinned, allowing an installed app clone to be offered by the OS. The login page retains an explicit app-open button that reuses the pending QR session, plus regeneration after expiry or failure. `open_qr_login` accepts only account/login IDs and derives the link from the native challenge; arbitrary renderer URLs cannot launch an app. The [official scan entry](https://passport.bilibili.com/h5-app/passport/login/scan) supplies this app-browser mechanism; source inspection does not establish device acceptance.

Android requests a separate temporary authorization task with `FLAG_ACTIVITY_NEW_DOCUMENT`, `FLAG_ACTIVITY_MULTIPLE_TASK` and `FLAG_ACTIVITY_EXCLUDE_FROM_RECENTS`. The official scan page closes its app browser after successful confirmation; an independent task allows that close to return to Any Music instead of exposing Bilibili's existing activity history. The chooser preserves the flags and implicit app/clone selection. Native QR polling still verifies and commits credentials. See [Android document-task behavior](https://developer.android.com/reference/android/content/Intent#FLAG_ACTIVITY_NEW_DOCUMENT). Automatic return with actual client versions, an existing Bilibili task and app clones requires live regression, especially for clients overriding document launch behavior.

Login method entries appear only on the first step. Selecting “选择方式” cancels the previous QR/browser generation and slides back; verification and completion cannot be skipped. Touch controls have a 44 px minimum and transitions respect reduced motion. Desktop retains QR display and isolated system-browser verification. Android offers QR handoff only; iOS login remains unavailable pending Keychain/authentication adapters.

Native capabilities drive mobile form and explicit unavailable errors. Mobile uses platform-specific ACLs and `externalPlugins: none`, excludes desktop executor/DEV resources and cancels transient work on suspension. Only an explicitly opened QR handoff survives suspension within its original 180-second validity; ordinary QR sessions, requests, media and plugin acquisitions are cancelled. Returning does not automatically reopen the platform app, and cancellation, replacement or expiry cannot revive a session. On 2026-10-20, the reference API 35 arm64 phone's debug APK completed user-confirmed Bilibili app authorization, return, credential reuse and an automatic signed-in check after restart; native search loaded five pages and 150 results. Three isolated Android handoff tests passed. See [S16](../cross-platform/architecture/plugin-system-s16-mobile-delivery.md) for the separate document/Keystore and release evidence. Android also composes foreground Bilibili media and downloads through native account-bound loopback grants, including Range/seek reads and native proxy routing. The listener binds before capability discovery; WebView cleartext is limited to loopback by network_security_config.xml, following [Android network security configuration](https://developer.android.com/privacy-and-security/security-config). accountProxy drives the proxy settings entry instead of a desktop-form check. Native fixture tests cover cookies, Referer, proxy selection, Range order, cancellation and grant cleanup; renderer tests cover descriptor registration, release and document saving. On 2026-10-20 the reference API 35 arm64 debug phone played Bilibili media, sought from about 106 seconds to 65 seconds while retaining playback, and saved a 5,610,491-byte MP3 through the system document picker. A separate temporary anonymous account received a native Bilibili HTTP 200 response through a locally observed proxy tunnel; temporary account/proxy/USB forwarding were removed. MP3 encoding had exposed a blocked Blob worker/WASM under the main host CSP; explicit worker-src self/blob and wasm-unsafe-eval now enable the bundled codec without changing external executor policy. See [debug acceptance](../../baselines/android-builtin-media/2026-10-20.json); optimized-release, interruption and broader-device acceptance remain separate. App clones, optimized-release authentication, iOS adapters and minimum-device/execution/channel exits remain unaccepted.

Primary references: [Tauri process model](https://v2.tauri.app/concept/process-model/), [prerequisites](https://v2.tauri.app/start/prerequisites/), [Chrome debugging profile requirement](https://developer.chrome.com/blog/remote-debugging-port).

## Plugin host and mobile targets

Native crates own protocol, policy, authority, anonymous networking and package verification; the application injects concrete stores, callers, consent and transport. Account HTTP/CDP/media grants and `product.json` remain host infrastructure. Guest projections cannot contain credentials or confer main-view IPC rights. Each executor binds an actual isolated native principal, epoch, scope, expiry and budgets; resource delivery waits for the native all-source filter. Changes to host/Profile/resources require fresh matching acceptance.

[Desktop delivery](../cross-platform/architecture/plugin-system-s15-tools-and-desktop-delivery.md#evidence-and-limits) records the exact admission boundary. The current Profile differs from its retained accepted record, so external installation/execution remains closed. Prototype acceptance, offline tests and CLI/testkit do not renew admission.

Current contracts live in [native authority](../cross-platform/architecture/native-plugin-authority.md), [anonymous networking](../cross-platform/architecture/plugin-networking.md) and [packages/recovery](../cross-platform/architecture/plugin-packages.md). Catalogs provide no media resolution, and no production distribution trust root is provisioned.

Mobile external policy stays `none`, without install/command/DEV authority. Android package acquisition supports inert preview/document saving; iOS adapters, minimum-device, execution and channel exits remain open in [mobile delivery](../cross-platform/architecture/plugin-system-s16-mobile-delivery.md). Desktop process/Profile/CDP acceptance never admits mobile targets.
