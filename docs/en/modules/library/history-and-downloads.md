# History, Listen Later and downloads

[中文](../../../zh-cn/板块/资料库/历史与下载.md)

The shared controller and repository own playback history, queue order and managed download tasks. Applications inject persistence and saving.

## Playback history and queue

Playback history keeps one entry per stable track ID across all playback entry points. Replaying a track moves it to the top and records progress for the new play. Playlist listening counts include repeat plays while a track remains in history. Loading a snapshot keeps the newest entry for each track before applying the limit. Merging a backup also keeps the newest play per track. Progress updates are throttled to one injected-storage write per second. The user can retain between 1 and 500 tracks. Lowering the limit immediately removes the oldest entries, and the storage boundary enforces the same hard maximum.

The listen-later queue uses a separate playback-queue:v1 snapshot with a runtime-owned prefix/backend containing stable track IDs, order, and playback mode. Temporary Favorites playback contexts, the current position, shuffle bags, and media URLs are session-only.

## Download tasks and history

Music Lists, Listen Later, Favorites, and individual playlists can start a managed download batch. One application-level manager applies a 1-5 worker limit, retries each song at most three times, and can cancel one song or the whole batch. Downloads unifies active tasks and saved records, with status selectors, per-song actions, pause/resume and retry. A one-track batch saves MP3 directly on success. A multi-track batch with successful files triggers one ZIP save containing every successful MP3 and a JSON report.

Permanent download history is stored separately under download-history:v1 with a runtime-owned prefix/backend. It records origin, timing, concurrency, complete `Track` snapshots, every attempt and managed error, cancellation/interruption, and generated file metadata. It never stores media bytes, ephemeral URLs, the Blob, or the user's final disk path. A refresh converts unfinished work to `interrupted` without losing completed attempts. Downloaded tasks remain in Downloads; confirmed record removal preserves saved files. Paused tasks restart media resolution when resumed. Byte-range continuation, track priority changes and automatic continuation after refresh remain unimplemented.

## Download view and runtime admission

Classic Downloads shares the [Discover song summary and full-name preview](../ui/catalog-track-view.md) in its song actions dialog. The header shows `歌曲操作` (Song Actions).

- Downloads use All, Downloading, Paused, Downloaded and Failed status selectors. Listen Later, Favorites and Downloads persist display preferences independently for each collection and region: All Songs, each platform detail and each download status. Unconfigured regions default to standard desktop density (the second option) and one phone column (the first option). When the collection is 760px wide or narrower and its arrangement tabs fill the row, or the host uses its phone layout, the single icon-only display button moves immediately before the bottom Filter launcher and matches its 36px height. Wider collections retain the toolbar picker. Placement follows the actual collection width, including desktop sidebar resizing. Holding download artwork for 500ms activates the same reorder gesture as Listen Later and Favorites; short clicks select only in operator mode and arrow keys move one slot in either mode. Active reordering uses the four-way move cursor, restored on release, cancellation or disposal. Download ordering persists stable task IDs separately from batch membership and scheduler admission; filtered reordering preserves hidden slots and progress updates never reset the saved order. Both Discover and Downloads use the operator's scrollbar-free horizontal rail: overflow reveals a right-side arrow that advances the row and returns to the start at the end; resizing or changing button counts updates it. Status and display buttons provide background feedback on hover and keyboard focus. A muted collection surface, white empty state, song rows, filter/operator launchers and a blue concurrency badge match the other collections. The badge places the number first, matching Listen Later and Favorites' numeric typography. Filters cover text, user tags, duration, platform and task date, with independent filter history. Each stable song ID has one download record across batches; another submission reuses its item ID and attempts and replaces its earlier list entry. The operator resumes paused tasks, downloads completed or failed songs again, pauses active tasks, cancels selected active/queued/paused tasks, and confirms record removal without deleting saved files. Mixed selections use Download and process eligible tasks; saved-only selections use Download Again. Cancel removes pending automatic resumes, aborts media/retry work, and keeps a retryable record. Cancelled records remain in the Paused selector with an explicit cancelled label. Row actions follow each task's current state and end with Actions. Song metadata shows the status. The song actions dialog offers the controls for the current task state. Generated output remains pending until saving is acknowledged; a saved item remains successful during partial batch retries. Native re-downloads first verify the current directory using the exact saved filename, byte length and full SHA-256, with one streaming check per shared ZIP artifact. Export title, recipe and creator must still agree before reusing that receipt. Missing, renamed, altered or unverified artifacts are downloaded again; matching bytes under a different name never suffice. Single-song output remains MP3 and multi-song output remains ZIP. ZIP verification refers to the saved ZIP, not separately extracted files. Userscript cannot inspect disk files and permits saving again without claiming local verification.

- Pause aborts reads/encoding, releases admission after cleanup, and retains stable task identity, attempts and explicit preview recipes. Resume restarts media resolution rather than retaining bytes or implementing HTTP byte-range continuation. Desktop and Android inject a Rust FIFO semaphore for complete-task admission; Userscript uses the frontend FIFO. Shared orchestration retains retry policy and the trusted browser encoder. Refresh/suspension cancels transient work without automatic replay; users explicitly restart interrupted tasks. Priority changes and byte-range continuation remain unimplemented.
