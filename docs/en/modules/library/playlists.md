# Playlists and portable transfer

[中文](../../../zh-cn/板块/资料库/歌单与导入导出.md)

The host owns stable playlist membership, order and the portable codec. Both themes consume readonly projections and named actions.

Playlists have one cover-card presentation without a style selector. It reuses the music-card grid and the controlled playlist renderer: landscape artwork above the text, a slightly larger playlist title and one clipped tag row underneath. Song count appears in a shadowed media-caption badge at the artwork's bottom right on card hover or keyboard focus, and stays visible for touch input. Artwork has no sequence number; the menu retains its independent hover background. The cards retain preview, selection and ordering. Node tests cover settings separation, host projections, clock resets and intents; they do not establish browser/GM/WebView layout, focus or physical-input acceptance.

- Classic My Playlists reuses the collection surface, count badge and responsive card grid from Listen Later/Favorites. Import Playlist (neutral outline) sits immediately before Create (primary fill), with both aligned to the right. Playlist Information sits immediately before Display Mode in the song-page bottom toolbar at every width, followed by Filter and Operator. Filters, operator selection, artwork hold-to-reorder, arrow-key alternatives, independent density preferences and overview navigation retain the collection contracts. The song-page header keeps Back and grouped All Songs / By Platform controls; it has no repeated title/count row or vertical collapse gesture. Details uses the track Actions dialog's subdued summary, with clickable artwork, name, song count and creation date, followed by the same three-column primary button group as track Actions: Like (add missing songs to Favorites), Download and Export, with icons above labels and the shared action-button motion. Existing tags occupy their own subdued, single-line preview region outside the summary; clicking opens the complete wrapping tag list and closing restores the preview trigger. Playlist cover cards use larger title typography below 8:5 artwork on wide layouts; single-column containers up to 600px use the same 72px artwork-and-text row as music cards, while compact two-column cells retain square tiles. They place primary-tinted tag blocks directly below the name in one clipped, non-wrapping row, with no descriptions or sequence numbers. Song counts use a shadowed badge at the artwork's bottom right on hover/focus, or persistently for touch input. Playlist cards keep the details action at the top of the title row even when tags are present; selection does not reserve a bottom row or a fixed body height. Artwork preserves its original ratio with a theme-tinted background filling unused space. Artwork and title open the playlist directly; image preview is available inside details only. Hover enlarges artwork with the same 1.055 scale and motion tokens as song cards, with no scaling under reduced motion. Name, Description, Cover and optional Manage Tags open horizontal detail pages with right-facing arrows and a bottom Back action before Save. Name and tag rows describe their purpose rather than repeating current values. Playlist and song options share one style definition for 28px leading icon columns, 12px gaps, typography, padding, separators and motion. Tag management matches track Actions: tinted removable chips, an inline add form and bottom Back. The main Actions footer only contains Delete Playlist aligned right; creation retains Cancel/Create. Cover upload is centered when alone; when Remove Cover is available, removal sits left and upload/replacement right. Export uses a content-sized centered button. Manage Tags uses the Discover platform-picker underline input and entry/focus animation; entering Description focuses the Back control. Creation suppresses duplicate-name feedback during a pending successful save and its closing transition. Closing retains the dialog until its leave animation finishes. Playlist labels use the tag plugin namespace and lifecycle with separate playlist associations; song-tag directory operations remain scoped to songs. Secondary buttons use the warm subtle-surface token. Playlist filters offer Text Search for names/descriptions, positive-integer song-count ranges, playlist user tags and cover status. Cover states support multiselect with OR matching; All Covers clears the specific choices. Text inputs, searchable tag checkboxes and count-range controls share the track filter editor styles and focus on mount so the underline starts with entry; ranges can be added, edited or removed, and valid pending bounds participate in previews and Confirm. Bounds are inclusive, blank endpoints are unrestricted, and multiple ranges/tags form a union within their dimension; dimensions intersect. Disabled tag contributions retain dormant conditions until explicitly confirmed again. Playlist filters reuse the music filter panel geometry, dimension rail, summary and choice controls: desktop has a left type rail, phones place it at the bottom, and each dimension has an isolated draft, live count preview and Back/Confirm actions. Only Confirm merges that dimension; Apply updates the collection and Cancel discards the panel draft. Playlist and song operators share the same selection row and scrolling action rail. Drafts survive presentation replacement; saving preserves stable IDs, membership and playback context. Name uniqueness uses NFKC, whitespace and case normalization. Creation exposes the same validated fields directly. Cover uploads accept JPG/PNG/WebP up to 5 MB and open a local framing dialog with landscape 8:5 or square 1:1 choices, drag/arrow-key positioning and 1–3× zoom. Confirm encodes only the selected source-pixel rectangle to JPEG with its longest edge up to 1024px in the separate bounded local cache, without enlarging small originals. Cancel preserves the previous cover; replacement, cancellation and disposal release decoded pixels, and late decodes cannot replace newer selections. Both complete themes use the same neutral crop dialog. Saved crops remain fully visible with theme-tinted unused space when a card uses another ratio. Previously saved low-resolution covers require re-uploading to recover detail. Cover preview uses a borderless lightbox whose image grows across the available screen area, with scrolling only at the screen edges and floating zoom controls, centered animated zoom, double-click zoom, Ctrl+wheel, native scrolling, Escape/Back and focus return. Closing retains the current artwork and zoom until the exit animation finishes; reduced motion disables scaling and entry motion. Overview controls and the song toolbar separate the header from content with a fine border. Song-page Back owns its button styles across slot boundaries. Returning to an overview preserves focus without treating pointer focus as a selected playlist. The shared modal semantics and no-referrer image boundary remain active. Node tests do not establish browser, WebView or touch acceptance.

- User playlist transfer currently uses JSON files (`any-music-playlist`, `schemaVersion: 1`), bounded to 5 MB and 5,000 tracks including recipe dependencies. It carries ordered membership, metadata, custom names and published custom-song recipes with stable creator attribution. Audio bytes, local cover caches, acquisition accounts, favorites and plugin namespaces are excluded. Import checks required basic fields, IDs, references and recipes locally before one additive save; it never requests a source or checks song availability during file import. Missing required track fields identify the field path. Opening a playlist starts cancellable descriptor checks, deduplicating custom-song leaves with at most three concurrent requests. Reordering the same songs keeps the current check, and progress updates are batched. Leaving, changing the playlist or disposing the host cancels pending work and rejects late results; presentation replacement keeps the same run. Checks release temporary descriptors/grants without playing or retaining media. A horizontal top notice summarizes failed songs and their AM status codes; details retain each song, classified network/missing-or-removed/access/account/source reason and upstream message, with explicit retry. Temporary failures do not delete songs or declare them permanently invalid. Import creates a fresh playlist ID, resolves duplicate names with a suffix, keeps existing local track data and favorites, and never changes the current user identity. Conflicting stable source identities or published recipe versions reject the import; failed saving leaves in-memory state unchanged. The document codec is independent of file saving, so a future authenticated server API can reuse it; imported creator IDs are attribution and grant no identity or ownership authority. Both themes use host-owned transfer actions; each runtime keeps its existing save adapter.
