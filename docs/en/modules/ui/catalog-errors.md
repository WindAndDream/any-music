# Catalog errors and recovery

[中文](../../../zh-cn/板块/界面/目录错误与恢复.md)

The workbench retains list and request identity across retry and verification. The [source adapter](../sources/listings.md) owns paging and cancellation.

- Music Lists retain request recipes, stable result metadata, and resumable positions without persisting iterators or ephemeral media. Reopening reuses retained results; recipes without cached results load page one on first view, and later pages load on demand. Errors during startup, search, URL import, saved-list restoration, or later paging stay in the affected list, including non-network failures and lists with partial results. Error details open only when the user chooses Handle Error or clicks the track-page error summary. Background updates, browsing, favoriting, reopening, and failed retries never open or reopen the dialog automatically. An offline first page does not require reentering the query. A later page failure keeps loaded tracks available and stops automatic paging, so scrolling does not repeat failed requests. Users can browse or favorite loaded tracks and explicitly retry after reconnecting. The track-page error summary stays sticky with the back bar at the top of the content region and reopens details when clicked. Valid and invalid states and the retry action remain visible.

- When a list fails or its content becomes invalid, its card shows a short status and a distinct Handle Error action instead of View Tracks. The error dialog holds the full cause, loaded progress, troubleshooting steps, and actions to retry, open the plugin center, or view tracks already loaded. Cards do not show a separate retry button. Retry reloads from page one; when tracks are already loaded, warn that the temporary results will clear and guide users to favorite anything they want to keep first. Error details do not offer a source-page verification/search shortcut. Account verification uses the owning runtime action. The host and theme share one error-dialog target: verification retains progress, successful verification or retry reloads page one and opens tracks after closing the dialog, and View Loaded Tracks closes it before navigation. Failed recovery keeps its actual cause actionable. Unavailable later pages alone do not prove that verification is required. Favorite Loaded Tracks remains available whenever there are loaded tracks left to favorite, including after a later page fails. Music Lists use the same content width as the track page without a 1600px outer limit. The grid fills available columns using a comfortable 300px minimum card width, bounded by the container; a single card keeps empty slots. Sidebar changes and narrow containers naturally reflow without viewport-forced column counts. Music-list cards remove the dedicated drag button and start two-dimensional reorder preview after holding blank card space for 500ms. Dragging uses the four-way move cursor across cards, their controls, and grid gaps, and release persists recipe order. In operator mode, clicks anywhere on a music-list card except its three-dot menu toggle selection, including text and primary actions. Native checkboxes toggle only once. Buttons, checkboxes, and text do not start hold-to-reorder. Pending holds neither capture the pointer nor block touch scrolling; movement beyond 8px, scrolling, early release, or cancellation clears the hold. Touch movement is intercepted only after activation. The card itself is focusable: Enter/Space toggles selection, and arrow keys reorder within the same group. Transferring implicit pointer capture from a card to the grid does not cancel reordering; only capture loss on the grid itself does. Refreshes to public loading, account, or error projections preserve dragging when IDs, order, and groups stay the same; actual order, group, or layout-size changes invalidate the old slot preview. Arrow keys move within the same group. Escape, pointer cancellation, blur, page or filter changes, and grid resizing cancel dragging without selecting cards; the endpoint click is suppressed. Pinned and regular lists reorder within their own groups, hidden entries stay in place, and reordering changes only the saved recipe order. Dragging over the other pin group clears the reorder preview and blocks the cross-group move. The shared amber top warning explains that pinned and unpinned lists cannot exchange positions and asks the user to unpin first. It appears once per drag, dismisses after three seconds, and does not take focus; returning to the original group allows reordering to continue.

- Disabled sources use `disconnected`; uninstalled sources use `missing`. Loaded tracks, filters and favorites remain available while new loading stops. Idle lists show a neutral notice without reopening old errors. Active loading or verification is cancelled, late results are ignored, and an interrupted-load status remains available for manual inspection. Re-enabling neither repeats that error nor requests new pages; explicit retry rebuilds page one. An idle list retains its cursor while disabled and resumes on demand. Empty lists cannot open tracks. Enabled sources with failed validity checks keep actual error handling. Affected playback returns to idle, related downloads and exports stop, and saved lists, tracks and queues remain intact.

- Track lists show a read-only platform and actual request account. Discover account preferences apply to new operations. Desktop restores each platform's last selected account and displays its name. With no valid saved choice, it saves a default in fixed account-list order, preferring an enabled, non-pending ready account; login or verification issues do not replace a saved choice. Removing or disabling an account makes an idle list choose an available account and rebuild page one on its next load. Active loads retain an inline interruption error for manual inspection; retry chooses an available account and directs users to Settings if none remain. The full-title button has horizontal padding, with measurements subtracting the same inset. List-action details place loading progress and pin status in one row, allowing progress text to wrap on narrow screens. Classic list renaming slides into the same dialog and reuses the song-name form: custom name first, then “搜索原名” (original search) with the exact query or “导入来源” (import source) with the exact link. Back discards the draft; saving a changed, nonempty name of at most 80 characters returns to list actions without changing the original request. Pin and Unpin resolve the current list by stable ID even after its action dialog closes.

- The sticky error bar shows one clickable error summary, without separate Handle Error, View Details, or source-page buttons. Clicking the summary opens Music List Error Handling; account verification and retry actions remain inside that dialog. On phones, dialog actions use content-sized buttons with a comfortable minimum width and wrap as needed, instead of stretching across each row.

- While waiting for account verification or reloading page one, the error dialog uses a neutral progress summary and hides the previous error code. Reloading also hides outdated instructions and the generic list-loading warning; an actual reload failure restores its error details. Restored verification errors expose Verify immediately when the runtime supplies recovery; Retry is not a prerequisite. The desktop Verify button uses the same surface background and outlined style as the Userscript source-verification link, while Retry remains the filled primary action. Retry means another attempt to load; users must first complete any required login or security verification. Desktop verification guidance emphasizes the warning that retrying before completing verification may produce the same error in bold. Automatic loading after verification uses Reloading progress text. Restore Original Names and Restore Filter History continue to describe restoring existing content.
