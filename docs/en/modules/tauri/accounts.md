# Desktop accounts, proxy settings and verification

[中文](../../../zh-cn/板块/桌面与移动端/账号与代理.md)

Native account state drives identity, proxy routing and verification. Renderer views receive only public projections and named operations.

## Accounts and verification

NetEase Cloud Music is built in on desktop with account-bound HTTP/media, native QR polling, and the account's embedded official page for login and verification. Rust verifies the official account/profile identity before committing credentials. See the [NetEase integration record](../sources/netease/api-integration.md) for protocol observations and outstanding live GM/desktop acceptance. Mobile does not register this source.

Official account pages are child WebViews of the product window (`browser/embedded`). Each account owns one persistent page context: a WebView2/WebKitGTK data directory under `profiles/<uuid>/webview`, or on macOS a WebKit data store derived from the account UUID, plus an exclusive store lock and its assigned proxy. Hidden pages keep a 1280×800 viewport outside the visible window area with background throttling disabled, so official layouts, lazy lists and scroll observers behave like a visible tab. A document-start bridge reports only allowlisted fetch/XHR exchanges (Douyin `/aweme/v1/web/` and `/passport/web/`), the serialized main document of work pages and fixed native script results; it disables media playback and never deletes or rewrites website DOM. Reports go through `account_page_report`, the only command of the separate `account-pages` capability: remote Douyin/Bilibili/NetEase origins, `account-page-*` labels, no local callers. Each page also carries a random token and is routed to its own actor. A driver presents these pages to the existing account actors as a bounded CDP subset (targets, navigation, evaluation, page-side input, cookies through the native WebView cookie API), so login, search, detail and import state machines keep their established request identity, budgets and cleanup. Stored native credentials seed a new page context once, so signed-in accounts keep their session. Product commands take the invoking `tauri::Webview` and accept only the `main` label. This transport has automated tests only; it has not received live website acceptance.

First installation starts with an empty account list and never creates default accounts. Users prepare login drafts and complete native verification before built-in accounts enter the list. External declarative gateways offer no-login access only when explicitly declared; see [Music Source Authentication](source-authentication.md). Existing saved accounts are preserved; restarting after deleting all accounts does not recreate any. Accounts support add/delete/rename/enable and direct access or one primary unauthenticated HTTP(S)/SOCKS5 proxy with up to eight ordered backups. The account connection settings and native routing own this bounded failover chain, as described below. Proxy authentication and proxy-group UI remain unavailable; independent account-pool/network-routing algorithms do not establish native connectivity or live acceptance.

The permanent entry is Settings: “Music sources → Account management” owns accounts, login/verification, connection assignment and automatic request policies; “Network and downloads → Proxy management” saves multiple independent proxies, shows assigned accounts and allows deletion after assignments are removed. Forms reuse shared settings cards, switches, control radii and single-column container adaptation. The temporary window toolbar is removed.

Proxy settings have separate Add proxy and Proxy management regions. Field errors appear beside inputs; failed saves retain drafts, and successful native saves clear them after snapshot confirmation. Compact rows show name, protocol, endpoint, assignment count and account names, adapting to narrow containers. Both renderer and Rust validate unauthenticated HTTP, HTTPS and SOCKS5/SOCKS5h endpoints with valid IPv4, bracketed IPv6 or domain hosts and explicit ports from 1 to 65535. Paths, queries, fragments, credentials and abbreviated IPv4 forms are rejected. Trimmed names must be unique. Endpoint deduplication normalizes scheme/host case, the terminal domain dot, IPv6, port digits and the trailing slash while preserving explicit default ports. Rust validates and deduplicates within the same configuration transaction to prevent concurrent duplicate saves. Syntax validation does not establish proxy connectivity.

The Discover page opens the platform account switcher. Its button shows the selected default account's custom name on every platform. Each platform restores its last selected public account ID before startup refresh. Without a valid saved choice, it selects the first enabled, non-pending ready account with credentials (or anonymous access for an external source), falling back to the first enabled, non-pending account, and saves that choice. A saved account awaiting login or verification remains selected so its recovery state stays visible. A platform with no accounts displays “无账号” and offers “添加” to open a standalone account creation dialog with that platform preselected, including for sources that allow anonymous access. This entry never opens global settings; the protected dialog retains standard enter/leave motion and closes back to Discover. Manual selection persists only a public account ID and applies to new searches, imports, session checks and playback/download resolutions. Existing lists and media retain their actual identity when search preferences change. Inside a track list, the platform and request account are read-only; retry prefers its original account. Removing or disabling the selected account chooses and persists a replacement by the same fixed order; no enabled, non-pending accounts leaves the selection empty. An idle list chooses an available account on its next load and rebuilds from page one without mixing old cursors. An active load stops and opens an error dialog; retry chooses an available account. If none remain, the error directs users to add or enable an account in Settings. Switcher and settings share the theme and modal host. Validation covers components, state composition and Rust tests, excluding application visuals and live account checks.

Generated account UUIDs bind an isolated CookieStore/client, encrypted credentials and `profiles/<uuid>`. Frontends cannot provide filesystem paths. The OS vault holds a 32-byte key; credential files use ChaCha20-Poly1305, without plaintext fallback. The embedded page engine manages its own page storage; the app reads cookies only through the native WebView cookie API and never puts credentials in URLs/logs.

Bilibili retains native QR generation, polling, confirmation and cancellation. Production Douyin login uses Rust `douyin_browser` to drive official pages in the account's embedded page. The app shows official PNG QR images and observes scanning, MFA, SMS send/submission and account confirmation through the page bridge. User-selected SMS and six-digit input operate uniquely matched official controls; face, send-SMS and unknown challenges show the same account's official page in the in-app page dialog. Login UUIDs scope replacement, cancellation and SMS. Private challenges remain in the page/native memory; stale results cannot update a new session.

Bilibili's native generation endpoint was checked on 2026-10-20 and returned `https://account.bilibili.com/h5/account-h5/auth/scan-web` with the same 32-character challenge key. Both Rust challenge construction and Android intent validation accept that exact host/path and the previously observed Passport scan route, with HTTPS and a single 32-character challenge key; ordinary account pages remain rejected. Android reports invalid handoffs separately from application launch failures instead of treating every rejection as a missing installation. Douyin's QR/check response allowlist covers the exact Passport paths on `www.douyin.com` and `login.douyin.com`. Auxiliary profile reads for browser operations preserve up to 32 in-flight login requests and 96 ordered events for the main account actor, without retaining response headers or signed queries. They cannot silently consume the QR or confirmation transitions.

Background work never opens a window: hidden pages stay outside the visible window area and are absent from the taskbar and Alt+Tab. Only the presented page of an explicit login or verification is placed over the in-app dialog's placeholder, using geometry reported by the renderer (`account_page_layout`). Verification pages stay hidden until the official page shows a login or security challenge; the challenge's dialog box is then isolated by `visibility` rules without removing DOM, and the dialog reserves its size. If no challenge is recognized within 12 seconds of loading, the whole page is shown. No headless flag or fingerprint spoofing is used; macOS pages use the system Safari version in their User-Agent. Platform risk decisions are not guaranteed to match visible browsing. Explicit visible handoff closes the account's pages before reopening its persistent context; previous QR/challenge continuity is not promised.

Each account owns a UUID, an embedded page context, an exclusive store lock and its assigned proxy. Exit/cancel closes every page and retains the context. Bounded per-page body buffers (16 bodies, 24 MiB) hold reported responses until their actor reads them. Missing login bodies wait for fresh official account confirmation rather than implying success. An authenticated user object plus a valid login cookie are required before the native WebView cookie API reads platform cookies, including HttpOnly values, into the encrypted native vault with the page's actual User-Agent. Credentials never cross renderer IPC. Standalone account checks query the official identity endpoint through Rust HTTP on demand. Completing visible verification rereads current cookies and closes the presented page. Expired short-lived cookies do not abort valid credential import.

Bilibili/NetEase in-app login pages read cookies and the page User-Agent once after the user selects “我已完成登录”, then close that page. Test-browser contract observations do not establish production account or Rust HTTP acceptance.

Browser verification pauses that account and cancels its old session without blocking other accounts. Explicit login rejection and known challenge signals produce signed-out and verification states respectively. HTTP 403/429 alone do not establish expiry, and challenge evidence takes priority over HTTP 401. Anonymous session checks do not expire anonymous accounts. Each account has one API request slot, jitter and bounded exponential backoff; three consecutive network/timeouts pause it for user inspection. Unknown errors are not classified as proven proxy failures. There is no automatic direct fallback or periodic background login probing.

Douyin identity checks and search use the following state boundaries. Chrome confirmed the identity response and the guest distinction, while Rust and renderer tests cover native projection and stale results. Production native HTTP acceptance remains separate.

Native accounts expose independent `state.login`, `state.verification` and `state.connection` facts. `status` is the account pool routing projection; `authentication` describes stored credential mode. Signed-in and verification-required can coexist. New accounts declare login, verification and connection facts explicitly; persisted accounts must contain those facts. Pausing content for a login action does not record a fabricated CAPTCHA requirement. Cancellation and restart release that operation pause while preserving actual content challenges. A Douyin account without stored login credentials is reported signed out without opening an account page.

Routing preflight failures carry the concrete account ID. First-page and pagination challenges bind it to the listing; the verification action exists only while that identity remains present and enabled. Launch failure, browser closure, cancellation, timeout or confirmation failure retain the original request reason and show the action's cause and retry in the same details view. Completion confirms official search results, identity and credentials before refreshing the snapshot and reloading page one. Snapshot failure or cancelled loading exposes the Retry action without another browser verification. Only the listing's own successful credential update can cross this recovery phase; deletion, disabling and proxy changes still cancel old work. Regression tests cover the production source adapter, account selection, listing states and mocked native IPC, without live account-browser acceptance in this update.

| Observation or operation                                                                                 | Account state and recovery                                                                                                                       |
| -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Official profile during login, or matching identity UID during a check, with usable login cookies        | Valid login; retain any separate content verification requirement                                                                                |
| Missing stored login cookies or a valid response identifying a different UID during an HTTP check        | Signed out (login expired); login is available                                                                                                   |
| Official login rejection or login panel while browser login cookies remain                               | Verification required; retained cookies do not prove platform acceptance and establish neither expiry nor success                                |
| `2483`, a verification link or search `verify_check`                                                     | Verification required, taking priority over HTTP/business authentication rejection; retain credentials                                           |
| Missing identity fields, unknown response code, changed format, connection failure or timeout            | Check incomplete; preserve account state and retry the identity endpoint on demand                                                               |
| QR expiry, closed verification window or cancellation                                                    | QR expiry belongs to that scan; cancellation proves neither logout nor completed verification, and saved accounts retain their pending challenge |
| Official search response confirms completed verification, followed by fresh identity/cookie confirmation | Save current credentials and restore availability; restart the same listing at page one                                                          |

The portable adapter parses search state and optionally reports it through `reportFailure` for the current account/listing. Rust checks target ownership, same-account cookies and the current session epoch before persisting public state. Request IDs support cancellation; old listings, replaced account environments and late results cannot overwrite newer state. Unavailable account candidates retain the actual verification or connection reason. Account checks count logout, verification and incomplete checks separately; SMS requests, submission, official confirmation and retry each display their operation progress.

## Windows development background-login experiment

The isolated Douyin login experiment runs through the standalone Rust example in Windows debug builds. Experiments remain independent of production account CDP sessions, never read/update product accounts, vaults or everyday profiles, and do not establish production acceptance.

Compare system Chrome (Edge when Chrome is absent) with headed `--no-startup-window` plus CDP `Target.createTarget(hidden: true)` against modern `--headless`. The official page owns QR generation, signing, polling and SMS requests. Rust observes exact allowlisted endpoints and operates uniquely matched controls. Unknown UI or security challenges stop automatic actions. Only clicking the visible-browser entry closes the background process and starts a new official login with the same temporary profile; QR/challenge continuity is not promised.

Each run has a UUID, temporary profile and loopback debugging port. A Windows job owns the process tree; a window-show event hook starts before launch. “No window observed” is an event observation; flashes/taskbar/Alt+Tab still need human acceptance. SMS requires explicit input. Duplicate actions, resend cooldowns, response sizes and a ten-minute duration are bounded. Cancellation, replacement, exit and timeout end listeners/processes and clean only a verified profile path. Cleanup failures are separately reported.

Browser success requires official final confirmation and an authentication cookie. An in-memory CookieStore and the same User-Agent then replay the browser's freshly signed `/aweme/v1/web/user/profile/self/` URL through Rust HTTP, applying the existing self-profile user-object criterion. This checks credential handoff/native transport, not the portable adapter's independent local `a_bogus` or all music operations. Cookies, challenge tokens, request URLs, unmasked phone numbers and codes do not enter public results/logs.

The opt-in live driver uses the same backend: `cargo run --manifest-path apps/tauri/src-tauri/Cargo.toml --example douyin-login-experiment -- headed-hidden` (or `headless`). Run only when explicitly requested. Temporary QR PNGs are deleted on exit. Manual actions are `sms`, `code <six digits>`, `visible` and `cancel`.

Neither temporary-Profile experiment passed its 2026-10-03 adoption criteria: headed mode stopped at secondary-verification controls and headless mode did not find the login entry. Complete QR/SMS confirmation, native credential handoff and strict invisibility remain unaccepted for that experiment. Production uses persistent embedded account pages; experiment results do not accept that path.

## Account settings and request connections

Native account identity is `(platformId, platformUserId)`, separate from the browser/Profile UUID and editable local name. Login commits and official identity checks reject another configured account with the same platform identity, including disabled accounts. Unauthenticated entries cannot be identified before login. Bilibili uses the native official login's `DedeUserID` and nav `mid`; Douyin uses the validated self-profile `uid`. An existing profile cannot be rebound to a different user. Deleting and re-adding the same platform user creates a fresh runtime UUID and credentials, while public name projections link its previous incarnations.

`accounts.json` atomically retains public account history with ordered name periods (`fromMs`/`untilMs`) and removal timestamps; deletion still removes credentials, connections and browser data. No historical name list crosses IPC: `accountLabels` projects only the latest label for each incarnation. Rename/status updates do not duplicate unchanged name periods. Tracks may retain bounded, display-only `acquisition` metadata (account UUID, name at acquisition and time). Track details resolve the latest name through this projection; persisted provenance never chooses a request account or revives removed operations. The library and download history retain the acquisition snapshot. Previously saved tracks without provenance remain valid and do not invent an account association.

Deletion confirmation separates its short question from three labeled consequences: data to clear, operations to stop and saved data to retain. It explicitly retains songs, music lists and account name history.

Account management immediately shows platforms with total, signed-in, login/verification and disabled counts, with Add account and Check all actions aligned at the bottom right. All layouts omit the redundant introductory text and retain the account-isolation hint. Creation opens within the management dialog, preserves the name draft and supports platform selection; adding from a platform list preselects that platform. Compact continuous account rows place the name, status, connection and check action together, with spacing between the details entry's hover background and its check button. Results appear within the status line: a valid-login result replaces the duplicate signed-in label without adding a result row. Failed checks retain known account facts, disabled accounts show their disabled state, and longer errors can wrap. Details separately edit the name, connection and login state, with Delete account beside Back in the footer and a separate deletion confirmation. Dialog paths start at the current platform or creation popup and exclude the outer account settings. A clickable path returns to any ancestor within the popup; closing its root returns to the platform overview. Long paths scroll horizontally with a hidden scrollbar. Narrow screens retain bottom sheets. Action buttons use content widths and wrap when needed, retaining at least 44px click heights. Trimmed names must be unique within a platform, with native validation immediately before persistence.

Management offers Check all, while account lists and details offer individual checks. Checks run serially with fixed identities and skip disabled accounts. Bilibili and Douyin report accounts without stored login credentials as signed out without a site request. Each checked account performs one platform session check without identity competition, automatic login or replay. Closing settings or cancelling aborts native reads and ignores late results. The allowlisted identity probes can run while content is paused. Douyin uses GET `/aweme/v1/web/query/user/` and accepts the returned UID only when it matches the stored account binding. After the identity check, the account-owned hidden WebView reads the official `/aweme/v1/web/user/profile/self/` API within a fixed budget. Rust validates the bound UID and returns only the nickname. The nickname read leaves the native login and verification state intact. The last verified nickname is stored with the native account metadata, is displayed after restart, and is retained on read failure. Native authentication evidence updates the status; network errors, timeouts and invalid responses never establish expiry or clear stored credentials. A valid identity never clears a separate content security challenge; the check continues to show required verification. Signed-in accounts disable repeated QR/browser login until expiry or required verification is confirmed.

Login presents QR and “应用内网页登录”. The latter opens the account's isolated official page in an in-app dialog whose “我已完成登录” action saves the login; closing the dialog cancels it. QR generation, encoding or display failure disables that account's QR entry and directs users to the in-app page; expired QR codes may be regenerated. Secondary verification presents the platform's actual methods, with methods the app cannot complete natively shown in the in-app page. Closing, switching methods and late results are isolated by login UUIDs so an older operation cannot end a replacement session.

Connections select one saved primary proxy and up to eight ordered backups, or direct access. Replay-safe Rust HTTP reads fail over only on proxy connection errors, connection timeouts or proxy authentication failures, retaining the account and CookieStore. A successful proxy is reused within the current account environment. Connection attempts share a total budget, while successful media streams do not inherit the short connection timeout. Writes are not replayed; source authentication/security challenges are not proxy failures, and direct access is never an implicit fallback. Douyin reopens the account's embedded pages with the next proxy only for proxy/tunnel failures; a proxied navigation that produces no document within 15 seconds is reported as a tunnel failure. Existing later-page requests prompt a listing refresh rather than reuse a cursor from the previous browser.

Deletion confirmation explains that requests, playback, downloads and login verification will stop; accounts in use can be deleted. Native operation startup and deletion share an atomic gate. Deletion blocks new work, cancels old sessions and queued requests, revokes media grants, ends browser verification and releases renderer usage before deleting credentials and detaching the validated Profile through a same-volume rename. A single background collector reclaims cache files and retries tombstones after restart. Failed detachment retains a disabled account and an actionable error for retry. Runtime invalidation synchronizes lists, cached sessions, the player and downloads. Affected playback returns to idle without advancing; other accounts and saved tracks, lists and queues remain intact. Invalidated lists rebuild page one before paging again.
