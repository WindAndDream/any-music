# Desktop Douyin catalog and viewport handoff

The account-owned child WebView executes official-page operations and the workbench owns the product result state. This page explains search, paging and the Windows isolated-world adapter.

## Search lists and security-verification recovery

The current production account returned HTTP 200, business code 0 and `search_nil_info.search_nil_type=verify_check`; the app displayed a verification error. The rebuilt desktop artifact also passed these page-one/page-two interactions. A normal native response contained a one-work first frame, an acknowledgment and a later nine-card frame; filtering related-search cards left nine tracks. The original one-item response without a next-page action was not reproduced, so the current challenge does not establish its complete cause. This evidence covers production Rust/IPC, desktop list interactions and manual verification recovery, excluding GM and media playback; website-contract captureDate remains unchanged.

Account browsers start at the Jingxuan homepage `/jingxuan`, confirming identity from an official self-profile response and login cookies. If no profile arrives within five seconds and there is no pending profile request, QR code or login challenge, startup creates at most one temporary auxiliary page at `/user/self` for compatibility. The explicit self-profile import operation can read `sec_uid` for a ready account. It and credential confirmation after verification can use independent auxiliary pages. These auxiliary pages are always hidden. Success, failure, cancellation and timeout close the temporary target; current listing and verification-search responses remain observed during checks. These checks neither reload nor navigate the visible page and retain official identity evidence, read budgets and cancellation. This update did not launch the app/browser; consistent homepage profile responses and the updated auxiliary-page behavior still require live acceptance.

Before submission, initialization and unique official controls are checked every 250 ms; after one confirmed click, authentication/challenge inspection returns to once per second. Rust focuses/selects the official input and inserts the keyword with the page's own editing command (falling back to the field's native setter and an `InputEvent` when an unfocused page refuses it), waits one task turn and re-reads current controls. Controls count as ready only after React owns both the input and the button (`__reactProps$` on each node): server-rendered controls exist earlier but silently drop input and clicks. The official homepage hydrates only after its full script set loads (about 110 scripts), which a standalone WKWebView baseline on a slow link measured at 5 to 32 seconds. Only a retained exact keyword, matching React field value and an unobstructed button center permit the click. On macOS the click is a native AppKit mouse event delivered to the account WebView (browser-trusted, `isTrusted=true`), with CSS points offset by the view's obscured top inset reported by the page bridge; on Windows it is a WebView2 DevTools-protocol `Input.dispatchMouseEvent` move/press/release sequence in CSS viewport coordinates, which pages also receive as trusted input. Other platforms, or a failed native dispatch, fall back to the CDP-subset mouse sequence. Loading and hydration have a 60-second budget measured from navigation or adoption of the account homepage; producing the requested result page has 18 seconds after the click or after a later page is due. Discover keeps one keyword search WebView per account. The first search takes over the hidden account homepage after identity is confirmed. Leaving the list releases its cursor and cached responses, and the WebView can stay offscreen for 90 seconds. The next search clears the official top search field and submits from the result page after the presentation lease releases its mask. If the result controls are unavailable or the click starts neither navigation nor a search request, the same WebView returns to the homepage to submit. Each submission admits only requests started for its own keyword after the browser's submission timestamp. Native search waits 85 seconds per page action and 100 seconds per command, and the renderer allows 105/115 seconds. The search reader waits for the matching official request after submission. On 2026-11-16, with explicit user authorization, the embedded transport on macOS returned keyword results, three pages from one listing page (the page issued each later `search/single` request after scrolling) and playback through the official detail API; no risk challenge appeared, so in-app verification was not exercised in this run. Later the same day the user confirmed the same login, search, pagination and playback flow on Windows x64 with the WebView2 trusted click; that run did not exercise a challenge either. Timeout messages distinguish controls not ready, submission not confirmed and unfinished search responses. Listings keep separate cursor chains even when they reuse the same WebView.

Background searches, visible verification and app restarts reuse the account's single embedded page context. Handoff closes every page and waits for the page driver before releasing the store lock. On Windows desktop, Discover can lend the account's native result WebView to the active track-list viewport. The source adapter publishes the account, query, WebView and admitted origin. Rust loads a build-owned Vue bundle into a WebView2 isolated world. The bundle mounts the same Classic or Studio track list and theme styles inside one closed Shadow root. The original page remains in place with its result geometry intact. While the native list is visible, the injected document style masks the website's background and top-level content, suppresses paint for original images, videos and canvases, and disables interaction with original nodes. The mask updates only added or removed body children and preserves the official result scroller. The projection carries display fields, and the isolated world returns bounded list actions to the active workbench, which owns playback and mutations. Other desktop engines use the standard app view until an isolated-world adapter is available for them.

The desktop app's Douyin track results and the Windows child renderer both use measured virtual track lists. Classic uses its track-card grid. Studio uses its native table or a grid for card styles. The workbench keeps the complete result collection and its selection. Each renderer mounts the viewport and overscan using its own theme scroll container, and the child uses the main window's breakpoint. Windows stages the result page offscreen at the list size and reveals it after virtual geometry, the restored position and the website mask have painted. A partially clipped viewport or read-only reopening uses the app list. Opening a song actions or display settings dialog restores the app list at the latest checkpoint and waits for the child to move offscreen. After the dialog closes, the child takes over once it has painted the current window. When the final page arrives, the app restores the virtual window before releasing the child.

The host track view prepares the first viewport before handing presentation to the injected list. Both use the measured list's full scroll extent for pagination. Restoring the checkpoint does not request another page. Downward input can request the next page within 1.5 viewport heights of the end, bounded to 240–1600 CSS pixels. Filtered results retain the normal scroll threshold. The shared listing admits one pending page. The Douyin adapter advances the original results scroller on demand while preserving its layout, consumes exact captured cursors and surfaces official verification through the account dialog. The Windows composition still requires live layout, scroll handoff, pagination, verification and memory acceptance.

Douyin search and search-URL import continue to read official `search/stream` and `search/single` responses through account-owned embedded pages. The portable adapter parses streams and maps tracks. Every listing has its own page, keyword and cursor chain; consumer scrolling requests the next page. Official preloads use bounded caches without replaying requests. Closing a listing or cancelling a read closes its target. Scrolling first follows the official `[data-e2e="scroll-list"]` result list's content ancestor, supporting Jingxuan cards without work links. Legacy work links and window scrolling remain fallbacks, avoiding sidebars. Visible captchas and login panels produce distinct verification and authentication errors. A current-page timeout uses `AM-4003` and suggests retrying; it does not establish a challenge or exhausted results.

When a result container exists, each wheel increment targets a visible hit-tested area inside it: the page receives a wheel event and, unless the page cancels it, the nearest scroll container under that point scrolls by the increment. The document scroll area is used only when no result container exists. There are no other direct scrollTop changes. Each increment rechecks visibility and remaining distance. An occluded container or nested scroll area waits rather than redirecting input to a sidebar or outer page; no wheel input is sent at the bottom. Scrolling and challenge-address detection recognize both `/search/` and `/jingxuan/search/`. Challenge-address detection excludes search keywords in either path so terms such as `captcha` do not falsely require verification.

Rust `search/scroll.rs` owns later-page pacing: an initial 180–420 ms wait precedes a short segment of at most 480 px, divided into 16–22 wheel increments with gradual acceleration and deceleration. Increments wait 28–46 ms; segments pause for 350–1400 ms, with bounded variation in distance and timing. Scrolling follows consumer demand and cached pages need no input. Once the requested cursor's request starts, scrolling stops while its response is pending. Timers live only inside the current read future and never catch up delayed steps; completion, cancellation, verification or the existing 18-second page timeout ends that scroll round and retains established cleanup. This improves input pacing without guaranteeing avoidance of platform risk controls. Deterministic tests cover these pacing and cleanup budgets; native runtime observations are recorded below. ## Douyin verification scope

Recorded Windows production observations establish scoped QR/SMS credential commits (2026-10-03), account-owned multi-page search and segmented native scrolling (2026-10-25), and user-completed verification followed by first-page recovery (2026-11-01). Empty-page reconciliation, response isolation, retries, cancellation and process cleanup have deterministic regressions. These observations were recorded with the previous system-browser transport and do not accept the embedded-page transport, which has automated tests only. They also do not establish GM transport, complete result exhaustion, every account combination or full playback acceptance.

The original cached empty responses and earlier seven/eight-page failures were not retained, so their exact causes remain unknown. Separate intermittent first-page timeouts also remain unexplained; a timeout alone does not establish a risk challenge. Website contract `captureDate` is unchanged. Native command changes require rebuilding/restarting Rust; frontend hot updates cannot replace a running native process.
